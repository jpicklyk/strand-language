# Strand

A programming language for AI agents to generate, not for humans to author.

Strand programs are content-addressed graphs of typed nodes with mandatory effect declarations. The artifact of record is the verified graph: there is no canonical text syntax and no character-stream serialization the language treats as source. Agents emit compact text projections — Layer A, and the familiar-shaped Layer F — that lower mechanically to the canonical graph before verification, and these projections carry no program identity.

The project is a research investigation with a working reference implementation. Its question is whether a program representation built for machine generation and machine verification gives better outcomes for AI-generated software than text languages adapted for AI use. The results to date answer that unevenly: the safety and analysis properties that attach to the verified graph are implemented, measured and independently reviewed, while the predicted advantages in generation accuracy and token cost have not appeared in measurement. Both halves are stated below.

## Purpose

Strand is a different *representation* of programs, designed around a consumer that is a program rather than a reader: an orchestrating host, or the generating agent itself, that must decide from an artifact whether to admit it, what to grant it, and whether to run it. Syntactic errors are not a category of the canonical form, because a graph operation either succeeds or fails with a structural reason. References are by content hash, so identity is stable across every store that holds a node. Every effect a node performs is declared as a typed edge, so the set of effects a program can reach is computed by graph traversal rather than recovered by whole-program analysis. State machines are graph fixpoints, so long-running programs and pure computation share one algebraic foundation.

The five integrated design claims are stated in [`02-core-thesis.md`](02-core-thesis.md) and their motivation in [`00-motivation.md`](00-motivation.md). They predict five outcome advantages, which the thesis does not weight equally. Structural safety and first-pass correctness are the lead claims: the maximum harm of a generated program should be computable from the artifact before it executes and bounded while it runs, and structural verification with machine-readable diagnostics should let an agent converge on a correct program in fewer attempts. Inference cost is treated as a constraint to be bounded, not a headline result. Native distribution and confidential-computing integration are long-horizon claims that depend on runtime and hardware work not yet begun. [`ADR-010`](decisions/ADR-010-reasoning-surface.md) adds a decision that sharpens the first claim: reasoning about a verified artifact is a first-class capability of the language, with a stable machine-facing surface and a soundness obligation, on equal footing with executing it.

Against the strongest alternatives — capability-checked text languages such as Scala capture checking and Flix, and runtime mediation such as CaMeL — the thesis stakes a narrow comparison ([`02-core-thesis.md`](02-core-thesis.md) § strongest-alternatives). Where the consumer of generated code is not its producer, where the bound must be re-derived from the artifact long after generation, and where verified components must keep one identity across distribution, the graph-native form provides properties those approaches do not. Where those conditions do not hold, the alternatives are stronger: the model emits a language it already knows, the ecosystem applies, and a human can read the result.

| First-pass correctness (lead) | Not supported by measurement to date | [`evaluation/dynamic-results.md`](evaluation/dynamic-results.md) Runs 7 and 8 |

**Structural safety.** The containment measurement (Q-044) defines the harm bound of a graph as its effect closure intersected with the capability grant, the budget and the sandbox policy, argues its soundness, and executes a matrix of six harm classes an agent can plausibly emit. Two are rejected at verification (confused-deputy argument drift, undeclared effects) and four are bound at runtime with structured errors (resource exhaustion, path traversal, server-side request forgery, credential leak through an error stream); stock Python contains none of the six by default. The result establishes that the bound is computable and enforced. Its limits are stated in the same document: soundness is argued with witnesses rather than proved, the baseline is unconfined rather than one of the strong alternatives, and the study measures what the language contains, not how an agent behaves under it. A strengthened matrix against sandboxed and capability-checked baselines is designed ([`proposals/strengthened-containment-matrix.md`](proposals/strengthened-containment-matrix.md)) and not yet executed.

An independent code review on 2026-09-29 tested the soundness argument against the implementation and reproduced failures of it with hand-built programs: a builtin binding that under-declared its effects verified with an empty closure and wrote a file under an empty grant; verification time doubled with each shared node, so a thirty-node program stalled the admission gate for minutes; and duplicate field names let a verified program reach a runtime type error. It also read-verified a set of runtime gaps, among them unchecked callback dispatch, request-path injection and redirect following past the network sandbox, and a bytecode VM that enforced capabilities by category only. These are closed, by the builtin signature and effect verification of Q-056 and by the review remediation recorded under Q-076 and [`security-index.md`](security-index.md) § Review-driven hardening; each closure is pinned by a regression test, and the adversarial negative corpus under [`corpus/negative/`](corpus/negative/README.md) now holds 47 programs that must be rejected. The residual trust assumptions are explicit: foreign bindings outside the builtin namespace are declaration-trusted, the in-process builtins are not isolated, and the static closure is a sound bound only together with the latent closure described next.

**Reasoning over the verified artifact.** Verification produces typed facts a machine consumer can query. A `ProgramAnalysis` over the verify result answers, per subgraph, the direct effect closure, the latent closure (effects reachable only through tool implementations and higher-order callbacks), their union as the total pre-execution reach, the capability requirement a caller must grant, the egress intersection, the harm bound under a specific grant, and the capability difference between two revisions. `runGuarded` refuses a program whose total closure exceeds a declared budget before any effect occurs, and an opt-in audit log reconciles the declared closure against the effects performed in a run.

**First-pass correctness.** The prediction has not held. In the latest full comparison (Run 7, fifteen tasks, one sample per cell) Strand verified on the first emission in 11 of 15 tasks against 15 of 15 for both Python and Kotlin, and all three converged within five attempts. Run 8, a minimal-core prompt over ten cells including seven semantic-error probes, recorded 3 of 10 first-pass and 10 of 10 converged within four emissions, which shows the verifier-feedback loop recovering every probe but not an advantage over a baseline. The suite is small and hand-authored, the baselines are at ceiling on it, and every run is a single sample with byte-proxy token counts, so the measurement can neither confirm nor refute the claim; on the evidence so far it stands against Strand.

**Inference cost.** Static per-emission cost favours Layer A on a small sample: 0.81× Python with type hints (geometric mean, three hand-written programs, a bytes-per-four-characters proxy, with the density levels iterated on those same programs), against 5.58× for the canonical dag-json storage form. Dynamic cost does not: Run 7 measured 28,092 tokens per successful task for Strand against 1,792 for Python and 1,255 for Kotlin, 15.68× and 22.39×. Almost all of the gap is the in-context language reference, an 86 KB system prompt against 3 to 5 KB for languages the model already knows; per-emission output is smaller than Python's on every task. Prompt caching, a minimal-core prompt with on-demand reference sections, the familiar-shaped Layer F surface, and training on Strand corpora are the amortization paths. The first three are implemented in whole or in part, and none has been measured at more than one sample per cell.

**Identity across implementations.** The canonical encoding is a versioned compatibility contract (currently epoch 3). Every corpus program's root hash is pinned as a golden vector, and an independent Python encoder written from the specification alone reproduces all 93. This is the one cross-implementation result; there is no second verifier or runtime.

## What is implemented

These are the mechanisms behind the results above. Each is realized in the reference implementation and has corresponding spec, test, and corpus material.

**The agent-emit / verifier-admit loop.** An LLM emits a graph; the verifier admits or rejects it with structured errors *before* execution; only admitted graphs run. Type errors, capability violations, schema-invariant breaks, and unbound references are not runtime categories — they are admission failures with machine-readable diagnostics the agent can iterate against. The dynamic-cost evaluation framework ([`evaluation/dynamic/`](evaluation/dynamic/)) measures the cost of this loop directly: tokens-per-successful-task across an agent's retry loop, not just first-emission token count.

**Mandatory effect declarations + capability-bounded execution.** Every node declares the effect categories it performs through typed edges. The verifier computes effect closures by graph traversal; programs that exercise effects beyond what the calling context grants are rejected statically. At runtime, the capability context is structured — `Network.Connect{host: "api.example.com", port: 443}` is more specific than `Network.Connect{host: *, port: *}`, and refinement matching enforces least-privilege at every call site. For the in-process builtins the declaration itself is checked: a binding whose declared effects or signature disagree with the builtin registry is rejected at admission. Bindings to code outside that namespace are trusted to declare honestly ([`ADR-005`](decisions/ADR-005-foreign-nodes.md)), which is the boundary of the guarantee until sandboxed bindings ship. See [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md).

**The verified artifact as a reasoning surface.** Verification does not just gate execution — it produces typed facts a machine consumer can query ([`ADR-010`](decisions/ADR-010-reasoning-surface.md)). A `ProgramAnalysis` over the verify result answers per-subgraph questions as data: the direct effect closure, the *latent* closure (effects reachable only through tool implementations and higher-order callbacks — the channel a naive static walk misses on exactly the agent-shaped programs that carry tools), their union as the total pre-execution reach, the capability requirement a caller must grant, the egress intersection ("can this exfiltrate"), the harm bound under a specific grant, and the capability diff between two revisions. The runtime facade exposes `analyze` as a peer of `verify` and `run`, and `runGuarded` closes the loop: a program whose total closure exceeds a declared budget is refused *before any effect*, with a structured report naming each exceeding category and the channel it was reached through. An opt-in audit log reconciles the declared closure against the effects actually performed, per run. See [`proposals/implemented/reasoning-api.md`](proposals/implemented/reasoning-api.md) and [`proposals/implemented/self-gating-execution.md`](proposals/implemented/self-gating-execution.md).

**Content-addressed program structure.** Programs are Merkle DAGs with BLAKE3 hashes computed over canonical CBOR. Two structurally-identical programs hash identically regardless of authoring path, so refactoring renames one label rather than every reference site, identical subgraphs deduplicate automatically, and programs can be admitted, denied, or attested by hash at policy boundaries. The hash is the program's identity. The encoding is a versioned compatibility contract: pre-1.0 breaking changes are batched into named epochs (currently epoch 3), every corpus program's root hash is pinned as a golden vector, and an independent Python encoder written from the specification alone reproduces all 93 of them. See [`decisions/ADR-003-content-addressing.md`](decisions/ADR-003-content-addressing.md) and [`design/canonical-encoding.md`](design/canonical-encoding.md).

**Algebraic effect handlers.** A `Handler` node intercepts every Application within its body that performs a declared effect category, replacing the call with a user-supplied function. Innermost handler wins on nesting. The handler's effect closure is computed by subtraction — wrapping a body in a handler that intercepts `Time.Now` *removes* `Time.Now` from the surrounding effect set. This makes test-time mocking, deterministic replay, and capability sandboxing first-class language constructs rather than ad-hoc library patterns. See [`proposals/implemented/effect-handlers.md`](proposals/implemented/effect-handlers.md).

**First-class state machines.** Long-running computation is modeled as event-stream actors via N-027 / N-028 / N-029 nodes. The runtime supplies a synchronous trace executor (for replay-determinism testing), an async multi-machine actor implementation (per-machine coroutine, channel-based stream wiring, select-based multi-input merge), bounded-queue overflow policies, in-band supervision via `StateMachine.Spawn` / `Terminate` effects, content-addressed snapshot and replay-from-log, and broadcast fan-out / multi-producer fan-in. Long-running services and pure computation share one algebraic foundation rather than living in separate frameworks. See [`design/state-machines.md`](design/state-machines.md) and [`proposals/implemented/state-machines-runtime-step-3.md`](proposals/implemented/state-machines-runtime-step-3.md).

**Schemas with verifier-checked invariants.** A `Schema` node attaches predicates to a value type; invariants on statically-known values are evaluated at verify time and surface as `SchemaInvariantViolation` *before* the program runs. `PositiveInt`, `NonEmptyList`, `UniqueKeyJsonObject`, and similar refined types are expressible without dependent types — the invariant body is just a `(T) -> Bool` Lambda that the verifier interprets. Values not statically known defer to runtime enforcement: the interpreter checks the obligation at the value-flow site before the value escapes, so a schema-violating dynamic value raises rather than reaching output. See [`proposals/implemented/schema-and-invariant.md`](proposals/implemented/schema-and-invariant.md) and [`proposals/implemented/runtime-schema-enforcement.md`](proposals/implemented/runtime-schema-enforcement.md).

**Layer A density text for emission cost.** Agents don't emit the verbose canonical dag-json directly; they emit a compact line-oriented text projection (Layer A density) that an always-on Elaborator compiles to canonical form, filling in inferable fields like effect closures, type arguments, and parameter types across eleven bidirectional inference cases. The projection is purely an emission convenience — the verifier and runtime only ever see canonical graphs. Static byte cost is **0.81× Python+type-hints** geomean on the three-task evaluation MVP. A second authoring surface, Layer F — a fully typed TypeScript-shaped dialect that lowers to the same canonical form — is shipping incrementally (step 1 landed); it trades byte compactness for model familiarity and is measured against Layer A through the same harness. See [`proposals/implemented/llm-authoring-layer.md`](proposals/implemented/llm-authoring-layer.md), [`proposals/implemented/layer-a-density.md`](proposals/implemented/layer-a-density.md), and [`proposals/familiar-surface-lowering.md`](proposals/familiar-surface-lowering.md).

**Embeddable runtime, durable services, and run-by-hash.** The runtime is a `StrandRuntime` facade taking a per-instance `HostPolicy`, so one host can run multiple agent-generated programs concurrently with isolated sandbox, limits, clock, and credentials — the substrate a multi-tenant host admitting untrusted programs requires. Every surface defaults default-deny: the library, the facade, and the CLI all start from a workspace-rooted filesystem sandbox, a default-deny network policy with SSRF/metadata blocklists, and a default-deny process policy; open sandboxes are an explicit opt-in. Machine groups run as long-lived services whose state survives a process restart through content-addressed snapshots, governed by per-event budgets rather than a single whole-run limit. An on-disk hash-keyed store provides admit-and-verify-once and run-by-hash, so content addressing pays off across runs and a resolved registry name dereferences to a runnable program. See [`proposals/implemented/embeddable-runtime.md`](proposals/implemented/embeddable-runtime.md), [`proposals/implemented/long-running-groups.md`](proposals/implemented/long-running-groups.md), and [`proposals/implemented/persistent-store.md`](proposals/implemented/persistent-store.md).

## What this is not

**Strand is not designed for human reading.** There is no canonical projection from graph to text. [`ADR-002`](decisions/ADR-002-no-human-projection.md) examines this decision in detail. For human inspection contexts — failure forensics, security audit, regulatory review — the design position is that analysis tooling over the graph serves better than textual rendering. The machine-facing half of that tooling is implemented (the reasoning API above, including a capability diff between two revisions, and a reverse projection to Layer A); human-facing graph queries and visualizations are not. Building a high-quality projection layer is a multi-year engineering effort that the research framing does not require.

**Strand is not a token-reduction grammar for an existing language.** Approaches like SimPy, ShortCoder, and Token Sugar modify Python's surface syntax to reduce LLM token consumption while preserving Python's semantics; these establish a useful lower bound on the benefit of AI-oriented language design. Strand's hypothesis is that the larger improvements come from changing the representation, not from compressing the existing one. The Layer A authoring projection happens to measure below conventional-language baselines on static byte cost for the three programs tested so far, but compactness is a side effect of the representational shift, not the thesis.

**Strand is not claimed to be performant in absolute terms, nor a replacement for existing languages.** Initial implementations prioritize correctness and analyzability over runtime performance. Strand is a research vehicle for testing the hypothesis in [`00-motivation.md`](00-motivation.md); its production viability depends on empirical results.

## Where Strand fits

The measured results and the shipped demonstrations point to a narrower role than "a language agents write", and a more concrete one than "a research vehicle". Every property the thesis defends attaches to the verified graph, not to the text an agent emits: admission-time verification from the received bytes, an effect closure surfaced from the artifact, hash-stable identity across stores, and handler-based virtualization of effects. Models are meanwhile more expensive and, on the evidence so far, less accurate emitting Layer A than a language they already know, and the familiar-shaped Layer F surface exists for exactly that reason. Taken together, Strand is strongest as a verified intermediate representation and admission substrate for untrusted agent output: an agent emits whatever surface it is fluent in, a lowering step produces the graph, and the graph is what a host admits, attenuates, runs, replays and audits.

Three uses follow directly from what is implemented. The first is an admission gate and capability broker for agent-generated plugins, tools and tasks: compute the closure, intersect it with a policy, attenuate the grant, run, and receive structured denials ([`demos/plugin-host/`](demos/plugin-host/README.md), [`demos/containment-host/`](demos/containment-host/README.md), [`demos/mcp-tool-manifest/`](demos/mcp-tool-manifest/README.md), [`demos/clean-room/`](demos/clean-room/README.md)). The second is correct-by-construction structured output whose invariants are checked before the value is used ([`demos/output-by-construction/`](demos/output-by-construction/README.md), [`demos/verified-llm-output/`](demos/verified-llm-output/README.md)). The third is deterministic replay and effect virtualization for agent workflows ([`demos/replay-timetravel/`](demos/replay-timetravel/README.md), [`demos/llm-virtualization/`](demos/llm-virtualization/README.md)); replay currently records inputs only, so this is a foundation rather than a finished feature.

In conventional systems Strand is not an application language and is not proposed as one. Its realistic touchpoints are a compilation target for narrowly-scoped agent-generated code inside an otherwise conventional service, a machine-checked manifest format for tools whose capability claims must be verified rather than read, and a delegation boundary at which an existing system hands bounded work to an agent. Effect-driven placement, per-node encryption and trusted-execution integration remain long-horizon claims without implementation; see [`02-core-thesis.md`](02-core-thesis.md) § outcome-priority and [`ROADMAP.md`](ROADMAP.md) Tier 4. The residual trust assumptions of the current implementation, chiefly unisolated in-process builtins and declaration-trusted foreign bindings, are enumerated in [`security-index.md`](security-index.md).

## Status

The design corpus is substantially complete: ten architectural decision records (ADR-001 through ADR-010) and eight design specifications covering node algebra, canonical encoding, effects and capabilities, state machines, encryption, security, distribution, and rendering. The full document tree and identifier registry are in [`INDEX.md`](INDEX.md).

The reference implementation lives under [`impl-kotlin/`](impl-kotlin/). It runs on the JVM as bytecode; a Rust port of the bytecode VM is planned for Milestone 2.3 per [`ADR-008`](decisions/ADR-008-compilation-target.md) and will not change the source-level language. Currently shipped:

| Layer | Scope | Status |
|-------|-------|--------|
| 1 | Pure computation core — literals, types, lambda calculus, System F polymorphism, NodeRef | Complete |
| 2 | Content addressing — BLAKE3 over canonical CBOR, NodeRef-by-hash | Complete |
| 3 | Effects and capabilities — refinement-lattice matching, no-continuation effect handlers | Complete |
| 4 | Foreign function interface — in-process builtins (real filesystem, sockets, HTTP, process, time, hashing, math, string, bytes, regex, logging, OS state, exit); sandboxed bindings deferred to Milestone 2.4 | Step 2 |
| 5 | Match patterns, fixpoint recursion, product and sum values, recursive types | Complete |
| 6 | State machines — sync trace runtime, async multi-machine actors, backpressure, supervision, snapshots, broadcast streams | Complete |
| 7 | Schema with verifier-checkable invariants and runtime enforcement on dynamic values; JSON (flat + nested-array/object), plain-text, and Markdown blessed libraries | Step 2 (HTML5/SVG/PDF libraries pending) |

A bytecode VM under [`impl-kotlin/bytecode/`](impl-kotlin/bytecode/) and [`impl-kotlin/vm/`](impl-kotlin/vm/) holds interpreter-equivalence across the 93-program corpus, including capability-denial parity under refined grants: the value-path equivalence net auto-enumerates every corpus program (each exclusion carries a documented reason), and state-machine, async-actor, and schema programs are covered by their own equivalence suites. One divergence is recorded and open: the VM does not yet apply the interpreter's rule that a parameterized effect called without an effect instance requires an unrefined grant. A four-layer LLM authoring stack under [`impl-kotlin/authoring/`](impl-kotlin/authoring/) — compact text projection, grammar-constrained decoding, bidirectional elaboration, and the canonical verifier — closes the gap between agent-friendly emission and the on-disk graph form. The implicit prelude is a content-addressed module of 284 reserved nodes — primitive types, 129 builtin entries, effect categories — resolvable by short name so agent emissions skip 2-3 nodes per stdlib reference.

The test suite stands at 2,678 tests as of 2026-09-29, alongside a 93-program positive corpus with pinned hashes and the 47-program negative corpus. The evaluation framework under [`evaluation/`](evaluation/) holds the static-cost measurement, the dynamic harness that drives a model through the verifier-feedback loop, the containment probes, and the independent conformance encoder; its results are summarized under Results to date above.

Thirteen executable demonstrations under [`demos/`](demos/README.md) put the shipped guarantees on screen — containment and clean-room no-exfiltration proofs, capability attenuation and the confused-deputy defense, deterministic replay and restart-resume, tool-manifest verification, prompt-injection containment, rogue-agent isolation in a supervised group, and the end-to-end agent-platform capstone that walks one untrusted agent-generated task through admit, run, verify, withstand, and audit.

The four-phase research plan is documented in [`research-plan.md`](research-plan.md) and the prioritized remaining work in [`ROADMAP.md`](ROADMAP.md). The current work is the measurement the lead claims still lack: the API-backed multi-sample sweep with real tokenizer counts and prompt caching, the remaining conventional baselines, the Layer F comparison against Layer A, and the strengthened containment matrix against sandboxed and capability-checked baselines. Each is an exit criterion in either direction; a result against Strand is recorded as such.

## Inspiration and prior art

Strand draws from several research traditions and identifies where it diverges from each. The full survey is in [`01-prior-art.md`](01-prior-art.md); the principal influences are summarized below.

**Content-addressed code.** Unison is the closest existing system and the primary inspiration for Strand's content-addressing decision. The major divergences are that Unison preserves a human-readable surface syntax, requiring substantial engineering for the projection layer, whereas Strand does not; and that Unison's abilities are a compile-time type discipline erased before execution, whereas Strand's effect declarations are edges of the stored artifact that the runtime consumes as capability requirements and placement constraints.

**Structured editing.** Hazel demonstrates that direct AST manipulation can replace text editing without loss of expressiveness, with the property that every program is always well-formed. Strand extends this principle from "humans manipulating ASTs" to "agents manipulating graphs," and uses content-addressing where Hazel uses traditional name binding.

**LLM-oriented languages.** Pel is a Lisp-inspired surface for LLM agent orchestration. QUASAR has LLMs generate a Python subset that is then transpiled to a separate execution language designed for parallelism and security. CoRE treats natural language as the program and uses an LLM as the interpreter. These projects share Strand's framing that programming languages can be designed for AI agents rather than adapted for them. Strand differs by abandoning text representation entirely and targeting general-purpose computation rather than orchestration.

**Effect-typed languages.** Koka, Eff, OCaml 5's effect handlers, and Haskell's IO type establish the technical feasibility of static effect tracking and demonstrate its benefits for reasoning about program behavior. Koka, Unison and Flix already track effects for every function with no untracked-IO category, so mandatoriness is not what distinguishes Strand. The difference is where the effect information lives and what it is for: in those languages it is discharged by the type checker and erased, while in Strand it is an edge of the stored artifact that the verifier recomputes at admission and the runtime consumes for placement, capability checks and partitioning.

**Artifact-level verification.** Proof-carrying code and the JVM bytecode verifier established that a consumer can check safety properties of an untrusted artifact at load time without trusting its producer, and the WebAssembly component model makes a module's imports typed declarations that the host validates before instantiation. Strand belongs to this tradition rather than claiming to originate it. What it adds is the effect closure as a checked property of a content-addressed artifact: the consumer recomputes which effect categories the graph can reach, from the bytes it will execute, and the artifact's identity is stable across every store that holds it.

**Capability-based systems.** E and Pony are programming languages built around object capabilities; seL4 is a formally verified microkernel built on capability-based access control. The capability tradition establishes the security properties Strand aims for. Strand's contribution is integrating capabilities with effect declarations: a capability is the runtime token corresponding to a static effect, which allows the runtime to refuse to evaluate a graph whose effect set exceeds the capabilities held by its execution context.

**Distributed dataflow systems.** Spark, Ray, TensorFlow's graph mode, and Differential Dataflow demonstrate that graph representation is the right shape for distribution. They construct graphs as a secondary representation built from host-language code; Strand makes graph representation primary. This eliminates the impedance mismatch between programmer code and the dataflow graph, but requires the language to handle workloads dataflow systems do not (state machines, long-running services, interactive systems). State machines as graph fixpoints over event streams are how Strand addresses this.

**Token-reduction grammars.** SimPy, ShortCoder, and Token Sugar modify Python's surface syntax to reduce LLM token consumption while preserving Python's semantics, demonstrating that even purely syntactic modifications produce measurable improvements (10–35% token reductions on equivalent tasks). These establish a useful lower bound on the benefit of AI-oriented design. Strand's hypothesis is that abandoning text representation entirely produces substantially larger improvements on the metrics that matter, but this hypothesis must be tested against these baselines rather than against unmodified text languages.

The combination of graph-native source representation, content-addressed node identity, mandatory effect declarations, effect-driven placement, capability-based execution tied to static effects, first-class state machines as fixpoints over event streams, and being designed for AI generation rather than human authorship is, to the project's knowledge, novel as an integrated whole. Individual elements have precedents in the systems described above; the research contribution is the integration and the empirical question of whether it composes into a language that performs better than text languages for AI generation.

Design documents use several conventions to remain navigable. Stable identifiers never change once assigned (ADR-NNN, N-NNN, E-NNN, Q-NNN). Major sections carry explicit anchors (`{#anchor-name}`) for cross-document linking. Each document ends with a References section listing outgoing and incoming citations, maintained in both directions. The master index at [`INDEX.md`](INDEX.md) provides three views of the corpus: an alphabetical concept index, a document tree, and the identifier registry. Unresolved questions live in [`open-questions.md`](open-questions.md) with Q-NNN identifiers and are referenced by id from spec documents, rather than carried as inline caveats.

## Voice and authority

Design documents are written in neutral specification voice — they describe the design as it currently stands, not the process by which it was reached. The design is provisional in the sense that implementation work continues to surface issues; revisions are recorded in each document's history. These conventions apply to documents in the design corpus (the root, `decisions/`, `design/`). They do not apply to implementation code under `impl-kotlin/`, which follows the host language's idioms.
