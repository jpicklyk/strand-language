# Secure by default

**Document:** `proposals/implemented/secure-by-default.md`
**Status:** Implemented 2026-07-05
**Question:** Q-075 (registers)
**Related:** Q-041 (`implemented/io-builtin-sandboxing.md`), Q-054 (`implemented/embeddable-runtime.md`), ADR-004
**Drafted:** 2026-07-05

## Problem

`Builtins.sandboxPolicy` is the process-global singleton `HostContext.processDefault()` reads when no explicit `HostPolicy` is supplied — the library-level default every embedder and every direct `Interpreter` / `Vm` construction inherits. Since Q-041 landed the I/O sandbox, that singleton has defaulted to `SandboxPolicy.OPEN_DEFAULT`: no workspace constraint, no network default-deny. The CLI alone installed `SandboxPolicy.SECURE_DEFAULT` at startup by building its own policy from parsed flags.

The inversion was deliberate and recorded at the time: Q-041 landed against an 895-test baseline whose `BuiltinsIoTest` and similar cases wrote to `@TempDir` paths and opened loopback sockets with no sandbox awareness at all. Flipping the singleton default to secure would have broken that baseline outright, so the singleton shipped open and the CLI alone shipped secure, with a KDoc comment recording the inversion as temporary.

That justification has expired. The pre-Q-041 baseline it protected is long gone — the test suite has since grown sandbox-awareness in the places that need it, and the tests that still exercise real IO can install the open policy explicitly rather than lean on an ambient default. ADR-004 requires mandatory typed effect edges precisely so a graph's full effect set is statically computable and every effectful call passes through a checked boundary; the sandbox is where that boundary becomes an actual containment guarantee rather than a bookkeeping exercise. A library whose main untrusted-agent-facing capability boundary defaults to no containment is backwards for a language built on that premise. Every embedder that constructs a `HostContext` or an `Interpreter` without an explicit `HostPolicy` — which is every call site the CLI does not control — got the open surface by default. An embedder who forgot to pass `HostPolicy.SECURE` got unrestricted filesystem and network access with no warning.

## Recommended approach

Flip the default. `Builtins.sandboxPolicy`'s initializer, and every test-reset path that restores it, now target `SandboxPolicy.SECURE_DEFAULT`. The library default and the CLI default agree: both are secure-by-default. `SandboxPolicy.OPEN_DEFAULT` remains exactly as capable as before — workspace-unrooted filesystem, network default-allow — but it is now an explicit opt-in a caller reaches for, not a value that arrives unasked.

A single source of truth backs the initializer and every reset path: `Builtins.DEFAULT_SANDBOX_POLICY`, a `val` (not the mutable `@Volatile var sandboxPolicy`) equal to `SandboxPolicy.SECURE_DEFAULT`. The singleton's initializer reads it; every test class that mutates the singleton in `@BeforeEach` and must restore it in `@AfterEach` reads it too, rather than repeating the literal `SandboxPolicy.SECURE_DEFAULT` at each site. A regression that changed the constant would be caught by a dedicated test asserting `DEFAULT_SANDBOX_POLICY == SandboxPolicy.SECURE_DEFAULT`, independent of whatever value other tests have mutated the mutable singleton to at the moment the assertion runs.

No change to `FsPolicy`, `NetPolicy`, or `SandboxPolicy`'s own constructor defaults — those already default secure-leaning (`NetPolicy(defaultDeny = true, ...)` is the class's own default; `SandboxPolicy.SECURE_DEFAULT` was always the stricter of the two named constants). The change is narrowly the singleton's *initial value* and the KDoc that described the inversion as intentional.

## Where it lives

`impl-kotlin/interpreter/src/main/kotlin/org/strand/interpreter/Builtins.kt` — the `sandboxPolicy` `@Volatile` field and the new `DEFAULT_SANDBOX_POLICY` constant beside it. `impl-kotlin/interpreter/src/main/kotlin/org/strand/interpreter/SandboxPolicy.kt` — the `OPEN_DEFAULT` / `SECURE_DEFAULT` KDoc, rewritten to describe the current state rather than the retired inversion. `impl-kotlin/interpreter/src/main/kotlin/org/strand/interpreter/HostPolicy.kt` — the `OPEN` / `SECURE` companion KDoc, same treatment. Every test class across `:interpreter`, `:corpus`, and `:runtime` that constructs a real filesystem or network scenario and previously rode the ambient default.

## Scope

Small. One field initializer, one new named constant, a KDoc truth pass across three files, and an explicit-opt-in pass across the handful of test classes that genuinely need the open surface. No new node category, no verifier change, no canonical-encoding change, no `HostPolicy` shape change — `HostPolicy.OPEN` and `HostPolicy.SECURE` are unchanged as values; only which one a caller falls into by omission moves.

## Implementation note

**The flip.** `Builtins.sandboxPolicy: SandboxPolicy = SandboxPolicy.OPEN_DEFAULT` becomes `Builtins.sandboxPolicy: SandboxPolicy = DEFAULT_SANDBOX_POLICY`, where `val DEFAULT_SANDBOX_POLICY: SandboxPolicy = SandboxPolicy.SECURE_DEFAULT` is a new named constant immediately above it. A repo-wide grep for `OPEN_DEFAULT` at the start of this work turned up 8 files touching the singleton or its KDoc in this snapshot of the tree (fewer than a typical later snapshot, since this codebase predates several since-landed features — there is no `ProcessPolicy`/`ProcessSandbox` here, and no Q-055 audit-sink field on `HostContext`): `Builtins.kt`, `HostPolicy.kt`, `SandboxPolicy.kt` (production); `SandboxPolicyTest.kt`, `HostPolicyTest.kt`, `AttemptTest.kt`, `CorpusSandboxTest.kt` (interpreter/corpus tests); `BridgedStreamTest.kt` (runtime test). Every production reference was audited; none silently depended on the old default surviving — `HostPolicy.OPEN` pins `SandboxPolicy.OPEN_DEFAULT` explicitly regardless of the singleton, and the CLI's `parseLimits` builds its own `SandboxPolicy` from flags (defaulting to `SandboxPolicy.SECURE_DEFAULT.fs` / `.net` when no flag relaxes it) rather than reading the singleton at all, so `cli/Main.kt`'s behavior is unchanged by the flip — it never depended on the singleton's default in the first place.

**KDoc truth pass.** `SandboxPolicy.OPEN_DEFAULT`'s KDoc no longer describes itself as "the singleton default" with a "deliberate inversion" paragraph; it now describes itself as an explicit opt-in policy, records that the inversion existed and why it was removed, and points at this document. `SandboxPolicy.SECURE_DEFAULT`'s KDoc drops "the policy the CLI installs by default" in favor of "the policy both the library and the CLI install by default." `NetPolicy.defaultDeny`'s KDoc no longer calls `OPEN_DEFAULT` "the test default" — it is "an explicit opt-out policy, installed by a test or embedder that needs it." `NetSandbox.checkConnect`'s internal comment about the `defaultDeny = false` "test policy" is retitled "opt-out policy." `HostPolicy.OPEN`'s KDoc no longer claims to mirror "the current `Builtins` singleton defaults" (it no longer does, on the sandbox field) — it now states plainly that it pins `OPEN_DEFAULT` regardless of the library default, as an explicit choice. `HostPolicy.SECURE`'s KDoc gains the note that it is now also the actual library/CLI default, not merely "the agent-facing surface." This snapshot of the tree has no `ProcessSandbox`/`ProcessPolicy` and no `HostContext` Q-055 audit-sink field, so those two KDoc updates named in the originating brief (written against a later snapshot) do not apply here; every KDoc site that does exist in this tree was updated.

**Test sweep.** The flip surfaced exactly one test failure on the first full run: `CorpusProjectionTest`'s corpus-70 scenario writes to the absolute path `/safe`, which the new secure default correctly rejects as a workspace escape (`FsPathEscape`) — the test's actual subject is the Q-039 projection/capability mechanism, not the sandbox, so it was not testing what it claimed to test once the ambient default stopped being permissive. Five test classes across the whole repository needed an explicit sandbox opt-in, four of them load-bearing (confirmed by the failing-then-passing test run) and one precautionary:

- `interpreter/BuiltinsIoTest.kt` — direct `Builtins.lookup` dispatch of `Fs.*` against `@TempDir` paths, loopback `Net.Connect`/`Http.RequestFromUrl`, and `Process.Spawn`, with no sandbox setup at all before this change. Installs `SandboxPolicy.OPEN_DEFAULT` in `@BeforeEach`, restores `Builtins.DEFAULT_SANDBOX_POLICY` in `@AfterEach`.
- `interpreter/StreamingReceiveTest.kt` — one scenario (`Net_Stream_Receive` Option-EOF) opens a real loopback socket; the class's existing `@BeforeEach`/`@AfterEach` gained the same install/restore pair alongside its existing credential-provider and clock save/restore.
- `corpus/PreludeProjectionInterpreterTest.kt` — five of its `fsRead`/`fsWrite`/`fsExists`/`fsAppend`/`fsDelete` scenarios run real IO against `@TempDir`, again with no prior setup.
- `corpus/CorpusProjectionTest.kt` — the corpus-70 failure above; fixed with the same `@BeforeEach`/`@AfterEach` pair.
- `interpreter/AttemptTest.kt` — precautionary, not load-bearing. Its own KDoc claimed dependence on the ambient open default for a relative, not-yet-existing path (`Fs.Read` of `strand-nonexistent-dir-xyz/missing.json`); an empirical check (running the pre-fix test body against the post-flip `Builtins.kt`) showed both scenarios already pass under `SECURE_DEFAULT` unmodified, because `FsSandbox.resolve`'s `NoSuchFileException` fallback lexically normalizes a missing relative leaf and finds it within the workspace root (the JVM's working directory) — no escape, so an ordinary `IoFailure`, not a `SandboxViolation`, either way. The explicit opt-in was installed anyway, both because the class's own documentation asserted the dependency and to make the test robust against a future change to `FsSandbox`'s fallback behavior that could make the dependency real.

Four already-sandbox-aware test classes (`SandboxPolicyTest`, `HostPolicyTest`, `CorpusSandboxTest`, `BridgedStreamTest`) needed only their `@AfterEach`/`@BeforeEach` reset value changed from the literal `SandboxPolicy.OPEN_DEFAULT` to `Builtins.DEFAULT_SANDBOX_POLICY`, since they already installed explicit policies per test; `HostPolicyTest` needed no change at all, since its assertions pin `HostPolicy.OPEN.sandbox` to `SandboxPolicy.OPEN_DEFAULT` directly rather than reading the singleton. `CorpusMutationFuzzTest` (`:corpus`) was already self-contained with its own scoped `SandboxPolicy.SECURE_DEFAULT.copy(fs = FsPolicy(workspaceRoot = <fuzz temp dir>, ...))` installed in `@BeforeAll` and restored in `@AfterAll`, and needed no change.

Confirmed as needing no fix, checked directly rather than assumed: `BuiltinsHttpServerTest` (server-side `Http.Listen`/`Accept`/`Respond`/`ServerClose` never call `NetSandbox` or `FsSandbox` — a listening socket is not gated the same way as an outbound connect); `CorpusTest`'s generic sweep over corpus 86/87 (the same relative-missing-path non-issue as `AttemptTest`); the CLI-integration tests `CliFederationTest`/`CliPreludeResidencyTest`/`CliStoreTest` (registry- and store-hash lookups, no `Fs.*`/`Net.*` builtin dispatch); `ProgramEvaluationContextTest` and `PersistentStoreTest` (construct explicit `SandboxPolicy`/`HostPolicy` values, or exercise the on-disk program-store JSON format rather than any IO builtin); and the `:runtime` module's demo-driver tests (`AgentPlatformDemoTest`, `CleanRoomDemoTest`, `ContainmentDemoTest`, `PluginHostDemoTest`, `ReplayDemoTest`, `SkillWorkflowDemoTest`), all of which drive scenarios through an explicit `StrandRuntime(HostPolicy.OPEN / HostPolicy.OPEN.copy(...))`, fully decoupled from the `Builtins.sandboxPolicy` ambient singleton the Q-054 facade no longer reads. `authoring`, `bytecode`, `core`, `hashing` (beyond the one `@TempDir`-using store-format test above), `schema`, and `vm` have no test that exercises a live sandbox-gated builtin at all.

**Pinning the default.** `SandboxPolicyTest` gained one regression-guard test: `Builtins DEFAULT_SANDBOX_POLICY is SECURE_DEFAULT`, asserting `Builtins.DEFAULT_SANDBOX_POLICY == SandboxPolicy.SECURE_DEFAULT` and `!= SandboxPolicy.OPEN_DEFAULT`. It asserts the named constant rather than the live `sandboxPolicy` field precisely so that another test's mutation of the mutable singleton (however it is ordered relative to this one under JUnit's unspecified method ordering) cannot make this assertion pass or fail spuriously — a future regression that changed `DEFAULT_SANDBOX_POLICY` itself back toward the open policy is what this test is built to catch.

**Test totals.** `.\gradlew.bat test --rerun-tasks --no-build-cache` from `impl-kotlin/`: **2384 tests, 0 failures, 3 skipped**, across all ten modules (authoring 608, cli 21, core 31, corpus 761, hashing 121, interpreter 516, runtime 154, schema 7, verifier 147, vm 18). `CorpusGoldenHashTest` alone: 117 tests, 1 skipped (the pre-existing Windows symlink fixture), 0 failures — unchanged from its pre-Q-075 baseline, as expected: this proposal touches no node encoding, no canonical CBOR, no hash. Zero golden-hash impact.

**Deviations.** None from the brief's substance. Two brief items did not apply to this snapshot of the tree and were confirmed absent rather than silently skipped: this worktree has no `ProcessPolicy`/`ProcessSandbox` (a later feature not yet present here), so there was no `ProcessSandbox` comment calling `OPEN_DEFAULT` "the library default" to rewrite; and `HostContext` here has no Q-055 audit-sink field, so there was nothing to check there either. The five-test-class opt-in count (four load-bearing, one precautionary) came from an exhaustive sweep of every Gradle module's test source set, cross-verified independently by a parallel research agent against the actual git commits and one empirical test run — the one correction that sweep produced (that `AttemptTest`'s fix is precautionary, not load-bearing, contrary to what its own pre-existing doc comment implied) is recorded accurately above rather than overclaimed.

The Q-041 proposal's deviation (1) paragraph is updated in the same pass with a short dated note recording that this inversion was removed under Q-075.
