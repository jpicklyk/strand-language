- 2026-06-13 (Q-058 persistent local store and run-by-hash moved Open → Proposed with a committed design in [`proposals/implemented/persistent-store.md`](proposals/implemented/persistent-store.md). Closes the gap that the content-addressed store is an in-memory map per CLI invocation — every run re-ingests, re-hashes, and re-verifies, nothing survives process exit, and `strand registry resolve` returns a hash nothing can dereference without a hand-passed `--peer-store`. The design defines an on-disk, hash-keyed store directory with a `store.json` recording `storeFormatVersion` and `encodingEpoch` (= `CanonicalEncoding.EPOCH`); a reader compiled against a later epoch (or a higher format version) **fails closed** on the mismatch rather than misreading bytes that would re-hash differently — the point at which Q-024's migration story becomes load-bearing. Hashable nodes are persisted one file per node keyed by full multihash hex (sharded by the leading prefix byte), bound nodes (`ParameterDecl`/`TypeParameter`/`RecursiveSelf`) inlined into their owning node's file, so two programs sharing a subgraph store the shared nodes once (dedup). Admit-and-verify-once: the first ingest verifies and records the verdict (Ok with `rootType`/`nodeTypes`/warnings, or the structured failure) keyed by root hash; a subsequent run/verify of the same root hash reuses the recorded verdict and skips re-ingest and re-verification — admit-once means verify ran once and was recorded, never that verification is skipped on first admission. Integrity is fail-closed at two layers: a per-node re-hash on read and the existing Q-043 Merkle root re-hash on admission — a corrupted entry is rejected, never trusted. The store composes with Q-043 rather than duplicating it: reading is exposed as a `DiskStoreResolver : NodeResolver` that slots into the existing `ChainedResolver`, so every backend that already threads `resolveTarget` dereferences the local store with no new threading, and admission reuses `FederatedProgram.fetchAndAdmit` unchanged. Run-by-hash on the Q-054 facade builds a `ProgramImage` from a root hash by reading the store; the CLI gains `--store <dir>` (with a `STRAND_STORE` env default) and accepts a root hash or registry name in place of a file path on `run`/`verify`/`machine`/`group`, plus a `strand store ingest` subcommand, with the existing file-path invocation unchanged. Registry integration closes the half-a-mechanism gap: a name resolved via `strand registry resolve` dereferences against the local store, so the resolved hash is runnable without `--peer-store` — the registry stays the off-graph name layer, the store is the on-disk content layer, the `DiskStoreResolver` is the bridge. No node category, no canonical-encoding change, no new verifier rule — the store consumes the existing hashing/verifier/federation machinery. Local single-machine scope only; GC/compaction, networked resolvers, cross-store dedup, and a structured `TypeExpr` verdict codec (fallback: re-verify the admitted local store, still skipping re-ingest/re-hash) are deferred. Status: Proposed.)

## Purpose

This document tracks unresolved design questions and known gaps in the Strand specification. Specification documents describe the current design without inline caveats about uncertainty; questions about the design live here. Each question references the specific documents and sections it concerns.

Questions are organized by topic and assigned stable identifiers (`Q-001`, `Q-002`, etc.) that do not change once assigned. When a question is resolved, its entry is updated with the resolution and a reference to the document where the resolution is recorded; the entry is not removed.

## Status legend

- **Open** — no proposed resolution
- **Proposed** — a resolution has been suggested but not adopted
- **Resolved** — resolution adopted; entry retained for historical reference
- **Deferred** — out of scope for current research phase

## Node algebra {#questions-node-algebra}

### Q-001: Exact node type inventory {#Q-001}

**Status:** Proposed
**Concerns:** [`design/node-algebra.md`](design/node-algebra.md)
**Resolution:** Inventory of 31 node types (N-001 through N-031) across eight categories (literals, types, functions and binding, references, effects and capabilities, control flow, state machines, metadata), with edge schemas and well-formedness rules, proposed in [`design/node-algebra.md`](design/node-algebra.md). Validation depends on implementation; the inventory is open to extension under the versioning rules.

The core thesis and supporting documents reference node types (Function, Application, Lambda, TypeDef, ForeignNode, StateMachine, EventStream, etc.) without formalizing the complete inventory. The exact set of node types, their edge schemas, and their well-formedness rules has not been specified. A formal node algebra is required before implementation can begin.

**Estimated complexity:** Moderate. Drawing from typed lambda calculus with row-polymorphic effects, the core node set is likely 15–25 types. The work is in specifying edge schemas and well-formedness rules precisely.

### Q-002: Treatment of hierarchical and nested state machines {#Q-002}

**Status:** Proposed
**Concerns:** [`design/state-machines.md`](design/state-machines.md)
**Resolution:** Compositional flat machines, as proposed in [`design/state-machines.md`](design/state-machines.md). Hierarchical patterns are implemented by parent machines that delegate to child machines based on their state. A future `HierarchicalStateMachine` syntactic-sugar node category may be added later without changing the underlying algebra.

Real-world state machines are often hierarchical (e.g., Harel statecharts). The current design treats state machines as single transition functions over flat state. How nested machines, parallel regions, and history states map to the node algebra has not been determined. Options include (1) representing hierarchy through composition of independent StateMachine nodes, (2) introducing dedicated node types for hierarchical state, (3) adopting a statechart-derived formalism wholesale.

### Q-049: Structural subtyping adoption {#Q-049}

**Status:** Open
**Concerns:** [`design/node-algebra.md`](design/node-algebra.md) § Types, verifier (Kotlin/JVM reference implementation)

`design/node-algebra.md` § Types previously asserted that the full structural subtyping algorithm — width subtyping on products, contravariant argument and covariant result positions on functions, effect-set inclusion on the arrow — "is part of the reference implementation." It is not and never was: the verifier decides type compatibility by strict structural equality, with a single relaxation at SchemaType boundaries, and `TypeParameter.bound` is parsed but unenforced. The specification was corrected 2026-06-10 to describe the implemented discipline; this question tracks the unresolved decision the divergence exposed.

The sharpest practical friction is effect-exact function-type equality at higher-order positions: a pure function cannot flow into a callback parameter declared with an effect row, although that direction is always safe; and absent width subtyping, agents must thread structurally identical type nodes everywhere, so extending a record or widening an effect row forces wholesale re-declaration. A silently-ignored `bound` field is worse than rejection — an agent writing bounded polymorphism receives no checking and no error. Candidate resolutions: adopt effect-set inclusion alone (smallest change, removes most of the friction); adopt the full structural subtyping originally specified; or retain strict equality and remove the `bound` field from the schema. Subtyping is a verifier compatibility relation, not an encoding change — hashes are unaffected under any option — but the choice interacts with Layer C elaboration, which infers types that must then be compatible at exactly these sites.

### Q-050: Verifier silent passes — Match exhaustiveness and unreachable nodes {#Q-050}

**Status:** Resolved (implemented 2026-06-10 in the Kotlin/JVM reference implementation)
**Concerns:** [`design/node-algebra.md`](design/node-algebra.md) § well-formedness, verifier, [Q-021](#Q-021) (first-pass correctness — these are the agent-mistake classes the verifier claimed to catch)
**Resolution:** Two checks close the gaps. (1) **Match exhaustiveness is a hard verify error.** `VerifyError.NonExhaustiveMatch(at, scrutineeType, missingCases)` fires when a Match has no top-level catch-all (wildcard or variable pattern) and does not cover its scrutinee: a Sum scrutinee (including a RecursiveType unfolding to a Sum, mirroring the constructor-pattern unfold) requires a top-level constructor pattern per case; a Bool scrutinee requires both literals; any other scrutinee with only literal patterns requires a catch-all. Nested-payload coverage analysis is deliberately out of scope and documented on the error. The rule landed with zero violations across the corpus, the Layer A fixtures, and the test suite; the IF and WHEN sugars are exhaustive by construction. (2) **Unreachable-node diagnostics.** A store-wide informational pass populates a new `VerifyResult.Ok.warnings: List<VerifyWarning>` channel (parallel to `deferredChecks`) with `UnreachableNode` entries for nodes unreachable from the root set: the program root, every ModuleManifest (plus export targets resolved through `hashToNodeId` and declaredEffects), every StateMachine (the `group` CLI drives all machines in the store), and every EffectCategory (categories are host-side grant targets — corpus 13's `netFx` exists solely for `--grant-all`). Edges walk `translateNodeIds` rather than `childNodeIds`, which omits binder declarations and the `Invariant.targetSchema` / `EffectProjection.category` metadata edges and would false-positive. The CLI prints `warning:` lines on the verify and run paths; verification never fails on a warning. The sweep immediately caught real corpus bugs: fifteen unwired nodes across thirteen curated programs (removed; root hashes unaffected since unreachable nodes never feed the root hash) and corpus 68's orphaned `upsertCall` — half of its stated upsert-plus-query demonstration had never been verified — now wired through a new Let root (a deliberate root-hash change, with the golden vectors regenerated). `CorpusWarningSweepTest` keeps the corpus warning-clean.

Previously a Match with a missing case verified cleanly and died at runtime with `NoMatchingCase`, and a node an author declared but never wired into the root expression was never type-checked at all — both verified-but-wrong shapes that corrupt the meaning of "verified," the only success signal an agent has. Identified by the 2026-06-10 independent review. Recorded follow-ups under this identifier: nested-payload exhaustiveness analysis; warning output on the `machine`/`group`/`author` CLI paths; and the store-wide machine-verification gap the sweep exposed — `strand group` executes every StateMachine in the store while the verifier type-checks only the root-reachable graph, so a non-root-reachable machine currently runs unverified, and closing that means store-wide machine inference mirroring `checkManifests`.

### Q-053: Nested recursive types at value-construction sites {#Q-053}

**Status:** Resolved
**Concerns:** [`design/node-algebra.md`](design/node-algebra.md) § Recursive types (N-041, N-042), [`proposals/implemented/nested-recursive-types.md`](proposals/implemented/nested-recursive-types.md), [`design/canonical-encoding.md`](design/canonical-encoding.md) § Types (tag 48), [`proposals/implemented/nested-recursive-self-depth.md`](proposals/implemented/nested-recursive-self-depth.md), [`proposals/implemented/encoding-epochs.md`](proposals/implemented/encoding-epochs.md), Q-026, Q-029, Q-047, Q-062
**Resolution:** A new node category **N-048 RecursiveProjection**, implemented in the Kotlin/JVM reference implementation ([`proposals/implemented/nested-recursive-types.md`](proposals/implemented/nested-recursive-types.md)). A value-construction `ofType` (or `paramType`, field type, pattern type) targeting a nested-recursive component points at a `RecursiveProjection(recursiveType: the whole outer μ, path: an ordered list of Case/Field/Unfold selector steps)` rather than at the bare open inner μ; the verifier resolves it by entering the outer μ's binder context (via one-step unfolds along the path) so an inner `RecursiveSelf(depth=N)` is already bound by the time resolution reaches it. The N-042 depth field is unchanged (it remains the in-type back-edge); RecursiveProjection is the closed front-door that makes a depth-bearing inner type reachable from a construction site, recovering the precision the corpus-66 splice loses (a malformed array spine becomes a verify-time `ProductFieldValueTypeMismatch`). **Tag 48 landed additively under epoch 1**, not as part of epoch 2: it is a fresh category tag, so no existing program hash moved (`CanonicalEncoding.EPOCH` stays 1; the goldens gained only the four new programs). The proposal framed tag 48 as riding the epoch-2 regeneration; implementation decoupled it, since the N-048 portion needs no epoch bump. The chartered epoch-2 normalization (gated optional fields to a uniform presence-prefix rule), the epoch bump, and the Q-049 `bound` decision remain the separate epoch-2 charter. Verifier-inferred outer context (no new node) is rejected — the inner μ has no canonical standalone meaning, so inference breaks content-addressing's one-canonical-interpretation rule; blessing the splice as the documented lowering is rejected — it permanently relocates a type-system guarantee into runtime schema checks. Polymorphic recursive types and higher-arity μ binders remain deferred. Unblocks the HTML5 and SVG blessed libraries (Q-026, Q-047).

Q-026's resolution explicitly flags this as "a separate Q-NNN-worthy open question"; this entry is that registration. The original candidate directions considered: a richer recursive-binder protocol that lets a construction site supply the enclosing binder context (adopted, as the closed RecursiveProjection front-door); higher-arity μ binders (also named as a possible extension under Q-029; deferred); or blessing the splice transform as the documented lowering, with authoring-layer tooling that generates it and recovers the lost precision through schema invariants (rejected as the canonical model).

## Effects and capabilities {#questions-effects}

### Q-003: Effect category granularity {#Q-003}

**Status:** Proposed
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md)
**Resolution:** 31 effect categories (E-001 through E-031) across eight groups (Network, Filesystem, Time, Process, Memory, Hardware, Crypto, Trust, StateMachine), with parameterization through structured fields and a refinement lattice for capability matching, proposed in [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md).

Effect categories must be granular enough to be useful for security policies (`Network.Connect{host=X, port=Y}` rather than `Network`) but coarse enough to be tractable for the verifier and for human reasoning about policies. The exact categorization scheme, including how parameterized effects are represented in the type system, has not been specified.

### Q-004: Capability delegation semantics {#Q-004}

**Status:** Proposed
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md)
**Resolution:** Hybrid discipline. Capabilities flow implicitly through in-graph calls (ambient within a trust domain). A `CapabilityScope` node narrows capabilities at trust boundaries. Foreign and encrypted-node boundaries require explicit re-grant. Proposed in [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md).

When a node holding capability C invokes another node that requires C, must C be explicitly passed as an argument (strict capability discipline) or does the runtime forward C implicitly (ambient within the scope)? Strict discipline is more secure but requires every effectful function to receive capabilities as arguments, adding boilerplate. Implicit forwarding is easier but reintroduces ambient authority that capability systems aim to eliminate.

### Q-005: Confused deputy mitigation {#Q-005}

**Status:** Proposed
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md), [`design/security-model.md`](design/security-model.md)
**Resolution:** Three-layer mitigation: parameter-tagged capabilities (the primary defense), capability minimization at scope entry via CapabilityScope, and optional argument-provenance checks. Proposed in [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md) and synthesized in [`design/security-model.md`](design/security-model.md). The language makes careful authority design expressible; it does not enforce its use.

When a privileged subgraph accepts arguments from a less-privileged caller, the caller can potentially manipulate the privileged graph into performing operations on its behalf — the classic confused deputy attack. The graph design makes capability passing explicit, which reduces ambient authority, but does not automatically prevent confused deputy attacks. The mitigation strategy has not been specified.

### Q-055: Effect-audit log of declared versus performed effects {#Q-055}

**Status:** Open
**Concerns:** [`design/security-model.md`](design/security-model.md) § monitoring, [Q-044](#Q-044) (containment measurement), interpreter foreign-dispatch boundary (Kotlin/JVM reference implementation)

`design/security-model.md` asserts that the runtime emits structured logs and metrics, and that persistent recording of graph admissions, capability grants, and effect violations supports detection of unusual activity. The implementation has none of the three: `strand run` emits a type line and a value line, no hook at the foreign-call boundary records which effects a program actually exercised, and the only enforcement evidence available to an operator is the absence of a CapabilityViolation. This is the gap between the containment bound being argued (Q-044) and being continuously observable.

The mechanism is cheap by construction: every effectful call already passes through one dispatch point with the EffectDecl, the resolved capability pattern, and the evaluated argument values in hand. An audit record — call-site NodeId, effect category, refinement parameter values, timestamp, outcome — emitted per foreign dispatch would let an operator reconcile the declared closure against performed effects per run. Open design points: record format and sink, CLI surface, interaction with credential scrubbing (Q-042 — argument values in the log must be the scrubbed forms), group-runtime integration alongside the existing metrics, and whether the log feeds a recorded-effects replay substrate for plain programs.

### Q-064: Capability-denial observability for orchestrating principals {#Q-064}

**Status:** Resolved (2026-06-12; implemented per [`proposals/implemented/capability-denial-observability.md`](proposals/implemented/capability-denial-observability.md))
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md), [`design/security-model.md`](design/security-model.md), [Q-048](#Q-048) (the catchable/uncatchable taxonomy), [Q-054](#Q-054) (the embedding API this lands on), [Q-055](#Q-055) (the audit log this likely shares records with)
**Resolution:** A `DenialReport` record (effect category name, scrubbed positional requested refinement parameters, rendered held-grant summary for the denied category, denying node, machine instance and event index, phase discriminator `expression`/`transition`/`invariant`/`group-start`) constructed at the existing denial site and exposed on two surfaces, both shipped. Surface 1: structured data on `InterpretError.CapabilityViolation` and `RefinementViolation` (the bytecode VM's category-only denial unified at the same boundary with an honestly coarse report, `VmCapabilityViolation` removed), plus denial-caused halt reasons — `HaltReason.CapabilityDenial` on the synchronous fold and `MachineInstanceHandle.denialReport` on the async actor path, with instance/event/phase attached at translation; the field the Q-054 embedding API will inherit. Surface 2: exactly one always-on machine-readable `strand:denial {json}` stderr line on denial-terminated `run`/`machine`/`group` invocations, field-for-field the report with the Q-051 author id and source line as separate fields; no line on any non-denial termination. Values pass through `CredentialScrubber` at construction and honor `ErrorVerbosity` (`RedactedWithKindOnly` withholds requested/held); nothing became observable in-language — no new `Value`, no `isCatchable` change — and Attempt's inability to catch denials is re-asserted over the new path with an unchanged report. Deviations recorded in the Implementation note (positional `requested` array rather than the worked example's name-keyed object; VM-boundary unification; sync-fold denials now halt with a reason instead of rethrowing).

Capability and refinement denials are uncatchable in-language by design — Q-048 classifies them terminal regardless of any enclosing Attempt, which is correct against a generated program probing its own sandbox. But the orchestrating principal that constructed the capability context is not the adversary that rule defends against, and its only signal today is rendered error text. A structured denial outcome at the host boundary — effect category, refinement parameters requested versus held, node, machine instance — would let an orchestrator repair the program or re-scope the grant programmatically instead of regenerating blind. The open design core is the shape of that outcome and the boundary that preserves in-language opacity while exposing the structure host-side; the likely landing surfaces are the Q-054 embedding API's run result and a Q-055 audit-log record kind, not the node algebra.

### Q-067: Surfacing the verifier-computed effect closure on the verify result {#Q-067}

**Status:** Resolved at the success-path level; pre-admission closure documented as host-re-derived
**Concerns:** [Q-044](#Q-044) (the harm bound this closure feeds), [Q-054](#Q-054) (the embedding API a surfaced closure would land on), `VerifyResult.Ok` and `VerifyState.nodeClosures` (Kotlin/JVM reference implementation), the containment demonstration ([`demos/containment-host/README.md`](demos/containment-host/README.md))
**Resolution:** `VerifyResult.Ok` gains `nodeClosures: Map<NodeId, Set<NodeId>>` (EffectCategory NodeIds keyed by node NodeId exactly as `nodeTypes` is), populated from `VerifyState.nodeClosures` at the single production construction site, plus a `rootClosure(root)` accessor returning the program root's EffectCategory set — `closure(g)` in the Q-044 harm bound. Additive with a default and hash-neutral (`VerifyResult` is not part of the canonical node encoding). The surfaced value is the verifier's own closure-subtraction-aware computation, so it is Handler-aware where a host-side structural walk is not (`SurfacedEffectClosureTest` pins this: corpus 16 surfaced equals the structural walk; corpus 36, a Handler intercepting Time.Now, surfaces an empty root closure while the walk still reports Time.Now; corpus 39 surfaces `{Filesystem.Write}` with the intercepted Time.Now subtracted and the handle's own write retained). The pre-admission case is resolved by a documented decision rather than a standalone entry point: the closure computation cannot be cleanly separated from full type inference — `nodeClosures` is filled only as a side-effect of `infer()` (the Application closure adds the *resolved* callee's effect row; the Handler subtraction depends on resolved signatures), and verification aborts before recording the root closure on the first hard error, so a rejected program has no verifier closure, sound or otherwise. A host needing the harm bound for an artifact that does not type-check (the containment demonstration's scenario S1, rejected with `ProjectionMismatch`) re-derives a sound structural upper bound, guaranteed sound by the mandatory `UncoveredEffects` rule; being Handler-unaware it is a looser bound than the surfaced value, acceptable for an over-approximation. The demonstration's scenario S3 (a clean-verifying program) now consumes the surfaced `rootClosure` directly; S1 retains `ContainmentDemo.declaredEffectClosure` for the rejected-artifact case with a comment recording this resolution. No node category, encoding, or golden-hash change.

The verifier already computes, for every reached expression node, the set of EffectCategory NodeIds its evaluation may exercise — `VerifyState.nodeClosures`, the closure-subtraction-aware computation that is the source of truth for `UncoveredEffects` and for Handler's effect removal. The closure of the program root is exactly the declared effect closure that the Q-044 harm bound `closure(g) ∩ C ∩ B ∩ P` opens with. That value is discarded after verification: `VerifyResult.Ok` exposes `nodeTypes` but not `nodeClosures`, so a host that wants the harm bound must re-derive it. The containment demonstration does precisely this in `ContainmentDemo.declaredEffectClosure` — a structural walk from the root collecting `EffectCategory.categoryName`s — duplicating a computation the verifier just performed (and, being Handler-unaware, computing a slightly looser bound than the verifier's).

The obvious fix is additive and hash-neutral: a `nodeClosures: Map<NodeId, Set<NodeId>>` field on `VerifyResult.Ok`, keyed by NodeId exactly as `nodeTypes` is, populated from `state.nodeClosures` at the single production construction site. `VerifyResult` is not part of the canonical node encoding, so this moves no hash. What it does not do is let the demonstration drop its walk: the demo's only consumer is scenario S1, whose whole point is to compute and display the harm bound for an *over-reaching submission the verifier rejects* (`ProjectionMismatch`), and `nodeClosures` is populated only on a successful `VerifyResult.Ok`. The design question is therefore broader than adding a field — it is whether and how the verifier should expose a sound effect closure that is usable on an artifact that does not (or does not yet) type-check, which is the pre-admission harm-bound use case the demo exercises. Surfacing on `Ok` is worth doing for the success-path consumers (run-by-hash verdict caches, audit tooling, an embedding host that admits a clean program and wants its declared closure without a second walk); covering the rejected-artifact case needs a distinct entry point that runs the closure computation independent of full type inference, or a documented decision that the host re-derives in that case. Until decided, the demonstration carries a sound upper-bound workaround — guaranteed by the mandatory `UncoveredEffects` rule, so no admitted graph performs an effect absent from the walk's result — with a comment pointing here.

### Q-068: Refinement-narrowing CapabilityScope {#Q-068}

**Status:** Open
**Concerns:** [Q-031](#Q-031) (refinement-lattice capability matching, whose follow-up this is), CapabilityScope (N-036) in [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md), the plugin-host demonstration ([`demos/plugin-host/README.md`](demos/plugin-host/README.md))

CapabilityScope (N-036) narrows the capability context for a subgraph by intersecting effect categories: a retained category keeps its refinement patterns verbatim, so a scope cannot tighten a wildcard-path grant `Filesystem.Write{path: *}` to a single subtree `Filesystem.Write{path: /plugins/A/*}`. In-graph attenuation is therefore category-granular, not refinement-granular. The plugin-host demonstration's fine-grained delegation (scenario C4) is consequently achieved at the grant level — the host constructs a narrowed `CapabilitySet` before running the plugin — rather than through a CapabilityScope node; the demonstration records the distinction, and the genuine category-narrowing CapabilityScope provides is shown as scenario C4' with its static `CapabilityScopeUnsatisfiable` guarantee.

Grant-level narrowing covers the host-delegates-to-plugin case, which is where attenuation naturally lives. The open extension is in-program refinement attenuation: a program holding a broad refined capability dropping to a narrower refinement before calling an untrusted subgraph, the capability analogue of dropping privileges before exec. Resolving it means extending CapabilityScope's matching to narrow refinement patterns within a retained category, a refinement-lattice meet reusing the Q-031 machinery, and deciding the verifier rules for an over-narrowing scope. Deferred until a concrete in-program attenuation need arises; the host-delegation use case the demonstrations exercise does not require it.

### Q-070: Latent ToolDef effects absent from the static effect closure {#Q-070}

**Status:** Open
**Concerns:** [Q-044](#Q-044) (the static harm bound this incompleteness qualifies), [Q-067](#Q-067) (the surfaced effect closure that omits these effects), N-044 ToolDef, [Q-037](#Q-037) (agent-native LLM capabilities, where the model chooses whether to invoke a ToolDef), the agent-workflow demonstration ([`demos/agent-workflow/README.md`](demos/agent-workflow/README.md))

An N-044 ToolDef bundles a parameter Schema with an `implementation` (a Lambda or ForeignNode) the model may choose to invoke during a per-provider LLM Generate call. The implementation can carry effects — a `get_weather` tool whose body performs `Filesystem.Write`. When the model invokes the tool, the runtime dispatches the implementation and capability-checks its effects at the foreign-call boundary, so an ungranted effect is denied — the agent-workflow demonstration's scenario A2 witnesses this, the tool's write denied with a `DenialReport` under a `{LLM.Generate}`-only grant — and the *enforced* bound is therefore sound. The gap is in the *static* bound: the program's root effect closure (`VerifyState.nodeClosures`, surfaced via Q-067's `rootClosure`) does not include the ToolDef implementation's effects, because the tool is invoked indirectly — by the model at runtime — not through a direct Application the verifier walks. A program that constructs a tool able to write files and hands it to Generate has root closure `{LLM.Generate}`; the benign program and the file-writing-tool program produce identical surfaced closures.

The consequence bears on the Q-044 lead claim that the maximum harm of a generated subgraph is computable from the artifact before execution. For agent programs — the target workload — ToolDefs are precisely the latent capabilities the model wields, so the static harm bound `closure(g) ∩ C ∩ B ∩ P` understates the reach of exactly the most security-relevant programs: a host admitting on the surfaced closure alone, without separately inspecting reachable ToolDef implementations, would not see that a program carries a tool that could write files were its category granted. Soundness — no run exceeds the runtime-enforced bound — is preserved; completeness of the *pre-execution* bound is not. The same shape recurs for any indirectly-invoked effectful value (a projected ForeignNode passed as a `List.Map` callback already misses Q-039's static projection-match check for the same reason), but ToolDef is the sharpest instance because an external party, the model, decides whether to invoke it.

Candidate directions. (1) Fold each reachable ToolDef's implementation effect surface into the verify result as a distinct channel — a `latentToolClosure` separate from `closure(g)` — so a host sees both what the program directly performs and what its tools could perform if invoked, without conflating the two or disturbing the Handler closure-subtraction semantics. (2) Surface a per-ToolDef declared effect surface (parallel to Q-067's `nodeClosures`) and make folding it into the grant decision the host's responsibility, a lighter change that keeps `closure(g)` meaning "directly performed." (3) Treat the runtime gate as the bound and document that the static closure excludes indirectly-invoked ToolDef effects, hosts expected to inspect ToolDefs — the record-only option, which leaves the headline static-harm-bound property explicitly qualified for agent programs. The choice interacts with whether a constructed-but-never-passed-to-Generate ToolDef should count (an over-approximation question) and with how the harm bound is presented to an orchestrating principal making a grant decision.

## Foreign function interface {#questions-ffi}

### Q-006: Trust and signing model for foreign bindings {#Q-006}

**Status:** Proposed
**Concerns:** [`design/security-model.md`](design/security-model.md), [`decisions/ADR-005-foreign-nodes.md`](decisions/ADR-005-foreign-nodes.md)
**Resolution:** Four complementary mechanisms: signed provenance, reproducible binding generation, curated registries, and runtime sandbox observation. Proposed in [`design/security-model.md`](design/security-model.md). Deployments combine mechanisms according to their sensitivity policy.

ForeignNode declarations make claims about foreign function effects that the Strand verifier cannot independently verify. A compromised or malicious binding can lie about effects, breaking the security guarantees of every downstream graph that uses it. The mitigation requires a trust model for foreign bindings: signed bindings, reproducible binding generation, a curated registry, or some combination. The exact model has not been specified.

### Q-007: Effect inference for unannotated foreign code {#Q-007}

**Status:** Proposed
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md), foreign function interface
**Resolution:** Native graph nodes always declare effects; the language does not infer. For foreign code, the source determines the approach: WIT-typed sources translate automatically, Erlang/Elixir specs translate with author confirmation, native C/C++/Rust requires manual annotation with tool-assisted proposals. When effects cannot be determined, the default policy refuses the binding rather than admitting an unusable conservative annotation. Proposed in [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md).

When auto-generating ForeignNode declarations from existing libraries (e.g., the Android SDK), effect annotations are not available from the foreign source. The default behavior — assume worst-case effects, refuse to bind, attempt static analysis of foreign code, observe behavior at runtime — has not been determined.

### Q-056: Signature verification for in-process builtin bindings {#Q-056}

**Status:** Open
**Concerns:** [`decisions/ADR-005-foreign-nodes.md`](decisions/ADR-005-foreign-nodes.md), [Q-006](#Q-006), interpreter `Builtins` registry, verifier ForeignNode admission (Kotlin/JVM reference implementation)

A ForeignNode's declared `foreignType` is taken on faith, which ADR-005 accepts for genuinely foreign code — the binding's claims are the trust boundary, and Q-006 covers that trust model. For the `strand-builtin:` namespace, however, the truth is co-resident in the same process: the registry knows every builtin's real argument and result shapes, yet the verifier never cross-checks a declared FunctionType against it. Because polymorphic and Option-returning builtins are deliberately excluded from the implicit prelude, agents hand-declare these signatures at every use site — so a mis-declared signature is a high-frequency failure shape, and it produces the worst outcome available to the verify-first discipline: the graph verifies cleanly, then the builtin's internal argument checks fail at runtime as raw JVM exceptions that carry no NodeId and are not translated into the structured `InterpretError` taxonomy. Integer division by zero was likewise a bare argument-check failure until the Q-048 follow-up of 2026-06-11 closed the untranslated-exception half of this question: `InterpretError.BuiltinContractViolation(at, target, detail)` — uncatchable, per the error-recovery taxonomy — now translates `IllegalArgumentException` strictly at the six `builtin.invoke` dispatch boundaries, so builtin contract failures surface structured and attributable. The declared-signature verification this question names remains open.

Resolution shape: per-builtin signature metadata in the registry — an exact FunctionType for monomorphic builtins, a shape schema for the polymorphic and agent-typed families — checked at ForeignNode admission for `strand-builtin:` targets with a new VerifyError on mismatch, plus translation of argument-shape failures and arithmetic domain errors at the dispatch boundary into structured `InterpretError` variants. Distinct from Q-006, which governs bindings whose implementations the verifier cannot inspect.

## State machines {#questions-state-machines}

### Q-008: High-throughput communicating state machine architecture {#Q-008}

**Status:** Deferred until Milestone 2.5+ (distributed multi-node runtime engineering)
**Deferred until:** Milestone 2.5+. Reason: step 1 synchronous runtime and step 2 single-JVM async actor runtime have both shipped (Q-032, Q-033 Resolved), and step 3 ([`proposals/implemented/state-machines-runtime-step-3.md`](proposals/implemented/state-machines-runtime-step-3.md)) has fully landed. The high-throughput multi-node engineering this question names — BEAM-scale lightweight scheduling across nodes, locality-aware placement, snapshotting in a content-addressed setting — is post-Milestone 2.5 work and depends on the distribution model in [`design/distribution-model.md`](design/distribution-model.md).
**Concerns:** [`design/state-machines.md`](design/state-machines.md)
**Partial resolution:** Design constraints are specified in [`design/state-machines.md`](design/state-machines.md): lightweight scheduling, batch event processing, locality-aware placement, snapshotting, content-addressed garbage collection. BEAM is the reference architecture. The constraints are necessary; the implementation engineering is open and is a Phase 2 milestone in [`research-plan.md`](research-plan.md).

The state machine design handles distributed consensus, real-time messaging, and similar workloads in principle: each participant is a state machine, communication is event streams between machines. The runtime engineering required to make thousands of communicating machines efficient is substantial. Erlang's BEAM VM provides a reference architecture but adopting it directly may not match Strand's graph-native execution model. The runtime architecture for high-throughput state machine systems has not been specified.

### Q-009: Event ordering across multiple streams {#Q-009}

**Status:** Proposed
**Concerns:** [`design/state-machines.md`](design/state-machines.md)
**Resolution:** Layered policies: FIFO-per-stream with non-deterministic merge as default; optional priority-based, causally-ordered (vector clocks), and timestamp-based merges as opt-in declarations on the StateMachine node. Proposed in [`design/state-machines.md`](design/state-machines.md).

State machines that receive events from multiple streams need a merge policy. Options include first-come-first-served, priority-based ordering, causally-ordered (vector clocks), and timestamp-based ordering. Each has tradeoffs in correctness, performance, and complexity. The default policy and the set of available alternatives have not been specified.

### Q-010: Hot upgrade semantics for transition functions {#Q-010}

**Status:** Proposed
**Concerns:** [`design/state-machines.md`](design/state-machines.md)
**Resolution:** Two-phase atomic upgrade. The new transition function must declare compatibility (same state type, or migration function provided). The runtime pauses event dispatch, applies the migration, swaps the function reference, and resumes. Cluster-wide coordinated upgrade uses the cluster coordinator. Proposed in [`design/state-machines.md`](design/state-machines.md).

Updating the transition function of a running state machine requires a defined upgrade procedure, including state migration when the state type changes. Erlang's `code_change` callback provides a reference, but its semantics in a content-addressed setting (where the old and new transition functions have stable distinct identities) require specification.

### Q-059: Long-running machine groups and snapshot persistence {#Q-059}

**Status:** Resolved at the single-process service level
**Concerns:** [`design/state-machines.md`](design/state-machines.md), [Q-008](#Q-008) (the distributed runtime this is prerequisite to), [Q-032](#Q-032)/[Q-033](#Q-033) (the shipped runtimes), runtime `Snapshot` and `EventCodec`, `strand group` CLI (Kotlin/JVM reference implementation)
**Resolution:** Three coordinated pieces on the Q-054 `StrandRuntime` facade, single-process only, implemented in [`proposals/implemented/long-running-groups.md`](proposals/implemented/long-running-groups.md): a reusable deterministic-reversible `Value` codec (`runtime/ValueCodec.kt`) over the first-order snapshot-relevant subset (Closures and live Resources in state are a documented structured-error non-snapshotable case; `EventCodec` now delegates its decode to it); snapshot persistence across restart via a `SnapshotCodec` plus facade `writeSnapshot`/`readSnapshot`/`resume` (the restart-resume trajectory equals an uninterrupted run, asserted end-to-end); and a non-batch `GroupService` driver with an opt-in per-event limits model (`EvaluationLimits.perEventStepBudget`) so long-lived actors are not killed by the whole-run wall-clock for being alive, preserving the Q-044 harm bound. Runtime-state serialization only — no node-encoding or golden-hash change; full suite 2255 tests green. Multi-node distribution remains [Q-008](#Q-008), out of scope.

A machine group today exists for the duration of one blocking host call. `Snapshot` captures a live `Value` with serialization declared the host's responsibility, but no `Value` byte codec exists anywhere in the implementation (`EventCodec` is decode-only), so no snapshot can leave the process and no group survives restart — replay-from-log is a within-process facility. `strand group` is strictly batch: it sends a routed-events file, closes the external inputs, and drains until the actors halt; there is no serve or follow mode. The default wall-clock budget of 30 seconds terminates any service-shaped program (the `Http.Listen` / `Http.Accept` builtins exist and invite exactly that shape), and blocking accepts advance no evaluation steps, so they are invisible to the wall-clock sampling the limits system relies on — the same gap Q-045 closed for stream reads via `streamReceiveTimeoutMillis`.

This question is distinct from and prerequisite to the Q-008 multi-node engineering: it is the single-process service story. Scope: a canonical `Value` encode/decode pair (the encode half of the existing event format), snapshot save/load surfaces on the group handle and the CLI, a non-batch group driver that keeps external inputs open, and a limits model compatible with long-lived processes — per-event or resettable budgets, and timeouts on blocking accepts.

## Encryption and security {#questions-encryption}

### Q-011: Per-node encryption key management {#Q-011}

**Status:** Proposed
**Concerns:** [`design/encryption-model.md`](design/encryption-model.md)
**Resolution:** Detailed envelope format, four key types (principal, session, attestation-bound, symmetric-wrap), multi-recipient encryption protocol, BLAKE3 + AES-256-GCM + X25519 algorithm selection, generation/distribution/rotation/revocation lifecycles, and revocation Merkle tree. ### Q-012: TEE attestation chain integration {#Q-012}

**Status:** Proposed
**Concerns:** [`design/security-model.md`](design/security-model.md), [`design/encryption-model.md`](design/encryption-model.md)
**Resolution:** Four-level attestation chain: platform identity → launched-workload measurement → Strand-runtime identity → graph identity. Attestation results are presented as `Trust.Attestation` capabilities. Cross-platform abstraction follows IETF RATS evidence/attestation-result distinction. Proposed in [`design/security-model.md`](design/security-model.md), with key-handling details in [`design/encryption-model.md`](design/encryption-model.md).

Trusted Execution Environment integration requires mapping Strand's content-addressed graph identity to the TEE's attestation primitives (measured launch, sealed storage, remote attestation). The specific protocol — what is attested, what the verifier checks, how attestations are presented as capabilities — has not been specified.

### Q-013: Obfuscation guarantees and limits {#Q-013}

**Status:** Deferred — topology obfuscation is a future research direction beyond Milestone 2.x
**Deferred until:** Future research phase (post-Phase-2). Reason: per-node encryption already provides cryptographic confidentiality of node *contents*, which is the load-bearing security property today. Stronger obfuscation through structural transformations (decoy nodes, splitting, merging) is identified as a future research direction and not on any Milestone 2.x line item; revisiting it requires either an adversary model that today's deployments demand or a research agenda separate from the production runtime.

**Partial resolution:** Per-node encryption provides cryptographic confidentiality of node contents to non-key-holders. Documented in [`design/security-model.md`](design/security-model.md).

The security model claims that subgraph encryption, hash-only metadata stripping, and semantic-preserving graph transformations provide meaningful obfuscation against reverse engineering. ## Distribution {#questions-distribution}

### Q-014: Scheduler policy under competing constraints {#Q-014}

**Status:** Proposed
**Concerns:** [`design/distribution-model.md`](design/distribution-model.md)
**Resolution:** Four primary policies (minimize data movement, minimize critical-path latency, balance load, maximize fault tolerance) combinable via weighted scoring. Default is hybrid (data movement primary, latency secondary, fault tolerance respected). Per-graph overrides via `Placement` annotations. Policies are themselves programmable as `SchedulerPolicy` nodes. Proposed in [`design/distribution-model.md`](design/distribution-model.md).

The distribution model describes placement as constraint satisfaction over effects and capabilities. When multiple valid placements exist, the scheduler must choose. The policy — minimize latency, minimize data movement, balance load, maximize fault tolerance — has not been specified. Different workloads benefit from different policies; whether the policy is fixed, configurable, or programmable per-graph is open.

### Q-015: Backpressure semantics for distributed event streams {#Q-015}

**Status:** Proposed
**Concerns:** [`design/distribution-model.md`](design/distribution-model.md), [`design/state-machines.md`](design/state-machines.md)
**Resolution:** Bounded queues per stream with per-stream overflow policy (block-producer default, drop-newest, drop-oldest, sample as alternatives). Cross-machine backpressure communicated via protocol `Backpressure` signal. Multi-hop propagation is straightforward but operationally requires monitoring to detect starvation. Proposed in [`design/state-machines.md`](design/state-machines.md) and [`design/distribution-model.md`](design/distribution-model.md).

When events arrive faster than a state machine can process them, the backpressure response must propagate to upstream sources. In a distributed setting, this propagation crosses machine boundaries and may involve multiple upstream sources with different policies. The standard backpressure policies (Reactive Streams, etc.) provide a starting point but their integration with Strand's distribution model has not been specified.

### Q-016: Network failure handling during graph fetches {#Q-016}

**Status:** Proposed
**Concerns:** [`design/distribution-model.md`](design/distribution-model.md)
**Resolution:** Retry with exponential backoff (3 retries default, 100 ms initial), fallback to alternative peers from the peer directory, bounded per-fetch timeout (30 s default, 5 s on critical path), failure propagation to the scheduler which may re-place or abort. Proposed in [`design/distribution-model.md`](design/distribution-model.md).

When a worker references a node by hash that requires fetching from a different machine, the fetch can fail due to network conditions. Retry policy, timeout, fallback to alternative replicas, and the propagation of unrecoverable failures up to the scheduler have not been specified.

### Q-017: Bytecode VM specification {#Q-017}

**Status:** Proposed (step 1 — Kotlin reference VM — specified in `proposals/bytecode-vm-step-1.md`, 2026-05-24; step 2 — Rust production VM per ADR-008 — to be drafted as a separate proposal when step 1 lands)
**Concerns:** [`decisions/ADR-008-compilation-target.md`](decisions/ADR-008-compilation-target.md), [`design/node-algebra.md`](design/node-algebra.md)
**Resolution:** Two-step shipping strategy. Step 1 ships a Kotlin reference bytecode VM (`:bytecode` + `:vm` Gradle modules) that runs every corpus program with bytewise-equivalent behavior to the tree-walking interpreter. Step 2 ports the same design to Rust per ADR-008 and tunes for performance. The instruction set (28 opcodes), uniform-boxed value representation, stack-based calling convention with closure captures, JVM-leaning GC, and node-by-node lowering scheme are fully specified for step 1; step 2 inherits the test suite as its correctness specification. Path B (Kotlin-first) chosen over Path A (Rust-first) because iteration speed dominates: design validation happens at week 4-6 instead of month 4-6, surfacing any design surprises (the project has had several) cheaply. ~70% of step 1's work transfers to step 2 (instruction set, lowering, test corpus, verifier integration); ~30% is Kotlin-specific (op-dispatch loop, GC). Effect/capability bytecode operations (`CAP_PUSH`/`CAP_POP`/`HANDLER_PUSH`/`HANDLER_POP`) are first-class per ADR-008; types, schemas, and recursive types are erased pre-bytecode; state machines remain runtime objects consuming bytecode for their transition functions. Detailed proposal in [`proposals/bytecode-vm-step-1.md`](proposals/bytecode-vm-step-1.md).

The decision to use a bytecode VM as the initial execution target requires a bytecode specification: instruction set, value representation, calling convention, garbage collection model. The step 1 specification closes the deferred half; step 2 carries the design into Rust for production performance.

### Q-019: Iterative computation primitives {#Q-019}

**Status:** Proposed
**Concerns:** [`design/node-algebra.md`](design/node-algebra.md), runtime

### Q-052: Cross-implementation hash conformance {#Q-052}

**Status:** Resolved at the conformance-artifact level (golden hash vectors plus a normative encoding specification, 2026-06-10); validation against a second implementation remains and falls due with the [Q-017](#Q-017) step 2 Rust port
**Concerns:** [`decisions/ADR-003-content-addressing.md`](decisions/ADR-003-content-addressing.md), [`design/node-algebra.md`](design/node-algebra.md) § Hash construction, [`design/canonical-encoding.md`](design/canonical-encoding.md), [Q-017](#Q-017) step 2, corpus
**Resolution:** Two artifacts make the "two implementations must produce identical hashes" convention verifiable from the written record rather than from Kotlin source. (1) [`corpus/golden-hashes.json`](corpus/golden-hashes.json) pins the root content hash of all 84 corpus programs plus the 14 Layer A density fixtures in compiled form, with structural program detection (top-level `root` and `nodes` keys), bidirectional coverage assertions in `CorpusGoldenHashTest`, and a documented regeneration path (`-Dstrand.regenerateGoldenHashes=true`; see `corpus/README.md` § Golden hashes); internal cross-checks tie the corpus-76 `targetHash`, the corpus-77 registry binding, and every Layer A fixture hash to their canonical counterparts. (2) [`design/canonical-encoding.md`](design/canonical-encoding.md) specifies the encoding normatively — framing (a four-byte big-endian category tag followed by concatenated canonical-CBOR items, deliberately not a parseable CBOR document), the complete category-tag and discriminator tables, presence-prefix and default-gating rules, metadata exclusions, enum ordinal assignments, de Bruijn frame construction, and the unbound sentinels — validated by six byte-level traces in `CanonicalEncodingSpecTest` built from the prose alone. The specification records the portability hazards the validation surfaced: name-keyed sorts use UTF-16 code-unit order rather than UTF-8 byte order, a free TypeParameter hashes through a sentinel preimage, MatchCase pushes no binder frame when its pattern binds nothing, FloatLit hashes raw IEEE 754 bits, and set-like lists are sorted but not deduplicated.

Before this registration, no language-independent conformance artifact existed: corpus hash expectations lived only as self-consistency assertions in Kotlin tests, and the encoding's load-bearing details (tag values, gating rules, ordinals, binder frames) were documented only in the encoder source. A second implementation could have produced divergent hashes for every program without any artifact catching it. Identified by the 2026-06-10 independent review.

### Q-054: Embeddable runtime and per-instance host policy {#Q-054}

**Status:** Resolved (facade implemented 2026-06-13; concurrent multi-tenant isolation completed 2026-06-13 in the Kotlin/JVM reference implementation)
**Concerns:** Kotlin/JVM reference implementation (`Builtins` singletons, CLI), [`proposals/implemented/embeddable-runtime.md`](proposals/implemented/embeddable-runtime.md), [Q-040](#Q-040)/[Q-041](#Q-041)/[Q-042](#Q-042) (the host-policy carriers), [Q-008](#Q-008) (distribution), [Q-017](#Q-017) step 2 (the Rust VM host API), [Q-058](#Q-058) (persistent store)
**Resolution:** A `HostPolicy` immutable value object bundling the scattered policy (sandbox, evaluation limits — which carry error verbosity and the stream-receive timeout, the single source of truth — clock, credential provider, name resolver, RNG, LLM/vector HTTP clients, log sink, OS-env source, exit handler, tool-loop limit) with `OPEN`/`SECURE` companion defaults mirroring `SandboxPolicy.OPEN_DEFAULT`/`SECURE_DEFAULT` (`SECURE` differs only in the sandbox field), plus a `StrandRuntime` facade (`verify` / `verifyAndCheckSchema` / `run` / `runMachine` / `runGroup`, taking a parsed `ProgramImage` — run-by-hash is Q-058, out of scope) constructed with a `HostPolicy` and threading it into the `Interpreter` / `StateMachineRuntime` / `SchemaChecker` it builds. The install/restore of the host-routed singletons is centralized in one `Builtins.snapshot`/`install`/`restore` protocol behind the facade's `withInstalled` extension, subsuming the CLI's former `withProgramEvaluationContext`; the CLI's `run`/`machine`/`group` are reimplemented as thin facade clients with flags, output, federation, denial-line emission, and exit codes unchanged. Implemented per [`proposals/implemented/embeddable-runtime.md`](proposals/implemented/embeddable-runtime.md). The concurrent-isolation follow-up (completed the same day) closes the facade's original scope decision: a `HostContext` immutable value — the per-invocation runtime-side projection of a `HostPolicy`, carrying every host-routed field a builtin lambda reads plus a per-context credential scrubber — flows through evaluation as an ordinary argument. The builtin invocation signature gained the context (`Fn.invoke(ctx, args)` / `FnH.invoke(ctx, args, apply)`); the ~165 pure builtins ignore it while the ~53 effectful lambdas read it through a `HostContext`-receiver registration helper with no per-site edit, and the interpreter, bytecode VM, and async actor runtime thread it as a value (the actor runtime binds it into every per-actor interpreter and stream feeder, so work moving across `Dispatchers.IO` threads reads the right tenant's policy by construction — no thread-local). `CredentialScrubber` was split into an instantiable `Scrubber` plus a process-global default, so each context scrubs error text against its own tenant's resolved credentials. With the reads explicit, the `Builtins.snapshot`/`install`/`restore` install/restore protocol and the facade's `withInstalled` were retired; the `Builtins` `@Volatile` singletons remain only as the single-tenant default source `HostContext.processDefault()` reads and as the test-injection seam. `ConcurrentMultiTenantIsolationTest` runs two runtimes on parallel coroutines with a `CyclicBarrier` forcing genuine overlap inside the effectful path and asserts each reads its own `FixedClock`, a SECURE tenant rejects an fs-escape an OPEN tenant concurrently permits, and one tenant's credential never appears in another's scrubbed error. One genuinely-incidental read is routed through the default and recorded: `DefaultLlmHttpClient.openStream` reads the global `streamReceiveTimeoutMillis` for the LLM SSE open-timeout because the transport interface carries no timeout argument (the isolation-critical `Net.Connect` socket timeout is context-sourced). Full suite 2286 tests green; no node category, encoding, or hash change.

The only executable entry point to the reference implementation is the CLI. A host application that wants to run a Strand program in-process must hand-replicate the CLI's pipeline (ingest → finalize → verify → schema-check → build obligations → evaluate) and participate in a mutation protocol over roughly a dozen process-global `@Volatile` singletons on the `Builtins` object — `sandboxPolicy`, `credentialProvider`, `clock`, `random`, `llmHttpClient`, `verifierNodeTypes`, `streamReceiveTimeoutMillis`, and the rest — whose save/restore discipline is correct only because the CLI runs exactly one program per process. Two concurrent evaluations in one JVM would share a single sandbox policy and credential provider, which is a security hazard rather than a style concern; `ResourceTable` and `CredentialScrubber` are likewise process-global. In-source comments acknowledge per-interpreter policy injection as a future refactor; nothing tracked it until this entry.

Resolution shape: a runtime facade (load, verify, run against an injected policy bundle) as the published embedding surface, with the global singletons replaced by per-interpreter or per-runtime-instance policy threading. This is the structural prerequisite for any server, daemon, or multi-tenant host, for safe parallel evaluation in one JVM, and for the distributed runtime; it also determines what the planned Rust VM's host API should look like.

### Q-065: Determinism enforcement for replay-relevant evaluation {#Q-065}

**Status:** Resolved (implemented 2026-06-12 in the Kotlin/JVM reference implementation)
**Concerns:** [`design/state-machines.md`](design/state-machines.md) (replay), [`design/node-algebra.md`](design/node-algebra.md) (purity), the `Builtins` registry, [Q-047](#Q-047) (invariant evaluation), [Q-050](#Q-050) (the warning channel reused)
**Resolution:** Registry metadata, not graph surface: a three-valued `determinism` field (`Deterministic` / `Stateful` / `Nondeterministic`) on every builtin entry, with registration requiring effect-free builtins to declare `Deterministic` explicitly (omission is a construction-time failure naming the target) and a consistency test asserting effect-declaring builtins are `Stateful` or `Nondeterministic`, effect-free builtins are `Deterministic`, and the registry-side flags agree with the prelude and signature-table effect declarations. `VerifyWarning.NondeterministicInReplayContext` on the Q-050 channel guards transition-function and invariant closures, resolved through a ServiceLoader oracle seam between the verifier and the interpreter registry and scoped to effect-free ForeignNodes (effect-declaring calls are already mediated by the effect machinery). The registry-wide double-evaluation audit covers all 165 `Deterministic` entries total-by-construction — 160 signature-generated, 5 fixtured (the resource-closing family) — with Float NaN edge semantics pinned on raw bits in the same pass; no nondeterministic effect-free builtin surfaced. No encoding or hash impact. Implemented per [`proposals/implemented/determinism-enforcement.md`](proposals/implemented/determinism-enforcement.md), which records the deviations.

Replay, snapshot recovery, and audit rest on pure transition functions re-evaluating to identical results, but purity is a structural property (no effect edges) while determinism is behavioral, and nothing marks or checks the difference. A builtin with no effect category may still be nondeterministic in host behavior; Float operations carry NaN edge semantics; any future operation with iteration-order dependence would silently break replay while remaining structurally pure. Candidate resolution: a per-builtin determinism marker in the registry, a verifier check that transition-function closures and invariant bodies reference only marked-deterministic builtins, and a registry-wide harness test asserting double-evaluation equality. The question includes whether the marker is registry metadata or surfaces in the graph.

### Q-044: Containment measurement for the structural-safety claim {#Q-044}

**Status:** Resolved at the measurement level (containment matrix shipped 2026-05-29 as [`evaluation/containment-results.md`](evaluation/containment-results.md)); agent-emission intent-visibility study deferred as a follow-up
**Concerns:** [`02-core-thesis.md`](02-core-thesis.md) § outcome-priority, [`design/security-model.md`](design/security-model.md), Q-021 (cost measurement this parallels), Q-039 through Q-042 (the resolved findings measured here)
**Resolution:** A measurement substantiating the re-weighted lead claim that the maximum harm of a generated subgraph is computable before execution and bounded during it. The harm bound is defined as `closure(g) ∩ C ∩ B ∩ P` — the statically computed effect closure intersected with the runtime capability context, resource budget, and sandbox policy — and the soundness property (no execution exceeds the bound) is argued with the corpus and unit-test witnesses as spot-checks. A comparative containment matrix scores six agent-plausible harm classes (confused deputy, resource exhaustion, path traversal, SSRF, credential leak, undeclared effect / ungranted capability) by where the harm is stopped: verify-time, runtime, or not at all. Every class is rejected at verification or contained at runtime in Strand; none is contained by default in the conventional baseline. The conventional-baseline rows are grounded in executed probes ([`evaluation/containment/python_baseline_probes.py`](evaluation/containment/python_baseline_probes.py)) under stock Python 3, not asserted.

The measurement is deliberately analytical rather than statistical: containment is categorical and deterministic, unlike the continuous, noisy token cost that Q-021 samples. A finite probe set witnesses containment but cannot establish soundness universally; a mechanized proof of the effect-closure and capability-confinement properties is a possible future strengthening. A distinct, larger study — whether mandatory effect declaration makes an agent surface dangerous intent more often than a conventional language buries it — measures intent visibility rather than harm containment, requires agent-emission sampling through the strand-eval harness, and is deferred as a follow-up under this identifier.

### Q-066: Adversarial verification corpus {#Q-066}

**Status:** Resolved (2026-06-12; implemented per [`proposals/implemented/adversarial-verification.md`](proposals/implemented/adversarial-verification.md))
**Concerns:** [Q-044](#Q-044) (whose soundness is argued, not benchmarked), [Q-052](#Q-052) (conformance), the verifier, [`design/canonical-encoding.md`](design/canonical-encoding.md)
**Resolution:** Three artifacts, all shipped. (1) The deterministic seeded mutation fuzzer `CorpusMutationFuzzTest` over every corpus program — eight mutation operators, fixed seed, invariant: every mutant either rejects with a structured `IngestError`/`VerifyError` or, if admitted, evaluates under `DEFAULTS` limits to a `Value` or structured `InterpretError`; any raw `Throwable` fails. Validated clean at 1000 iterations per program; seven defect classes found and fixed at the ingest/interpreter boundary with triggers preserved, plus one canonical-encoder gap fixed after the independence witness shipped. (2) The curated [`corpus/negative/`](corpus/negative/README.md) of 26 near-miss programs with expected error families (un-witnessed `VerifyError` families, hostile ingest shapes, every fuzzer find), driven by `CorpusNegativeTest`. (3) The independent canonical encoder in stock Python ([`evaluation/conformance/`](evaluation/conformance/README.md), vendored CC0 BLAKE3 reference implementation) written from `design/canonical-encoding.md` alone — never from the Kotlin source — which reproduced all 87 golden root hashes on the first complete run with zero specification corrections, discharging Q-052's second-implementation validation at the encoding layer ahead of the Rust VM. Hostile Layer A / Layer F text fuzzing, coverage-guided fuzzing, and a stronger admitted-mutant oracle remain deferred per the proposal.

Every test in the suite is spec-aligned golden path. The verifier is the entire admission boundary the Q-044 harm bound rests on, and no adversarial input has ever exercised it: no fuzzed graph mutations, no malformed dag-json corpus, no hostile Layer A. A fuzzing harness (random structural mutation over corpus programs with the invariant that every mutant either verifies and evaluates within limits or fails with a structured error — never a raw exception, hang, or unsound admission), a curated negative corpus of near-miss programs, and property checks (verify-then-rehash stability, translate round-trips under mutation) would convert the soundness argument's spot-check witnesses into systematic ones. A related cheap assurance under the same identifier: a minimal independent canonical encoder — a few hundred lines in any second language recomputing the golden hashes from dag-json — would discharge Q-052's second-implementation validation early, without waiting for the Rust VM.

**Resolution:** Conservative additive versioning. Node category IDs are stable; new categories receive higher numbers; existing IDs never reused. Schema changes are new category IDs, not modifications of existing ones. Effect categories extend in the same pattern. ### Q-034: Authoring-layer design for efficient LLM emission {#Q-034}

**Status:** Resolved at static-cost level; dynamic-cost validation remains Phase 1 follow-up (full four-layer emission stack landed 2026-05-24, Layer A density v1 through v4 landed 2026-05-25)
**Concerns:** [`00-motivation.md`](00-motivation.md), [`decisions/ADR-001-graph-not-text.md`](decisions/ADR-001-graph-not-text.md), [`decisions/ADR-002-no-human-projection.md`](decisions/ADR-002-no-human-projection.md), [`design/node-algebra.md`](design/node-algebra.md), [`research-plan.md`](research-plan.md)
**Resolution:** A four-layer emission stack sitting upstream of the verifier: a compact text projection (Layer A) the LLM emits, grammar-constrained decoding (Layer B) that masks invalid emissions at decode time, bidirectional elaboration (Layer C) that recovers derivable type and effect annotations, and the existing canonical dag-json + verifier (Layer D) unchanged. Tool-call assembly is an alternative interaction interface that maps to the same Layer C elaboration. Tokenizer alignment is recognized as Phase 4 follow-up. Estimated compounded token-cost savings of 3-8× over canonical dag-json, projected to bring Strand within 1.3× of conventional-language baselines on the Q-021 evaluation suite. Detailed proposal in [`proposals/implemented/llm-authoring-layer.md`](proposals/implemented/llm-authoring-layer.md).

The full stack has shipped in the Kotlin/JVM reference implementation. Layer A is a 51-code grammar (the original 42 codes from step 1 plus nine additional codes added during the density work for the IF / WHEN / inline-PFV-list / compact-LAM / nested-expression sugars). Layer B emits GBNF derived dynamically from `LayerAGrammar.codes` via `ConstraintGrammar` and is exposed through the `strand grammar` CLI command. Layer C elaboration is always-on as of the 2026-05-25 cleanup pass that removed the explicit-only translator path; eleven inference cases ship, the four original cases from §5.3 of the original proposal (Lambda effects, effectInstances defaulting, Application typeArguments, Lambda paramType) plus seven cases added by the density work (recursion-slot paramType, FunctionType synthesis, SumCaseSchema caseType from SumValue, and compact-LAM-param paramType from each of: call sites, builtin signatures, StateMachine transition-function context, Match scrutinee, ProductFieldValue, and ProductGetField). Layer D is unchanged.

The Layer A density follow-up to step 1 layered nine grammar sugars and the v4 nested-expression form on top of the base Layer A grammar: implicit prelude (well-known type and builtin shorthands), inline literals at argument positions, auto-VarRef binding for unambiguous PRC-binder references, IF as Match-on-Bool sugar, compact Lambda parameter declarations, inline literal patterns, anonymous `_` declarations addressable through `@last`, inline `[k=v ...]` ProductFieldValue list form, WHEN as constructor-pattern sugar, and nested expressions inside argument positions. The combined ten-slice progression cuts the three-task evaluation suite geomean from 2.28× Python+type-hints (Layer A baseline) to 0.81× Python+type-hints (per-task: factorial 0.87×, json-value 0.81×, toggle-machine 0.76×). All ten increments preserved the canonical CBOR encoding and verifier behavior — the work lives entirely in `impl-kotlin/authoring/` and its corpus fixtures. Detailed implementation note in [`proposals/implemented/layer-a-density.md`](proposals/implemented/layer-a-density.md).

The measured 0.81× geomean lands below §6's projected floor of 1.30× for stacks without tokenizer alignment, closing the static-cost half of the Q-034 hypothesis. The dynamic-cost half — first-pass verification rate, tokens-per-successful-task across the agent's retry loop, retry-loop economics under verifier feedback — remains Phase 1 follow-up and requires real model-API integration. Tokenizer alignment (§3.3) and tool-call assembly (§3.6) are deliberately deferred; they would compound on the measured static-cost win but are not needed to close the static-cost hypothesis. Bidirectional inference for SchemaType↔T subtyping is also deferred and remains the reason that json-value's compact-LAM param must stay explicitly annotated.

The canonical authoring format — dag-json with full hash references, mandatory type annotations at every function boundary, and explicit effect declarations at every composition site — is verbose at the surface. An LLM emitting it node-by-node likely consumes substantially more tokens than the equivalent program in a conventional source language; informal estimates place the multiplier at roughly 2-5× for non-trivial programs before any tooling intervention. This pressures the AI-first framing in [`00-motivation.md`](00-motivation.md): if generation cost dominates retry cost, the verifier's correctness wins may not pay for themselves on a per-program token basis.

The graph remains the source of truth per [ADR-001](decisions/ADR-001-graph-not-text.md); [ADR-002](decisions/ADR-002-no-human-projection.md) rejects a *human*-readable projection. Neither decision speaks to an authoring layer optimized for LLM emission that compiles to canonical form before reaching the verifier. The question is what that authoring layer is and how much of the verbosity it can absorb.

Several candidate techniques are recognized, none yet adopted or proposed as the resolution.

**Authoring-layer projection.** A compact serialization (symbolic builtin references, operator-like sugar, positional encoding) that tooling expands to canonical dag-json. Distinct from a human-readable projection in audience and intent.

**Inference passes on the authoring layer.** Type inference and effect propagation that fill in derivable annotations before the graph reaches the verifier. The verifier still sees a fully-annotated graph; the LLM omits what the tooling can recover.

**Tokenizer alignment.** Domain-specific tokenizers that treat node category tags, edge labels, common builtin target strings, and base-N hash digests as single tokens.

**Constrained generation.** Grammar-driven decoding against the closed inventory of node categories and per-category edge schemas, reducing the model's commitment cost at each position.

**Session-scoped handles.** Short local identifiers for recently-introduced nodes within an authoring session, resolved to canonical hashes at commit.

**Tool-call assembly.** The LLM constructs the graph through tool invocations rather than serialized output, permitting incremental validation and shorter per-step output.

Resolution requires a working verifier and an agent generating against it. Meaningful evaluation pairs candidate techniques with measured tokens-per-successful-task across a representative task suite, against both raw canonical emission and the conventional-language baselines named in [Q-021](#Q-021). The static-cost half has been settled: Layer A density v4 measures at 0.81× Python+type-hints geomean across the three-task MVP, below the §6 1.30× projection floor for stacks without tokenizer alignment. The dynamic-cost half — first-pass verification rate, tokens-per-successful-task across the retry loop — remains Phase 1 follow-up under the framework tracked in [Q-021](#Q-021).

### Q-036: Reverse projection from canonical dag-json to Layer A {#Q-036}

**Status:** Resolved (implemented 2026-05-25 across five git commits per the proposal's §9 shipping order; proposal moved to [`proposals/implemented/layer-a-reverse-projection.md`](proposals/implemented/layer-a-reverse-projection.md))
**Concerns:** [Q-021](#Q-021), [Q-034](#Q-034), [`proposals/implemented/llm-authoring-layer.md`](proposals/implemented/llm-authoring-layer.md), [`proposals/implemented/layer-a-density.md`](proposals/implemented/layer-a-density.md), [`decisions/ADR-001-graph-not-text.md`](decisions/ADR-001-graph-not-text.md), [`decisions/ADR-002-no-human-projection.md`](decisions/ADR-002-no-human-projection.md), [`decisions/ADR-003-content-addressing.md`](decisions/ADR-003-content-addressing.md)
**Resolution:** A two-stage projection pipeline (`LayerATranslator` walks the canonical dag-json bottom-up producing a `LayerADocument` IR with density sugars applied in preference order; `LayerARenderer` formats the IR as Layer A text deterministically) plus a hybrid elaboration-omission strategy (static SAFE rule for recursion-slot `paramType`; probe-and-fallback for the BORDERLINE cases that re-runs the Elaborator to verify per-field omissions; static UNSAFE rule for `paramType` resolving to a `SchemaType<T>` node). The 10 density-v4 sugars (implicit prelude, IF/Match-on-Bool, WHEN/constructor-pattern, compact LAM params, inline literals, auto-VarRef, inline ProductFieldValue list, nested expressions, anonymous `_` with @last, plus the Slice 6 inline-literal-pattern path subsumed by Slice 2) all have detectable trigger patterns in canonical dag-json — most mechanical, only WHEN needs `nodeTypes` from the verifier for SumType scrutinee resolution. Correctness invariant: `forward_compile(render(translate(canonical))) == canonical` byte-for-byte, asserted by `LayerAReverseRoundTripTest` against all 64 canonical corpus programs. Three implementation deviations from the original proposal worth recording: (1) the planned standalone `ElaborationOmission.kt` module ships as private methods on `LayerATranslator` (single linear `LayerADocument → LayerADocument` pipeline kept the data flow obvious); (2) `Lambda.effects` was demoted from SAFE to BORDERLINE during Step 2 because corpus programs 12/13/14 legitimately over-declare effects beyond the body's closure (the §4.5 classification-evolution policy fired exactly as written); (3) a `FORCE_ALL_OPTIONALS = setOf("APP")` rule was added that wasn't in the plan — Application's effectInstances defaulting can pick out-of-scope EffectDecls (corpus programs 33-35), so the translator always emits the field explicitly to short-circuit the Elaborator inference (canonical CBOR gates effectInstances on non-empty, so byte equality holds). Original proposal moved to [`proposals/implemented/layer-a-reverse-projection.md`](proposals/implemented/layer-a-reverse-projection.md).

The Q-034 stack closes the forward direction: an LLM emits Layer A density-v4 text → Elaborator + DagJsonEmitter → canonical dag-json → verifier. The reverse direction — canonical dag-json back to Layer A — was a small `LayerATranslator` utility deleted in the 2026-05-25 cleanup pass once it stopped being load-bearing. The deletion was identified as a gap because three workloads need a reverse path: agent modification of existing programs (read existing dag-json, modify, re-emit), few-shot examples in agent prompts (exemplars should be in the same form the model emits, not in canonical dag-json which has 7× the byte cost), and inspection/audit workflows. The deleted translator produced canonical-form Layer A (always MAT, never IF/WHEN; always explicit PRC declarations; every field present), so restoring it as-is would have given the verbose baseline instead of the density-v4 form a model expects. ADR-002 is preserved — Layer A remains a tool-layer LLM-emission/consumption form, not a human-readable projection.

### Q-051: Authoring feedback fidelity — node-id mapping and elaboration gaps {#Q-051}

**Status:** Resolved (implemented 2026-06-10 in the Kotlin/JVM reference implementation)
**Concerns:** [Q-034](#Q-034) (the emission stack), [Q-021](#Q-021) (the retry loop whose economics this governs), CLI, authoring module
**Resolution:** Two mechanisms restore fidelity to the verifier-feedback loop. (1) **Node references in error output resolve to what the agent wrote.** A `NodeRefAnnotator` in the CLI post-processes every rendered `VerifyError` / `InterpretError` / schema-check / warning line, replacing each `#N` that the ingest name map knows with `#N 'authorId'` — extended with `(line L)` for Layer A compiles (`Authoring.compile` now returns a `CompileResult` carrying a `sourceLines` map), `(synthesized '__if0_case_true')` for sugar-expansion nodes, and `(prelude 'intT')` for implicit-prelude nodes. All five subcommand paths (`verify`, `run`, `machine`, `group`, `author`) annotate, so an agent sees `NonExhaustiveMatch(at=#5 'm' (line 8), ...)` rather than a bare integer it must reverse-engineer by counting declaration order. (2) **Elaboration gaps are reported, not silent.** `Elaborator.elaborateWithGaps` runs a post-fixed-point scan: any targeted field still absent after convergence is an attempted-but-failed inference, surfaced as `ElaborationGap(nodeId, field, inferenceCase, reason, line)` records and printed by `strand author` as `elaboration note:` lines only when compilation or verification fails — implementing the `ElaborationGap` policy the Q-034 proposal specified but the implementation had left implicit. Four structural cases: untyped compact-LAM parameters, `ParameterDecl`s missing `paramType`, omitted `SCS` caseTypes with payload-bearing `SumValue` usages, and `FIX` recursionTypes referencing undeclared unsynthesized names.

Previously NodeIds were raw ingest indices with no rendered mapping back to Layer A — the author-id map existed at ingest and was discarded by the CLI — and the dynamic-evaluation record shows retry exhaustion concentrated exactly where errors landed on sugar-synthesized nodes the agent never wrote; the elaborator's give-ups produced downstream errors with no signal that inference was the component that declined or what annotation would unblock it. Identified by the 2026-06-10 independent review. Deferred under this identifier: richer synthesized-node provenance (pointing at the originating sugar line rather than the synthetic id), machine-readable structured error output for harness consumers, and warning annotation on the `machine`/`group` paths.

### Q-058: Persistent local store and run-by-hash {#Q-058}

**Status:** Resolved (implemented 2026-06-13 in the Kotlin/JVM reference implementation)
**Concerns:** [`decisions/ADR-003-content-addressing.md`](decisions/ADR-003-content-addressing.md), [`proposals/implemented/persistent-store.md`](proposals/implemented/persistent-store.md), [Q-043](#Q-043) (whose persistent-cache deferral is the narrow form of this), [Q-024](#Q-024) (versioning, which becomes load-bearing once graphs persist), [Q-054](#Q-054) (the `StrandRuntime` facade run-by-hash extends), [Q-063](#Q-063) (the bundled prelude module the registry resolves against), hashing module, CLI

The content-addressed store is an in-memory map per CLI invocation. Every run re-ingests, re-hashes, and re-verifies the authored JSON from scratch; nothing survives process exit. Across runs, content addressing therefore buys none of its advertised operational properties: there is no admit-once/run-by-hash workflow, no dedup across programs, no caching of verification verdicts, and `strand registry resolve` returns a hash that nothing can dereference without a hand-passed `--peer-store` file — the registry is half of a mechanism. The unit of operation remains a file path, as in a scripting language, except the file is by design not human-readable, which makes the absence of a store-backed workflow more costly than it would be elsewhere.

Q-043 deferred persistent caching of resolver fetches; this question covers the broader substrate: an on-disk hash-keyed store with a defined layout, admit-and-verify-once semantics with recorded verdicts, run/verify/machine/group by root hash, and registry integration so a resolved name dereferences against the local store. The store design should record the format version per ADR-003's multi-hash discipline, at which point the Q-024 migration story carries real weight.

### Q-026: Blessed output library set {#Q-026}

**Status:** Proposed (three of six libraries shipped — JSON in Layer 7 step 1.5 (2026-05-24); PlainTextDocument + NonEmptyText and MarkdownDocument + NonEmptyMarkdown landed alongside in [`proposals/implemented/plaintext-and-markdown-libraries.md`](proposals/implemented/plaintext-and-markdown-libraries.md), 2026-05-24. **Resolution:** Six schemas in the reference distribution: HTML5 (with `Html5Document`, `Html5AccessibleAA`, `Html5StrictCSP` layered variants), SVG (`SvgDocument`), JSON (`JsonValue` + `UniqueKeyJsonObject` — **shipped**, see [`proposals/implemented/json-blessed-library.md`](proposals/implemented/json-blessed-library.md)), PDF (`PdfDocument` targeting PDF/A-2u), plain text (`PlainTextDocument`), and Markdown (`MarkdownDocument`). Nested-μ for arbitrarily-nested JSON is a separate Q-NNN-worthy open question.

Which structured output formats are included as blessed schemas in the reference distribution affects what agents can rely on as available without additional library configuration. Including too few leaves agents working with raw `Bytes` for common formats; including too many ties the language distribution to format curation and audit. The selection criteria and the initial set have been specified; the boundary may move as the ecosystem develops.

### Q-028: Cross-library invariant composition {#Q-028}

**Status:** Deferred — tool-assisted conflict diagnosis is a future tooling direction
**Deferred until:** Phase 4 (tooling and ecosystem). Reason: the verifier already checks all invariants from all claimed schemas; the only thing missing is *diagnostic* tooling that identifies which invariants are in tension when construction fails repeatedly. That diagnosis tool is Phase 4 work (alongside Q-023's graph-editor tooling), not core language design. The current "agent's construction loop observes the conflict by failing to construct any concrete value" behavior is acceptable until production workloads demand the diagnostic.
**Concerns:** [`design/rendering-and-views.md`](design/rendering-and-views.md)
**Partial resolution:** When multiple schemas apply to the same value, the verifier checks all invariants from all claimed schemas. Conflicting invariants (whose conjunction is unsatisfiable) are not detected by the verifier as such; the construction loop observes the conflict by failing to construct any concrete value. Future work may add diagnostic tooling that identifies which invariants are in tension when construction fails repeatedly. Documented in [`design/rendering-and-views.md`](design/rendering-and-views.md).

Cross-library composition is necessary for organizations that layer custom invariants on top of standard schemas. The current design relies on the verifier being a sound checker and on the agent to choose compatible schemas; whether stronger tool-assisted conflict diagnosis should be part of the language is open.

### Q-030: Effect handler algebra and runtime semantics {#Q-030}

**Status:** Resolved (implemented in Layer 3 step 3 of the Kotlin/JVM reference implementation, 2026-05-23)
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md) § Effect handlers, [`decisions/ADR-004-effects-as-edges.md`](decisions/ADR-004-effects-as-edges.md)
**Resolution:** A `Handler` node category (N-043) intercepts a specified effect category within its body expression and invokes a handler function with the intercepted call's arguments, replacing the call's result with the handler's return value. Restricted to the **no-continuation** form (the handler is just a function, no `resume`, no captured continuation, no abort), which covers test-mocking and effect-redirection without requiring CPS transformation in the tree-walking interpreter. The key novel verifier rule is the effect-closure subtraction `closureOf(handler) = (closureOf(body) - {intercept}) ∪ closureOf(handle) ∪ <handle function's declared effects>` — `Handler` is the only node category that *removes* effects from a closure (`CapabilityScope` narrows the runtime context but does not change the static closure). Verifier additionally enforces signature agreement: every intercepted Application's value-argument and result types must structurally equal the handler's, and the handler must be monomorphic (a `Forall`-typed handle is rejected as `HandlerOverPolymorphicHandle`). Runtime dispatch threads an active-handler stack alongside the capability context; `findLast` selects the innermost handler, matching the lexical-scope reading of nested Handlers. Multi-shot continuations, one-shot continuations, re-raise, and abort-only handlers remain deferred as separate follow-up slices that this design does not foreclose. Original proposal moved to [`proposals/implemented/effect-handlers.md`](proposals/implemented/effect-handlers.md).

`effects-and-capabilities.md` § Effect handlers originally described handlers in prose ("the Handler's body executes; when the body performs an effect that matches the handler's category, control transfers to the handler's `handle` clause...") without pinning the node algebra, closure rule, or interpreter dispatch. ADR-004 § Consequences explicitly deferred the semantics to that document; § Effect handlers has been expanded to carry the full algebra.

### Q-031: Refinement-lattice capability matching {#Q-031}

**Status:** Resolved (implemented in Layer 3 step 2 of the Kotlin/JVM reference implementation, 2026-05-23)
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md) § Effect closure semantics, § Capability mechanism, § Confused deputy mitigation; [`decisions/ADR-004-effects-as-edges.md`](decisions/ADR-004-effects-as-edges.md); Q-003, Q-005
**Resolution:** `EffectDecl` (N-022) is load-bearing at the call site via a new `Application.effectInstances: List<EffectDecl>` edge that supplies concrete parameter values for the called function's declared effects. The runtime's `Set<EffectCategory NodeId>` capability context is replaced with a structured `CapabilitySet(grants: Map<NodeId, List<CapabilityPattern>>)` where each pattern has `Wildcard | Concrete(Value)` per parameter slot. Matching algorithm: a capability covers a requirement iff each capability slot covers the corresponding requirement slot (wildcard covers anything, concrete covers by value equality). New runtime error `RefinementViolation` is distinguished from `CapabilityViolation` so policy authors see which kind of denial happened. The refinement check fires only for categories with an explicit EffectDecl at the call site; categories declared by the callee but absent from `effectInstances` pass the check after the category-presence check (so a caller forwarding a capability down the chain is not denied at its own call). Confused-deputy mitigation (Q-005) is enabled by parameter-tagged capabilities falling out of this design. The pre-Q-031 `Interpreter.eval(root, Set<NodeId>)` API is preserved as a thin wrapper over `CapabilitySet.ofCategories(...)`. Sub-string and glob wildcards on strings remain deferred; refinement-narrowing on `CapabilityScope` remains deferred behind a separate follow-up question. Original proposal moved to [`proposals/implemented/refinement-lattice-capability-matching.md`](proposals/implemented/refinement-lattice-capability-matching.md).

Today's (Layer 3 step 1) capability matching was by `EffectCategory` NodeId identity only. The design corpus (`design/effects-and-capabilities.md` § Effect closure semantics) called for matching by parameter refinement (`Network.Connect{host: *, port: 443}` covering `Network.Connect{host: "api.com", port: 443}`). Layer 3 step 2 closes that gap end-to-end.

### Q-032: State machine runtime architecture and shipping strategy {#Q-032}

**Status:** Resolved as a three-step strategy; step 1 implemented (Layer 6 step 1 of the Kotlin/JVM reference implementation, 2026-05-24). Steps 2 and 3 remain to be drafted as separate proposals when implementation begins; the high-throughput engineering question they address is tracked under Q-008.
**Concerns:** [`design/state-machines.md`](design/state-machines.md), [`decisions/ADR-007-state-machines.md`](decisions/ADR-007-state-machines.md), [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md) § State machine effects, [`design/distribution-model.md`](design/distribution-model.md), Q-008, Q-009, Q-010
**Resolution:** A three-step shipping strategy for Layer 6. Step 1 is a deterministic synchronous trace runtime: `runMachine(machine, events): Trace` drives a single-input-stream machine over a supplied event list in the calling thread. The interpreter remains synchronous; the runtime is a pure fold; replay determinism is guaranteed by construction. Step 1 shipped in the Kotlin/JVM reference implementation 2026-05-24 (`impl-kotlin/runtime/`), with five corpus programs (41-toggle-machine through 45-bank-account-machine), an OutputBatch positional convention (field name `output_i`), and a cached transition-function closure at instance start. Step 2 introduces per-machine Kotlin coroutine actors with channel-based input/output streams, multi-stream FIFO+nondeterministic-merge, and inter-machine wiring; the transition function stays synchronous (T is pure by spec), only the actor loop suspends. Step 3 adds bounded queues with overflow policies (per Q-015), supervisor patterns as a corpus idiom (per ADR-007 — supervisors are not a new node category), and snapshot/replay-from-log persistence. Hot upgrade (Q-010) remains deferred. The deterministic trace API from step 1 survives forever as the debugging and training-corpus-generation interface that step 2 wraps with async I/O. Detailed proposal in [`proposals/implemented/state-machines-runtime.md`](proposals/implemented/state-machines-runtime.md).

ADR-007 calls out the runtime engineering as "substantial and not solved by this ADR" and points at Q-008 as the open implementation problem with BEAM as the architectural baseline. This question extends Q-008 with a concrete step-by-step plan; step 1 is now executed, steps 2 and 3 remain — they address the high-throughput multi-machine engineering Q-008 calls out, which remains Open until step 2 lands.

### Q-033: State machines step 2 — async multi-machine actor runtime {#Q-033}

**Status:** Resolved (implemented in Layer 6 step 2 of the Kotlin/JVM reference implementation, 2026-05-24)
**Concerns:** [`design/state-machines.md`](design/state-machines.md), [`decisions/ADR-007-state-machines.md`](decisions/ADR-007-state-machines.md), [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md) § State machine effects (E-028..E-031), [`design/distribution-model.md`](design/distribution-model.md), Q-008, Q-009, Q-032
**Resolution:** A per-machine Kotlin coroutine actor model running on a shared dispatcher. Each `MachineInstance` runs in its own `launch { }` coroutine; input streams become `Channel<Value>` of bounded capacity (default 1024); the actor loop uses Kotlin's `select` over the machine's input channels to implement FIFO-per-stream + nondeterministic merge (Q-009's default). Multi-input machines see events wrapped in a runtime-synthesized tagged-Event sum (`InputEvent = stream_0(T₁) | stream_1(T₂) | ...`); multi-output machines return `(State, List<TaggedOutput>)` using recursive types (N-041/N-042). Inter-machine wiring is structural — EventStreams declared `streamKind: internal` are shared `Channel<Value>` instances between the producing and consuming machines, validated by new verifier rules (single-producer, no-orphan). Implicit `StateMachine.Send`/`Receive` effects (E-028, E-029) propagate through the verifier; the machine's declared `effects` must cover them. Supervisor patterns are state machines (no new node category); step 2 ships a one-for-one restarter as a corpus capstone, with E-030/E-031 spawn/terminate effects wired. The interpreter stays synchronous (transitions are pure); only the actor loop suspends. Step 1's `runMachine(machine, events): Trace` survives unchanged as the deterministic-replay seam — async runs record their consumed events via a per-instance recorder, then replay through `runMachine` for trace-equality assertions. Three deviations from the literal proposal worth recording: (1) the new internal-stream topology rules listed in the proposal's § 5 ship as **runtime-side** `MachineGroupValidationError` variants rather than verifier rules, because the per-machine verifier reasons about one StateMachine at a time and cannot reason across cross-machine stream connections; promoting these to true verifier rules would require a new "GroupVerifier" pass; (2) the implicit `StateMachine.Send` / `Receive` effects (E-028/E-029) remain runtime-internal and unenforced by the verifier, deferred to step 3 along with a registration mechanism for "well-known" EffectCategory nodes; (3) the supervisor corpus program (48) implements the proposal's § 6.6 observational supervisor framing (multi-input merge wired via internal streams) rather than the § 7 spawn-and-restart framing, which needs real dynamic spawn/terminate via E-030/E-031 and lands in step 3. Original proposal moved to [`proposals/implemented/state-machines-runtime-step-2.md`](proposals/implemented/state-machines-runtime-step-2.md).

Deferred to step 3 or later: bounded-queue overflow policies beyond block-producer, multi-producer fan-in and broadcast fan-out on internal streams, supervisor restart policies beyond one-for-one with real spawn/terminate via E-030/E-031, snapshot/replay-from-log persistence, priority/causal/timestamp merges (Q-009 alternatives), implicit StateMachine.Send/Receive verifier enforcement via a well-known-EffectCategory registration mechanism, distributed execution. Hot upgrade (Q-010) remains a separate question entirely.

Initial categories: E-035 LLM.Generate (parameters: `provider: String, model: String`) and E-036 LLM.Embed (same parameters). ### Q-039: EffectDecl–argument coupling at foreign call sites {#Q-039}

**Status:** Resolved (Kotlin/JVM reference implementation, 2026-05-27; proposal moved to [`proposals/implemented/foreign-effect-projections.md`](proposals/implemented/foreign-effect-projections.md))
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md), [`design/security-model.md`](design/security-model.md), [`decisions/ADR-004-effects-as-edges.md`](decisions/ADR-004-effects-as-edges.md), [`decisions/ADR-005-foreign-nodes.md`](decisions/ADR-005-foreign-nodes.md), Q-005 (confused deputy mitigation), Q-031 (refinement-lattice capability matching), [`security-index.md`](security-index.md) § Finding 1
**Resolution:** Optional `effectProjections: List<EffectProjection>` content on `ForeignNode` and `FunctionType`. Each `EffectProjection` carries an `EffectCategory` NodeId plus a positional list of `ProjectionSource`s — either `ArgRef(index: Int)` referencing one of the function's positional arguments or `LiteralNode(target: NodeId)` referencing a binding-controlled literal node. The verifier enforces at admission that projection arity matches the category's parameter count, that `ArgRef` indices are in range, and that `LiteralNode` targets are literal nodes of the right type. At every `Application` of a projected function whose `effectInstances` is non-empty, the verifier requires the parameter expressions to match the projection structurally — `ArgRef(j)` source requires the same NodeId as `Application.arguments[j]`, `LiteralNode(t)` source requires a literal node whose canonical-form bytes equal `t`'s. The runtime synthesizes capability-check parameter values directly from the projection plus the actual evaluated arguments, eliminating drift between the value used for the capability check and the value the foreign code consumes. ForeignNodes without `effectProjections` continue under the current Q-031 semantics (with the security gap documented in `security-index.md`). Initial migration slice covers six prelude entries: `fsRead`, `fsWrite`, `fsAppend`, `fsExists`, `fsDelete` (each pinning the path refinement to `ArgRef(0)`), and `netConnect` (pinning host/port to `ArgRef(0)`/`ArgRef(1)`). Per-provider LLM/Vector bindings, `Crypto.RandomBytes`, `Http.Request`, `Process.Spawn`, and `Crypto.Sign/Encrypt/Decrypt` were deferred to follow-up slices — the LLM/Vector migration needs a signature redesign to surface `model`/`store` as positional arguments; `Crypto.RandomBytes` needs an EffectCategory parameter refresh; `Http.Request` is paired with the Q-041 sandboxing redesign. No new node category — projections are inline metadata. Detailed proposal and implementation note in [`proposals/implemented/foreign-effect-projections.md`](proposals/implemented/foreign-effect-projections.md).

The Q-031 proposal text explicitly noted that EffectDecl parameter expressions "are typically VarRefs into the application's arguments ... but may be any expression of the right type" — the proposal allowed unrestricted EffectDecl parameter expressions for flexibility. The 2026-05-26 audit of the Kotlin reference implementation surfaced that this flexibility translates into a confused-deputy attack at the implementation level: an agent can author an EffectDecl whose evaluated parameter value matches a granted refinement pattern while passing entirely different values to the function being called. The capability check passes; the foreign code performs the unauthorized operation. The proposal closes the gap at the binding layer (ForeignNode is the security boundary; every effect eventually reaches a foreign call), restoring the parameter-tagged-capability property promised by Q-005 and `security-model.md` § Confused deputy synthesis.

### Q-040: Interpreter resource limits and DoS resistance {#Q-040}

**Status:** Resolved (implemented 2026-05-27 in the Kotlin/JVM reference implementation; proposal in [`proposals/implemented/interpreter-resource-limits.md`](proposals/implemented/interpreter-resource-limits.md))
**Concerns:** [`design/security-model.md`](design/security-model.md), [`security-index.md`](security-index.md) § Finding 2
**Resolution:** Introduce a unified host-configured `EvaluationLimits` data class honored at admission (JSON ingest depth cap, total node count, total ingest bytes) and at evaluation (step counter / fuel, stack-depth bound, allocated-value count, optional wall-clock budget). Limits flow through the runtime API alongside `CapabilitySet`: `Interpreter.eval`, `Vm.evaluate`, and `StateMachineRuntime.runMachine` / `runGroup` each accept the new `EvaluationLimits` argument with sane defaults. Both evaluators (tree-walking `Interpreter` and bytecode `Vm`) honor the same limits — a program that succeeds under one but exhausts limits under the other is a cross-backend equivalence violation. Breaches surface as a new `InterpretError.ResourceExhaustion(kind, atNode?, current, limit)` sealed variant (with the bytecode VM accepting `atNode = null` until source-mapping lands in a separate slice). Ingest breaches surface as a parallel `IngestError.ResourceExhaustion`. Default values target the seed-corpus envelope (every existing program runs unchanged under defaults); production deployments tighten via host configuration; benchmarking harnesses relax. The verifier is not the enforcement point (verifier is statically deterministic; limits are runtime policy). State-machine runtimes inherit per-evaluation budgeting from the underlying `Interpreter` / `Vm` rather than a separate per-event budget — multi-event runs treat the entire trace as one logical evaluation. No new node category, ADR, or effect-category identifier required — limits are runtime policy, encoded as host-side parameters. Detailed proposal in [`proposals/implemented/interpreter-resource-limits.md`](proposals/implemented/interpreter-resource-limits.md).

A language whose primary author is an AI agent that may misgenerate must distinguish hostile graphs (or accidentally-broken graphs) from accidental crashes. The 2026-05-26 audit observed concrete attack shapes: deeply-nested JSON crashing `kotlinx.serialization.json` with `StackOverflowError` before any Strand code runs; a Fixpoint whose body is `λ rec x. rec(x)` exhausting the JVM stack through `eval → applyCall → applyFixpoint → eval`; a productive-non-termination Fixpoint that always advances state and runs indefinitely without language-level error. The verifier accepts these graphs (they are well-formed); the host process dies or hangs. The proposal restores the property that every Strand evaluation either succeeds, returns a structured language-level error (including `ResourceExhaustion`), or is cancelled by the host — never crashes the host process.

### Q-041: I/O builtin sandboxing — SSRF and path traversal {#Q-041}

**Status:** Resolved (implemented 2026-05-27 in the Kotlin/JVM reference implementation; proposal moved to [`proposals/implemented/io-builtin-sandboxing.md`](proposals/implemented/io-builtin-sandboxing.md))
**Concerns:** [`design/security-model.md`](design/security-model.md) § Foreign binding trust, [`decisions/ADR-005-foreign-nodes.md`](decisions/ADR-005-foreign-nodes.md), Q-006 (binding trust model), Q-039 (foreign effect projections), [`security-index.md`](security-index.md) § Finding 3
**Resolution:** A host-configured `SandboxPolicy(fs: FsPolicy, net: NetPolicy)` sits alongside `CapabilitySet` in the runtime context and constrains the actual argument values admitted at foreign-call boundaries inside `Fs.*`, `Net.Connect`, and the redesigned `Http.Request`. `FsPolicy(workspaceRoot, escape: Allow|Deny, followSymlinks: Bool)` defaults to a workspace-rooted sandbox: all `Fs.*` paths are canonicalized and rejected if the resolved path escapes the configured root (via `..`, absolute paths, or symbolic-link redirection). `NetPolicy(defaultDeny, allowedHosts, blockedRanges)` defaults to default-deny on loopback, RFC1918, link-local, multicast, broadcast, IPv6 ULA, and cloud-metadata endpoints (`169.254.169.254`, `metadata.google.internal`, `metadata.azure.com`, Alibaba `100.100.100.200`); optional allowlist of outbound destinations narrows further (e.g., `*.example.com`, `api.openai.com`). DNS rebinding is mitigated by `PinAtCheck` default — resolve once during policy check, pass the resolved IP to the JVM connect call so the second resolution cannot subvert the check; stricter `RecheckAtConnect` and `RequireIpLiteral` modes are opt-in. Breaches surface as a new `InterpretError.SandboxViolation` sealed variant so agents see recoverable feedback. `Http.Request` is redesigned: the new binding takes `(host, port, scheme, path, method, headers, body)` as positional arguments so Q-039's projection vocabulary binds host/port directly to `ArgRef(0)` and `ArgRef(1)`; the legacy single-URL form is preserved as a `Http.RequestFromUrl(url, ...)` convenience wrapper that parses and forwards. This is explicit defense-in-depth complementing Q-039: Q-039 binds capability-check values to actual function arguments (closing the EffectDecl spoofing attack); Q-041 independently constrains what those argument values are allowed to be (closing the orthogonal "capability genuinely permits but argument is out-of-policy" attack). The policy is host-configured, not graph-authored — sandbox decisions live in the runtime trust boundary per ADR-005, never in the Strand graph itself. Detailed implementation note plus five recorded deviations in [`proposals/implemented/io-builtin-sandboxing.md`](proposals/implemented/io-builtin-sandboxing.md).

The Layer 4 step 2 builtin slice wired real OS calls into the interpreter without sandbox observation — `Fs.Write` passes paths to `java.nio.file.Paths.get(path)`, `Net.Connect` accepts any `(host, port)`, `Http.Request` accepts any URL through `URI.toURL().openConnection()`. Programs with wildcard capabilities (`--grant-all` demo mode, permissive policies, legacy non-projected ForeignNodes) have unrestricted OS reach: SSRF to cloud-metadata endpoints exposes IAM credentials; path traversal reads `/etc/shadow`; loopback access reaches in-process Redis or other unauthenticated services. The proposal restores the runtime sandbox observation defence layer that [`design/security-model.md`](design/security-model.md) § Foreign binding trust enumerates as one of the four mechanisms for the Q-006 trust model, while leaving the WebAssembly / seccomp full-isolation work (Milestone 2.4) as the deeper future direction.

### Q-042: Credential isolation and error redaction {#Q-042}

**Status:** Resolved (implemented 2026-05-27 in the Kotlin/JVM reference implementation; proposal moved to [`proposals/implemented/credential-isolation.md`](proposals/implemented/credential-isolation.md))
**Concerns:** [`design/security-model.md`](design/security-model.md), [`decisions/ADR-005-foreign-nodes.md`](decisions/ADR-005-foreign-nodes.md), [`proposals/implemented/agent-native-capabilities.md`](proposals/implemented/agent-native-capabilities.md) § 4.4, [`proposals/implemented/agent-native-vector-stores.md`](proposals/implemented/agent-native-vector-stores.md) § 4.2, Q-040 (interpreter resource limits — provides the `EvaluationLimits` carrier), [`security-index.md`](security-index.md) § Finding 4
**Resolution:** Three coordinated mechanisms. (1) A `Credential` wrapper type returned by `CredentialProvider.resolve` (previously `String?`). `Credential.toString` returns `[REDACTED:<provider>:<key>]`; `equals`/`hashCode` are reference-identity; the raw String is reachable only through an explicit `reveal()` method whose call sites are auditable via `git grep`. (2) A process-global `CredentialScrubber` singleton registers every credential value minted by `CredentialProvider.resolve` and scrubs every `IoFailure(kind, detail)` construction by replacing literal occurrences of any active credential with its `[REDACTED]` placeholder. The scrub runs unconditionally at construction; per-provider files (Anthropic, OpenAI, Gemini, Pinecone, Chroma) benefit automatically without per-site changes. (3) A host-configurable `ErrorVerbosity` enum (`Redacted` default, `Full` opt-in for dev/debug with a runtime warning, `RedactedWithKindOnly` for maximum suppression) lives on the `EvaluationLimits` data class from Q-040, threaded through the `InterpretError.IoFailure` materialisation in `applyForeign`. The combination addresses the three concrete leakage paths surfaced by the audit: upstream response bodies echoed verbatim in `IoFailure.detail`, JVM `IOException.message` embedding URL credentials, and the absence of any compiler-enforced barrier between a credential `String` and any other `String`. Pattern-based scrubbing (Bearer / sk- / x-api-key regex), heap-clearing on rotation, certificate pinning, audit logging of credential reads, and subprocess-environment filtering for `Process.Spawn` are deferred to follow-ups; the proposal documents their hooks. No new node category, ADR, or effect-category identifier required — credential handling is runtime policy, not graph well-formedness. Detailed implementation note plus six recorded deviations in [`proposals/implemented/credential-isolation.md`](proposals/implemented/credential-isolation.md).

The Q-037 / Q-038 Phase 1 work documented the credential-provider design carefully (credentials are not capabilities; keys live in the execution environment, not the content-addressed graph) but the runtime implementation passed credential values through bare `String?` types without isolation or scrubbing. The 2026-05-26 audit observed that an HTTP 401 from an upstream Anthropic-compatible proxy that echoes the request's `x-api-key` header in its error body produces an `InterpretError.IoFailure` whose `detail` field carries the raw API key — exposed to whatever logging or telemetry consumes the runtime's error stream. The proposal restores the property promised by the Q-037 § 4.4 design: credentials are operational secrets, not data the agent or its observers see.

**Resolution:** Two coordinated mechanisms in Layer 2 step 3. (1) A `NodeResolver` interface composed in a chain (`LocalHashStoreResolver`, `ChainedResolver`, `FileSystemResolver`, `CachingResolver`) plus an off-graph `NameRegistry` JSON file mapping human names to hashes; NodeRef resolution falls through the chain on cache miss; integrity enforced by recomputing the canonical hash of every fetched node. (2) **A new node category N-046 ModuleManifest** — a content-addressed grouping primitive that bundles exports with aggregate effect declarations. Each manifest export is `(target: Hash, declaredEffects: List<EffectCategory>, displayName: String)`; the verifier admits the manifest by checking that each export's declared effects exactly equals the effect surface of the targeted node — the function's declared effect row for a function export, the construction closure for a value export (the implementation clarified that a bare Lambda's closure is empty, so a function export certifies its effect row, not its closure). The current state is that every Strand program is one `NodeStore`, one `nodeIdToHash`, one `hashToNodeId`, all produced by a single `Hasher.finalize` pass over one JSON document; there is no protocol for resolving Hash to Node when the target is not in the local store, and there is no algebra-level primitive for asserting that a collection of exports forms a coherent bundle with aggregate capability claims. The gap is twofold — a runtime extension for cross-store resolution and a node-algebra extension for bundle declarations. The amended ADR-003 explicitly endorses content-addressed grouping primitives as compatible with the no-import-system stance, distinguishing them from conventional modules built on name-based identity and import-path resolution.

### Q-045: Streaming and asynchronous I/O {#Q-045}

**Status:** Resolved (core slice implemented 2026-05-31 in the Kotlin/JVM reference implementation; proposal moved to [`proposals/implemented/streaming-async-io.md`](proposals/implemented/streaming-async-io.md). The deferred actor-runtime bridge, decoded `StreamEvent`s, process/file streaming, streaming send, and TLS/WebSocket streaming remain follow-ups with the unblockers recorded in the proposal § 8.)
**Concerns:** [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md), [`decisions/ADR-004-effects-as-edges.md`](decisions/ADR-004-effects-as-edges.md), [`design/state-machines.md`](design/state-machines.md), [`decisions/ADR-005-foreign-nodes.md`](decisions/ADR-005-foreign-nodes.md), [`proposals/implemented/layer-4-step-2-real-io.md`](proposals/implemented/layer-4-step-2-real-io.md), [`proposals/implemented/agent-native-capabilities.md`](proposals/implemented/agent-native-capabilities.md) § 4.6 (Q-037), Q-040 (resource limits), Q-041 (sandboxing), Q-042 (error redaction)
**Resolution:** A uniform synchronous streaming-handle contract built on the existing `ResourceTable` and `Net.Receive` pattern (demand-driven chunked receive), closing Tier 2 part 3 of the 2026-05-28 roadmap and implementing the Q-037 § 4.6 streaming sketch. Three operations per streaming namespace: an open builtin returns a `Value.Resource` immediately and declares its semantic effect (E-035 `LLM.Generate` for streaming generation; sockets reuse `Net.Connect`/E-001); `<Namespace>.Stream.Receive(handle: Int, maxBytes: Int) -> Option<Bytes>` performs one blocking read returning `Some(chunk)` per chunk or `None` at end-of-stream, declaring E-004 `Network.Receive`; `<Namespace>.Stream.Close(handle: Int) -> Unit` releases the handle (idempotent, no effect). Chunks are raw `Bytes` (a decode layer is deferred — see below); EOF is `Option`'s `None` rather than the legacy empty-bytes sentinel. No new node category, ADR, or effect-category identifier — streaming reuses E-004 and E-035, since the effect closure is a static set (a drain loop contributes the receive category exactly once, regardless of chunk count) and needs no multiplicity construct. The drain declaring E-004 rather than carrying no effect is a settled decision on structural-safety grounds: a no-effect drain would make a stream handle an ambient capability-free network channel (drainable inside a `CapabilityScope` that revoked `Network.Receive`), making the effect closure an unsound bound and breaking the Q-044 harm bound; a streaming-LLM program therefore declares both E-035 (open) and E-004 (drain). A per-read timeout is host policy, not a graph argument: a new `EvaluationLimits.streamReceiveTimeoutMillis` field (Q-040 carrier) is installed as the socket/HTTP read timeout at open so a hostile graph cannot raise its own ceiling, and a timed-out read surfaces as recoverable `InterpretError.IoFailure` (scrubbed per Q-042). The core slice ships LLM streaming generate variants, `LLM.Stream.Receive`/`Close`, and an `Option`-EOF `Net.Stream.Receive` (legacy `Net.Receive` retained for hash stability — in-place migration would rehash its `FunctionType` node; new emissions steered to the Option form via system-prompt docs only, the `Http.Request`/`Http.RequestFromUrl` dual-form precedent). Deferred with concrete unblockers: the state-machine actor-runtime bridge (external streams as event sources via `MachineGroupHandle.externalInputs`, inheriting `OverflowPolicy`/`EventRecorder`/metrics) — built on top of this pull primitive but carrying its own unresolved graph-surface question (how to declare an IO-backed `External` stream), now registered as Q-046; a stateful SSE-event decoder resource (a one-shot parse is insufficient because `Stream.Receive` chunks can split a frame mid-frame) plus a normalized cross-provider `StreamEvent` sum; process/file streaming; streaming send; and TLS/WebSocket streaming. Proposed in [`proposals/streaming-async-io.md`](proposals/streaming-async-io.md).

Strand's real-I/O surface (Layer 4 step 2) is synchronous and one-shot: builtins block and return the complete result, with no way to consume an LLM response or socket as it arrives. The pieces a streaming surface needs already exist but were never composed — `Net.Receive` is a chunked receive in everything but its ambiguous empty-bytes EOF, `ResourceTable` already mints opaque handles with a registered-but-unused `llm_conversation` kind, and Q-037 § 4.6 specifies the LLM streaming path verbatim then defers all of it. A second incremental-delivery mechanism, the state-machine actor runtime, has full backpressure and replay but is intra-process push-based (the runtime delivers events; the machine never pulls) and the interpreter is synchronous with atomic transitions, so external I/O cannot be a blocking pull inside a transition. The gap is a first-class incremental-receive surface for foreign I/O plus an eventual bridge from live external producers into the existing stream runtime. The first half shipped (Q-045 core slice); the bridge is registered as Q-046.

### Q-046: Actor-runtime bridge for IO-backed external event streams {#Q-046}

**Status:** Resolved (landed 2026-06-03 in the Kotlin/JVM reference implementation, core slice; proposal moved to [`proposals/implemented/actor-runtime-stream-bridge.md`](proposals/implemented/actor-runtime-stream-bridge.md)). Deferred within the same identifier: decoded `StreamEvent`s + the SSE framing decoder (which would unlock drop policies on framed streams and a typed `Failure` case), group-level (not just per-instance) recorded replay, multiple bridged streams per machine, streaming send, process-source streaming, and the Layer A `source` grammar.
**Concerns:** [`design/state-machines.md`](design/state-machines.md) (the actor runtime, `External` EventStream, `MachineGroupHandle.externalInputs`, `OverflowPolicy`, `StreamBus`, `EventRecorder`), [`proposals/implemented/streaming-async-io.md`](proposals/implemented/streaming-async-io.md) § 8 (the pull primitive this builds on, and the deferral that names this question), [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md) (E-004 `Network.Receive` vs. the runtime-implicit E-029 `StateMachine.Receive`), Q-044 (the harm bound the soundness argument preserves), Q-045 (the streaming-handle primitive), Q-009 (event ordering / nondeterministic merge — bridged events interleave with other input streams), Q-015 (backpressure — the `External` stream's `OverflowPolicy` governs the feeder), Q-008 (high-throughput communicating machines — the eventual scale target)
**Resolution:** Bind an `External` EventStream to its IO source with a single optional `source` edge on the EventStream node (N-028), pointing at the graph node that opens the stream (an `Application` of `*.CreateStream` or `Net.Connect`); the runtime starts one host-side feeder coroutine per `source`-bound stream at `runGroup`, draining the Q-045 handle on `Dispatchers.IO` and pushing chunks through the stream's existing `OverflowDispatcher`. The four sub-questions resolve as: **graph surface** — a `source: NodeId?` field, additive under ADR-003 (zero existing-hash churn), in-graph and verifier-visible, no new node category (the CLI-bind and separate-binding-node alternatives are rejected in the proposal); **effect accounting** — the binding's transport effects (`open.effects ∪ {E-004 Network.Receive}`) are absorbed into the consuming group's effect closure and checked against `group.capabilities` at group start (a new `MachineGroupValidationError.ExternalStreamSourceEffectUncovered`), so revocation via `CapabilityScope` (N-036) bites exactly as for a direct drain and the Q-044 harm bound stays sound — E-029 stays a capability-free marker, the transport effects are the real gated ones; **replay determinism** — recording stays at the consumer (post-overflow-policy, post-`wrapEvent`), so replay reproduces the machine's experience with zero live IO and never resurrects dropped chunks; **feeder lifecycle** — close-exactly-once via a single `finally` over all exit paths (idempotent `ResourceTable.remove`), cancellation bounded by `streamReceiveTimeoutMillis`, EOF as channel closure, transport failure local per-instance (no in-feeder retry, no group failure). The core slice is raw-`Bytes` events under `BlockProducer`-only backpressure (drop policies corrupt byte streams and are rejected at bind) with per-instance replay; decoded events + SSE framing decoder, group-level replay, multiple bridged streams per machine, streaming send, and process-source streaming are deferred with unblockers. New verifier variants `StreamSourceOnNonExternal` / `StreamSourceNotAnOpener` / `StreamSourceEffectMismatch` / `StreamSourceTypeMismatch` / `ByteStreamSourceRequiresBlockProducer`; no new node category, ADR, or effect-category identifier; every pre-Q-046 program hashes byte-identically (the `source` edge is omitted from the canonical encoding when absent). Implemented in [`proposals/implemented/actor-runtime-stream-bridge.md`](proposals/implemented/actor-runtime-stream-bridge.md) (see its Implementation note for the four recorded deviations, chiefly: group-start coverage is checked by category name; `source` is required to be a direct `Application`; the Layer A `source` grammar is deferred). Verify-only corpus 84 plus the 8-case `BridgedStreamTest` (verifier rules, the adversarial coverage gate, and an end-to-end loopback-socket bridged drain with deterministic replay); full suite 1165 tests green.

The Q-045 core slice delivers a synchronous *pull* surface: a program calls `<Namespace>.Stream.Receive` in a `Fixpoint` loop and blocks the calling thread on each chunk. That fits an agent driving one stream at a time, but the existing state-machine actor runtime (Layer 6) is *push*-based and offers exactly the machinery a multi-stream, replayable, backpressured consumer needs — `select`-based nondeterministic merge across input channels (Q-009 default), per-stream `OverflowPolicy` (Q-015), `StreamBus` fan-in/fan-out, per-instance `EventRecorder` replay, and runtime metrics — but only for events delivered *into* a machine by host Kotlin code via `MachineGroupHandle.externalInputs`. Nothing today reads a live socket or LLM stream into an `External` EventStream. The bridge is a host-side coroutine that drains a Q-045 streaming handle (`Stream.Receive` in a loop) and feeds each chunk onto an `External` stream's channel, so a machine consumes a network/LLM stream as ordinary events and inherits all of the above for free. The feeder is straightforward; the open question is the *graph surface*.

The unresolved design question is how to declare, at the graph level, that a given `External` EventStream is backed by a specific IO source — today an `External` stream is an untyped ingress point with no statement of provenance. Candidate directions, none adopted:

- A `streamKind`-adjacent binding on `EventStream` naming the IO source (a host-resolved descriptor), parallel to how `ForeignNode.target` names a builtin. Keeps the binding in the graph but reintroduces a host-name-to-graph coupling the content-addressing model otherwise avoids.
- A `ForeignNode` that *produces* a stream — the open builtin (`*.CreateStream`) is referenced from the machine group's wiring rather than called inside a transition, with the runtime starting the feeder at `runGroup`. Reuses the Q-045 opens directly but needs a way to attach a produced handle to a named `External` stream.
- A CLI/host affordance (`strand group --bind-stream <stream>=<source>`) that keeps IO-source binding entirely off-graph, mirroring `--peer-store` and the sandbox policy. Simplest, but the binding is then invisible to the graph and to any static reasoning about where a machine's events originate.

Secondary questions ride along. **Effect accounting:** the bridge performs the E-004 `Network.Receive` reads on the program's behalf outside any transition, so it resembles the runtime-implicit E-029 `StateMachine.Receive` (enforced via the `WellKnownEffect` registry) more than the Q-045 drain, where the program pulls and E-004 surfaces in the value-level closure — which effect a machine consuming a bridged stream must declare, and where the verifier enforces it, is unsettled. **Replay determinism:** unlike the raw handle-drain (Q-045's recorded known limitation — streamed runs are not replayable), a bridged stream inherits `EventRecorder` and becomes replayable, which is one of the strongest motivations for the bridge. **Backpressure and lifecycle:** the feeder coroutine's lifecycle relative to the machine group (start, cancellation, what happens at EOF or transport failure) and how the `External` stream's `OverflowPolicy` throttles a producer the runtime does not control need specification. The question is deferred until multi-stream concurrent consumption is a real workload; taking it up turns the streaming work medium-large (per `streaming-async-io.md` § 8).

### Q-047: Runtime schema enforcement (Layer 7 step 2) {#Q-047}

**Status:** Resolved at the foundational-slice level (landed 2026-06-03 in the Kotlin/JVM reference implementation; proposal moved to [`proposals/implemented/runtime-schema-enforcement.md`](proposals/implemented/runtime-schema-enforcement.md)). The deferred extensions under § 8 — ForeignNode-backed checkers, the HTML5 / SVG / PDF blessed-library set, bytecode-VM runtime enforcement, and schema-typed state-machine validation — remain open follow-ups with their stated unblockers.
**Concerns:** [`decisions/ADR-009-structured-outputs.md`](decisions/ADR-009-structured-outputs.md), [`design/rendering-and-views.md`](design/rendering-and-views.md) (§ schema-mechanism, § trust-model, § blessed-libraries), [`proposals/implemented/schema-and-invariant.md`](proposals/implemented/schema-and-invariant.md) (Layer 7 step 1, whose `SchemaInvariantDeferred` disposition this resolves), Q-035 (whose deferred scope this is), Q-026 (blessed libraries — JSON / PlainText / Markdown landed, HTML5 / SVG / PDF remain), Q-006 (the foreign-binding trust model that extends to ForeignNode-backed checkers), Q-040 (the `EvaluationLimits` budget invariant evaluation runs under)
**Resolution:** Lift Schema/Invariant evaluation from verify-time-on-statically-known-values (step 1) to runtime-on-dynamic-values, closing the gap that step 1 records as the `SchemaInvariantDeferred` informational diagnostic. The step-1 `SchemaChecker` evaluates invariants only on values it can resolve statically (literals, fully-static product/sum/Let/VarRef/NodeRef towers) and surfaces every other schema-typed value as a non-failing deferred check — so an invariant violation on a value computed at runtime (a function parameter, an `Application` result, a `Match` branch, a foreign-call return) is never caught. Step 2 makes the interpreter enforce those invariants when the value materialises: schema obligations (the `TypeExpr.SchemaType` entries the verifier already re-records at value-flow sites — `Application` argument, `ProductFieldValue`, `SumValue` payload) are threaded into the interpreter, and when the interpreter produces a value for an obligation-site NodeId it evaluates each of the schema's pure-expression invariant bodies against the actual value, raising a new recoverable `InterpretError.SchemaInvariantViolation(at, schema, invariant, valueDescription)` on `false`. The combined discipline is sound and complete-at-runtime: verify-time rejects statically-provable violations early; runtime rejects the rest when the concrete value appears; a schema violation is never silently emitted (preserving the Q-044 containment framing — schema validity is contained at verify or runtime). The capability context for invariant evaluation stays empty and the body stays pure (the step-1 `SchemaInvariantBodyMustBePure` / `…Monomorphic` / `…TypeMismatch` rules are unchanged for the foundational slice). Three extensions ride under this identifier and are deferred with concrete unblockers: **(a) ForeignNode-backed checkers** — relax `SchemaInvariantBodyMustBePure` to admit an invariant body that is a registered host checker (for invariants needing arithmetic, external knowledge, or whole-tree traversal that a pure body expresses awkwardly), with the trust model extending Q-006's foreign-binding mechanisms (signed provenance, reproducibility, sandboxed execution) per `rendering-and-views.md` § trust-model; **(b) blessed-library extension** — HTML5, SVG, PDF schemas and serializers (JSON / PlainText / Markdown already landed under Q-026), where HTML5 and SVG are blocked on the nested-recursive-self pattern (the same blocker recorded for the JSON nested-μ case) until a richer recursive-binder protocol or a single-big-sum workaround lands; **(c) bytecode-VM runtime enforcement** — the VM erases schemas pre-bytecode (Q-017), so runtime invariant checks are interpreter-only in the foundational slice and a `CHECK_SCHEMA`-style lowering (or a verifier-injected check) is needed for VM parity; and **(d) schema-typed state-machine state/events** — runtime validation of a live view's per-transition rendering (`rendering-and-views.md` § live-views). The foundational slice (a) runtime pure-expression invariant enforcement in the tree-walking interpreter — landed 2026-06-03: `InterpretError.SchemaInvariantViolation(at, schema, invariant, valueDescription)`, an `Interpreter.schemaObligations: Map<NodeId, TypeExpr.SchemaType>` constructor parameter checked at the `eval` exit (invariant bodies evaluated with an `inInvariant` re-entrancy guard, under empty capabilities and the run's `EvaluationLimits`), the CLI `run` path building the obligation map from `VerifyResult.Ok.nodeTypes`, corpus 82 (dynamic pass → `IntV(2)`) and 83 (dynamic violation → `SchemaInvariantViolation`), and `CorpusRuntimeSchemaTest` (5 cases, including an interpreter-with-obligations==VM pass-case cross-check and a guard pinning the VM's non-enforcement of the violation case; corpus 82 is also in `VmEquivalenceTest`). Full suite 1157 tests green; no node encoding changed. Specified and implemented in [`proposals/implemented/runtime-schema-enforcement.md`](proposals/implemented/runtime-schema-enforcement.md); see its Implementation note for the six recorded notes (chiefly: the check fires at the generic `eval` exit keyed on the verifier's re-recorded NodeIds; static sites are re-checked redundantly; enforcement is interpreter-only because the VM erases schemas pre-bytecode).

Layer 7 step 1 (Q-035) shipped the Schema (N-032) and Invariant (N-033) node categories, the `SchemaType` first-class type, the value-flow re-recording at `Application` / `ProductFieldValue` / `SumValue` sites, and the `:schema` module's `SchemaChecker` that evaluates pure-expression invariants at verify time. Its deliberate boundary is *statically-known values only*: anything the checker cannot fold to a literal tower becomes a `SchemaInvariantDeferred` diagnostic that surfaces but does not fail. The consequence is that the schema mechanism, today, guarantees nothing about a value an agent's program computes at runtime — exactly the values a generated program most often flows into a schema position. ADR-009 § Decision and `rendering-and-views.md` § schema-mechanism describe the verifier checking invariants "at graph-construction time over symbolic representations of the value's structure" and a ForeignNode-checker dispatch protocol, neither of which the step-1 slice implements for dynamic values. This question covers the runtime half.

### Q-048: In-language error recovery {#Q-048}

**Status:** Resolved (N-047 Attempt implemented 2026-06-11 in the Kotlin/JVM reference implementation, both evaluator backends; proposal moved to [`proposals/implemented/error-recovery.md`](proposals/implemented/error-recovery.md))
**Concerns:** [`design/node-algebra.md`](design/node-algebra.md), [`design/effects-and-capabilities.md`](design/effects-and-capabilities.md) § Effect handlers, [Q-040](#Q-040) (resource limits — uncatchable by design), [Q-041](#Q-041) (sandbox violations — uncatchable host policy), [Q-042](#Q-042) (a caught error's detail carries the scrubbed form), [Q-044](#Q-044) (the harm bound the closure rule preserves), [Q-047](#Q-047) (schema violations — the prime catchable case), [Q-021](#Q-021) (the retry-loop-exercising tasks this gates)
**Resolution:** A new node category **N-047 Attempt** — `Attempt(body: Expression)`, typed as the verifier-synthesized structural sum `Ok(T) | Err({kind: String, detail: String})` and consumed with the existing Match/ConstructorPattern machinery exactly like Option. Failures are not effects: `closureOf(attempt) = closureOf(body)`, so the Q-044 harm bound `closure ∩ C ∩ B ∩ P` is computed identically with or without Attempt and the containment argument survives unchanged. A catchable/uncatchable taxonomy classifies all thirteen `InterpretError` variants: `IoFailure` and `SchemaInvariantViolation` are catchable; program defects (`NotCallable`, `ArityMismatch`, `UnboundAtRuntime`, `NoMatchingCase`) are uncatchable — the agent regenerates rather than handling its own type errors; host-policy errors (`ResourceExhaustion`, `SandboxViolation`, `CapabilityViolation`, `RefinementViolation`) are uncatchable so a program cannot probe policy or run a handler on an exhausted budget (an explicit `Policy.Probe` effect is recorded as the principled alternative if probing is ever wanted); infrastructure errors (`MissingNode`, `UnknownForeignTarget`, `NodeRefTargetNotInStore`) are uncatchable. The flat Err payload (kind tag plus scrubbed detail string, no NodeIds, no offending value) keeps Err values identical across interpreter and VM; both backends ship in one slice — the Q-047 interpreter-only precedent is deliberately not repeated because Attempt is result-shaping, not check-omitting. Layer A surface: a `TRY` code with prelude support for the error-payload type. Alternatives surveyed and rejected with rationale: Try-variant builtins (doubles the IO surface, no schema coverage, Match-tower cost on pipelines), a catching Handler mode (category-keyed so schema violations have no interception home; the error value is not observable, so retry-then-fallback remains inexpressible), and a full algebraic failure channel (requires the abort machinery the N-043 no-continuation design deliberately avoided). Specified and implemented in [`proposals/implemented/error-recovery.md`](proposals/implemented/error-recovery.md), whose Implementation note records seven deviations — chiefly: the VM unwind reuses `SUM_NEW` (only `ATTEMPT_PUSH`/`ATTEMPT_POP` are new opcodes) and closed the pre-existing VM IoFailure/SandboxViolation translation parity gap en route; Result synthesis is `TypeExpr`-level with origin-excluded structural equality; the WHEN-from-TRY elaborator inference case is deferred, and the `BuiltinContractViolation` hygiene follow-up (overlapping [Q-056](#Q-056)) shipped as a same-day follow-up commit. Corpus 85–87 (Ok passthrough, Fs.Read fallback, retry-with-backoff — the canonical agent program), all VM-equivalent; full suite 1448 tests green after integration.

Strand programs cannot observe their own failures: any `IoFailure` (connection refused, DNS failure, HTTP timeout, a vanished file, every LLM provider error), `SandboxViolation`, or `SchemaInvariantViolation` propagates as a host-level exception that no node category can observe, and Handler (N-043) intercepts before dispatch — it can mock an effectful call but cannot attempt the real operation and fall back on its failure. The only recoverable failures today are value-coded ones (`Http.Request` status-as-data, the Option-returning parse and stream-receive builtins). The canonical agent program — call an API, retry transient failure with backoff, fall back on permanent failure — is therefore inexpressible, which also gates the Tier 1 retry-loop-exercising tasks in [`ROADMAP.md`](ROADMAP.md). Identified by the 2026-06-10 independent review.

## Recursive types {#questions-recursive-types}

### Q-029: Recursive types and termination of canonical hashing {#Q-029}

**Status:** Proposed
**Concerns:** [`design/node-algebra.md`](design/node-algebra.md), [`decisions/ADR-003-content-addressing.md`](decisions/ADR-003-content-addressing.md)
**Resolution:** A μ-binder mechanism via two new node categories: `RecursiveType` (N-041) and `RecursiveSelf` (N-042). RecursiveType introduces a positional self-binder over its body; RecursiveSelf inside the body resolves by de Bruijn depth, not by hash. This is exactly analogous to how `Lambda`/`VarRef` and `ForallType`/`TypeParameter` handle their respective binders. Equirecursive equality is decided by hash equality of the canonical encoding — no separate coinductive equality algorithm at the language level. ADR-003 is reinforced rather than revised: the new node pair is precisely the "fixed-point indirection" ADR-003 endorses for term-level recursion, extended to types. The body must be contractive (every path from binder to a RecursiveSelf reference traverses at least one type constructor) to guarantee termination of any monotone fold. Proposed in [`design/node-algebra.md`](design/node-algebra.md) § Recursive types.

How can a recursive type (`List = Nil | Cons(head: Int, tail: List)`) be content-addressed when its hash would depend on itself? ADR-003 explicitly rules out self-referential hashes ("recursion through a node's own hash is undecidable"). node-algebra.md originally said "recursive types must go through Fixpoint or NodeRef" but neither mechanism was sufficient — Fixpoint is term-level, NodeRef walks to its target during hashing. Mutually recursive type families are encodable via single-product `RecursiveType` + projection; higher-arity recursive binders are a possible future extension but not required by the proposal.
