# Strand `impl-kotlin/` — session brief for Claude

Kotlin/JVM reference implementation of Strand. **Layers 1 through 7 step 1 are complete** (Layer 6 step 2 fully implemented as of 2026-05-24):
- Layer 1 (pure-computation core, N-001..N-019 + N-034 TypeAbstraction + N-035 ForallType)
- Layer 2 step 1 (content addressing — canonical CBOR encoder, BLAKE3 hasher, alpha-equivalence by positional encoding, hash-keyed dedup store)
- Layer 2 step 2 (NodeRef-by-hash — `Node.NodeRef.target` is `Hash` in the canonical form; new `RawNodeStore` + `StoredNode` intermediate carries `RawNodeRef(targetId: NodeId)` between ingest and `Hasher.finalize`; finalize replaces every raw entry with a canonical `Node.NodeRef(target = computed hash)` and returns the bidirectional `nodeIdToHash` / `hashToNodeId` maps as a `FinalizedProgram`. Verifier and interpreter accept the reverse map and resolve `NodeRef.target` through it; new verifier rule `NodeRefTargetMustBeClosed` enforces that the target subgraph references no binders outside itself, so the hash is context-independent. `Hash` and `HashFunction` moved from `:hashing` to `:core` to host this without a circular module dependency. Canonical bytes are unchanged for every NodeRef — all 45 corpus programs hash byte-identically across the step-1/step-2 boundary. Cross-store fetches remain deferred)
- Layer 3 step 1 (effects and capabilities — N-021 EffectCategory, N-022 EffectDecl, N-036 CapabilityScope, effect-closure verification, capability-context interpreter)
- Layer 3 step 2 (refinement-lattice capability matching — `Application.effectInstances` is load-bearing; runtime capability context is a structured `CapabilitySet(grants: Map<EffectCategory NodeId, List<CapabilityPattern>>)` with per-slot `Wildcard | Concrete(Value)`. Refinement check fires only for categories with an explicit EffectDecl at the call site; categories without an instance pass through after the category-presence check (so a caller forwarding a capability down the chain is not denied at its own call). Distinguishes `CapabilityViolation` (category absent) from `RefinementViolation` (category present, no pattern covers). The pre-Q-031 `Interpreter.eval(root, Set<NodeId>)` overload is preserved as a thin wrapper over `CapabilitySet.ofCategories(...)`, which produces a single-slot wildcard sentinel that covers any-arity requirements — every pre-Q-031 corpus program runs unchanged. Builtins gained reference stubs for `strand-builtin:Filesystem.Write` and `strand-builtin:Network.Connect` to exercise the refinement path end-to-end)
- Layer 3 step 3 (no-continuation effect handlers — N-043 Handler intercepts every Application within its body whose called function declares the intercepted EffectCategory; the handle expression evaluates to a function value at Handler-entry and is invoked with the intercepted call's arguments. Innermost handler wins on nested same-category Handlers (`findLast` over the active-handler stack). Verifier enforces signature agreement (every intercepted Application's value-arg and result types must equal the handler's), monomorphism of the handle (`Forall`-typed handles are rejected as `HandlerOverPolymorphicHandle`; non-function handles as `HandlerNotAFunction`), and the closure-subtraction rule `closureOf(handler) = (closureOf(body) - {intercept}) ∪ closureOf(handle) ∪ handleFun.effects` — Handler is the only node category that *removes* an effect from a closure. The interpreter threads `List<ActiveHandler>` alongside the `CapabilitySet` context introduced by Q-031; the three public `eval` overloads all start with an empty handlers list. The handler's own declared effects flow into the surrounding capability context — so a handler that itself writes to a file requires the surrounding context to grant Filesystem.Write. Capability checks for the intercepted category are skipped at the intercepted call site — the handler replaces the effectful call wholesale)
- Layer 4 step 1 (foreign function interface — N-020 ForeignNode, in-process Builtins registry: Int arithmetic Add/Sub/Mul/Div/Mod/Neg, Bool.Not, Int comparisons Eq/Lt/Le/Gt/Ge, String.Concat, Time.Now with a fixed replay timestamp, plus `Filesystem.Write` and `Network.Connect` reference stubs for Q-031)
- Layer 5 step 1 (Match + Pattern — N-023 Match, N-024 MatchCase, N-025 Pattern with LiteralPattern/VariablePattern/WildcardPattern variants; "first match wins" semantics; runtime `NoMatchingCase` for unhandled scrutinee values)
- Layer 5 step 2 (Fixpoint — N-026; recursion via runtime self-reference, no self-referential hashes per ADR-003; the body Lambda's first parameter is the recursive call slot, supplied by the runtime; verifier checks the body's type matches `((recursionType, ...recursionType.parameters) -> recursionType.result)`)
- Layer 5 step 3a (product values — N-037 ProductValue, N-038 ProductFieldValue, N-039 ProductFieldGet; closes the construct-a-product gap)
- Layer 5 step 3b (sum values + constructor patterns — N-040 SumValue, plus a new ConstructorPattern variant of N-025 Pattern; closes the construct-a-sum gap and makes Option/Result-style programs expressible. Constructor patterns nest arbitrarily; VariablePatterns reached via a ConstructorPattern's payload tree are valid binders for the case body)
- Recursive types (N-041 RecursiveType + N-042 RecursiveSelf) — closes the recursive-type gap via μ-binder positional encoding. Equirecursive semantics decided by hash equality (canonical encoder *is* the type-equality algorithm). Verifier enforces contractivity. Unblocks linked lists, trees, and any data structure with self-referential type definitions
- Layer 6 step 1 (synchronous trace runtime for state machines — N-027 StateMachine, N-028 EventStream, N-029 Transition. New `runtime/` module exposes a single public API: `StateMachineRuntime.runMachine(machine, events: List<Value>, capabilities: CapabilitySet = EMPTY): Trace`. Step 1 restricts machines to exactly one input stream (verifier-enforced via `StateMachineInputStreamCountUnsupported`); transitionFn must resolve directly to a Lambda (no Fixpoint wrapping); the result type must be the product `{state: State, outputs: OutputBatch}` where `OutputBatch` is a positionally-indexed product `{output_0: Option<outputStreams[0].eventType>, output_1: Option<outputStreams[1].eventType>, ...}`. Empty `outputStreams` means OutputBatch is the empty product `{}`. The runtime is a deterministic fold over the event list — pure transition functions guarantee replay determinism by construction. Halt reason in step 1 is always `EventsExhausted`; explicit-termination and supervisor-initiated halts are step 2/3)
- Layer 6 step 2 (async multi-machine actor runtime — per-machine Kotlin coroutine actors on `Channel<Value>`; `StateMachineRuntime.runGroup(group: MachineGroup, scope: CoroutineScope): MachineGroupHandle` is the async entry point alongside the preserved sync `runMachine`. `MachineGroup` carries the canonical NodeStore, hashToNodeId reverse map, list of StateMachine NodeIds, capability context, per-stream `bufferCapacity` (default 1024), and `recordInputs` flag (default `true`). Stream wiring is computed once at `runGroup` startup: every EventStream NodeId gets one `Channel<Value>`; structurally-equal streams share a channel (content-addressing IS the wiring); external inputs/outputs surface as `SendChannel`/`ReceiveChannel` on the `MachineGroupHandle`. Topology validation (`MachineGroupValidationError.InternalStreamNoProducer | NoConsumer | MultipleProducers | MultipleConsumers | ExternalStreamCannotBeProduced | OutputStreamCannotBeConsumed`) runs in `MachineGroup.validateTopology()` before any actor spawns — runtime-side rather than verifier-side, since the existing verifier reasons about one StateMachine at a time. Each actor runs a `select`-based loop over its input channels (Q-009's nondeterministic-merge default); for multi-stream machines, payloads are wrapped in a `stream_i`-cased SumV before being passed to the transition function. Output dispatch detects shape: a `ProductV` is the step-1 OutputBatch (preserved unchanged for single-stream programs 41-45); a `SumV` is the step-2 tagged list `Nil | Cons(head: TaggedOutput, tail)` whose `TaggedOutput.case` is `output_i`. The interpreter is unchanged — only the actor loop suspends. Per-instance `EventRecorder` captures input events for replay-determinism assertions: feed `handle.recordedEvents(instanceId)` back into `runMachine` against the same StateMachine NodeId to reproduce the per-step trace. **Verifier multi-stream lift** (Q-033 follow-up landed 2026-05-24): `StateMachineInputStreamCountUnsupported` is removed; `Verifier.synthesizeInputEventSum(inputEventTypes)` builds the `stream_0(T_0) | ... | stream_{n-1}(T_{n-1})` sum for multi-input transitions; `Verifier.synthesizeTaggedOutputListType(outputEventTypes)` builds the recursive `μ. Cons({head, tail}) | Nil` shape that the transition function may return as an alternative to OutputBatch (the runtime dispatches based on actual produced value). Single-input machines preserve the original `inputStreams[0].eventType` Event type so corpus 41–45 verify unchanged. Both expected result shapes (OutputBatch and tagged-list) are accepted for any machine; the verifier picks the closer one for diagnostics. **Async corpus programs 46–49** ship: 46 (single-machine counter), 47 (multi-input merge with synthesized InputEvent sum), 48 (three-machine supervisor pattern wired via internal streams, Let-chain root for multi-machine reachability), 49 (tagged-output list emitting to two streams per event). The **`strand group <file.json> --events <events.json>` CLI subcommand** drives a MachineGroup built from every StateMachine NodeId reachable in the canonical store; the routed-event format (`{"stream": "<authorName>", "tag": "<tag>", ...}`) names the destination external input stream per event. Three intentional deviations from the original proposal: (1) the proposal's §5 verifier rules for cross-machine topology (`InternalStreamNoProducer` etc.) ship as runtime-side `MachineGroupValidationError` variants because the per-machine verifier cannot reason cross-machine; (2) implicit `StateMachine.Send`/`Receive` (E-028/E-029) verifier enforcement is deferred to step 3 along with a registration mechanism for well-known EffectCategory nodes; (3) corpus 48 implements the §6.6 observational supervisor framing rather than §7's spawn-and-restart framing — real dynamic spawn/terminate via E-030/E-031 lands in step 3. Step 3 (backpressure overflow policies beyond block-producer, supervisor restart policies with real spawn/terminate, snapshot/replay-from-log, fan-out/fan-in on internal streams) remains roadmap.)
- Q-034 step 1 — Layer A authoring projection + Layer C elaboration (2026-05-24, density work landed 2026-05-25). New `:authoring` Gradle module under `authoring → core` (with kotlinx-serialization-json as an implementation dep for the dag-json emitter). Provides the syntax-level half of the four-layer emission stack proposed in [`proposals/implemented/llm-authoring-layer.md`](../proposals/implemented/llm-authoring-layer.md): a compact text grammar (`<author-id> <CODE> <arg>...`, one node per line), [`LayerAParser`](authoring/src/main/kotlin/org/strand/authoring/LayerAParser.kt) (generic line-based tokenizer that accumulates [`AuthoringError`](authoring/src/main/kotlin/org/strand/authoring/AuthoringError.kt) reports across the document), and [`DagJsonEmitter`](authoring/src/main/kotlin/org/strand/authoring/DagJsonEmitter.kt) (per-code arg-shape validation + canonical dag-json assembly). **[`Elaborator`](authoring/src/main/kotlin/org/strand/authoring/Elaborator.kt) runs unconditionally** as part of `Authoring.compileToDagJson(text)` — the optional `compileWithElaboration` entry point and the `strand author --elaborate` CLI flag were collapsed away in the 2026-05-25 cleanup pass. The elaborator now ships **11 bidirectional inference cases** that fill in absent annotations: the original four cases sketched in Q-034 §5.3 (`Lambda.effects` from the body's effect closure, `Application.effectInstances` defaulted from capability context, `Application.typeArguments` inferred from value-argument types, `Lambda.paramType` inferred from call-site context) plus seven additional cases added by the Layer A density v4 follow-up (recursion-slot `paramType`, `FunctionType` synthesis from a `FIX recursionType` reference to an undeclared name, `SCS` caseType inference from `SumValue` payloads, compact-LAM parameter inference at call sites, Match scrutinee context, `ProductFieldValue` context, `ProductFieldGet` target context — plus the StateMachine transitionFn context). The inference passes run in a fixed-point loop (bounded at 8 iterations; every realistic document converges in 2-3) so earlier cases feed later ones. Effect-closure rules mirror the verifier's `nodeClosures` computation. Compiled JSON is fed into the existing `:core` `JsonIngest` unchanged — no verifier or interpreter changes. **Grammar coverage** is complete across the implemented node algebra: 42 codes spanning Layer 1 (literals, types, lambda/application/let/varref, NodeRef, TypeAbstraction, ForallType), Layer 3 (EFC EffectCategory, EFD EffectDecl, CAP CapabilityScope, H Handler), Layer 4 (FN ForeignNode), Layer 5 (MAT Match, MC MatchCase, PLT/PVR/PWC/PCN Pattern variants, FIX Fixpoint, PV/PFV/PFG product values, SV SumValue, RT/RS recursive types), Layer 6 (SM StateMachine, ESE/ESI/ESO EventStream variants, TR Transition), and Layer 7 (SCH Schema, INV Invariant). Variant-bearing categories (Pattern.kind, EventStream.streamKind) use the [`CodeSchema.discriminator`](authoring/src/main/kotlin/org/strand/authoring/LayerAGrammar.kt) field — one Layer A code per variant, each emitting the right kind/streamKind discriminator alongside the positional fields. Only N-030 Name and N-031 Provenance are unmapped (metadata-only, no current corpus usage). The density-v* shorthand forms (implicit prelude reserving 49 names for primitive types / builtins / effect categories, inline literals at REFERENCE / LIST_REF / NULLABLE_REF positions, auto-VarRef for PRC binders, `IF` and `WHEN` sugar that expand to Match / MatchCase / Pattern towers, compact LAM parameter declarations, anonymous `_` ids with `@last` resolution, inline ProductFieldValue lists, nested `(CODE args...)` expressions) all live in the same grammar and lower to byte-identical canonical dag-json — every density program hash-equals the canonical JSON it shadows. The new regression net is [`LayerADensityTest`](corpus/src/test/kotlin/org/strand/corpus/LayerADensityTest.kt), 10 density fixtures across `density-v1` / `density-v1.5` / `density-v2` / `density-v2.5` / `density-v3` / `density-v4` covering factorial, JSON value, toggle machine, and option-some-unwrap programs. **Measured impact:** the three-task evaluation suite (factorial / json-value / toggle-machine) under `evaluation/results.md` reports baseline Strand Layer A at 2.20× Python+type-hints geomean and Layer A density v4 at **0.81× geomean** (factorial 0.87×, json-value 0.81×, toggle-machine 0.76×) — under the Python+type-hints baseline on every task, well below the §6 projected floor of 0.8–1.3× and achieved without any tokenizer-side fine-tuning. `strand author <file.layer-a> [--emit-json]` CLI subcommand compiles + verifies + reports root type. **Deferred from Q-034 step 1:** tokenizer alignment (Phase 4 fine-tuning investment) and the full Q-021 baseline evaluation against all five conventional-language baselines on the broader task family (Phase 1 work). The current three-task evaluation MVP is static-cost only; dynamic cost (tokens-per-successful-task across an agent's retry loop) requires model-API integration that is also a Phase 1 follow-up.
- Layer 7 step 1.5 — first blessed library: JSON (2026-05-24). Builds on the Q-035 Schema + Invariant mechanism with no new node category and no verifier change: just a real schema graph and three corpus programs. `JsonValue` is a flat sum over `JsonNull | JsonBool(Bool) | JsonNumber(Int) | JsonString(String)`; `JsonObject` is a recursive list `μ. Cons({head: JsonEntry, tail: <self>}) | Nil` over `JsonEntry = {key: String, value: JsonValue}`. The `UniqueKeyJsonObject` Schema wraps `JsonObject` with a `unique_keys` invariant whose body is a `Fixpoint`-recursive `(JsonObject) -> Bool` Lambda that walks the entries list and checks for duplicates via a nested `Fixpoint` `contains: (String, JsonObject) -> Bool` helper. Three Bool-combining builtins (`Bool.And`, `Bool.Or`, `String.Eq`) were added to `interpreter/Builtins.kt` to support the invariant body's logic. Corpus programs 54 (JsonValue primitives), 55 (UniqueKeyJsonObject with three distinct keys, accepted), 56 (UniqueKeyJsonObject with duplicate keys, rejected with `SchemaInvariantViolation`) ship; all invariant evaluations are static via `SchemaChecker.tryEvaluateStatically` (the entries lists are SumValue/ProductValue/literal towers). One design deviation worth surfacing: `JsonValue` does **not** include `JsonArray(List<JsonValue>)` or `JsonObject(List<JsonEntry>)` cases (the recursive cases that would make it a full JSON model), because Strand's RecursiveSelf always resolves to the innermost μ binder and there is no mechanism for an inner Recursive (the list) to reference an outer Recursive (JsonValue). Nested-μ for arrays/objects of JsonValue is deferred to a future step (likely needing either a "single big sum" workaround or a richer recursive-binder protocol). Proposal at [`proposals/implemented/json-blessed-library.md`](../proposals/implemented/json-blessed-library.md).
- Layer 7 step 1 (Schema + Invariant — N-032 Schema, N-033 Invariant. New `schema/` Gradle module under `schema → interpreter → verifier → core` exposes `SchemaChecker(store, hashToNodeId, verifyResult).check(): SchemaCheckResult`. Schema is a first-class `TypeExpr.SchemaType(schemaId, valueType, invariants)` variant that may appear in any type position; when a plain-T value flows into a `SchemaType<T>` position the verifier re-records the value's NodeId with the SchemaType so the SchemaChecker pass can find it. The `typesCompatible(expected, actual)` helper at value-flow sites (Application argument, ProductFieldValue, SumValue payload) relaxes strict structural equality to permit assignment in both directions (T → SchemaType<T> and SchemaType<T> → T); other equality sites (Match case-body divergence, Fixpoint body shape, Handler signature, StateMachine signature) keep strict `==` semantics. Pure-expression invariants only — the verifier rejects ForeignNode-typed bodies as `SchemaInvariantBodyMustBePure`, Forall-typed bodies as `SchemaInvariantBodyMustBeMonomorphic`, and non-`(valueType) -> Bool` shapes as `SchemaInvariantBodyTypeMismatch`. The canonical encoder excludes `targetSchema` from Invariant's encoding to break the Schema↔Invariant hash cycle (matches N-009 ProductTypeField precedent: parent-child relationship is recoverable from the parent's `invariants` list, not from the child's encoding); the field is retained on the in-memory ADT for the verifier's `InvariantTargetMismatch` defensive topology check. SchemaChecker walks `VerifyResult.Ok.nodeTypes` for SchemaType entries; statically evaluates values per the proposal's recursive definition (literals; ProductValue / SumValue with sub-values statically known; Let chains; VarRef into Let-bound static values; NodeRef to closed static subgraphs); invokes invariant bodies via `Interpreter.applyCallable` under an empty capability context (purity is statically enforced). Non-static values produce `SchemaInvariantDeferred` informational diagnostics in `VerifyResult.Ok.deferredChecks` (default disposition: surface but do not fail). Synthetic PositiveInt + NonEmptyList corpus programs 50-53 exercise the mechanism. Reference output libraries (HTML5, SVG, JSON, PDF, plain text, Markdown), ForeignNode-backed checkers, symbolic / non-static invariant evaluation, provenance manifests, live-view composition with state machines, and interaction with encrypted nodes remain deferred to subsequent shipping steps)

```
runtime/      Synchronous trace runtime (Layer 6 step 1) + async multi-machine actor runtime (Layer 6 step 2) + step 3 (overflow policies, supervision, snapshots, metrics)
schema/       Verify-time invariant evaluation for Schema/Invariant (Layer 7 step 1)

vm/           Q-017 step 1 bytecode VM — dispatch loop, Frame, VmClosure/VmForeign/VmFixpoint callables, capability stack + active handler list, EQ/SUM_CASE_IS/SUM_PAYLOAD/THROW_NO_MATCH helpers, `Vm.applyClosure` + `Vm.evaluate` public APIs for runtime/schema integration. **57 of 58 corpus programs pass `interpreter == VM` equivalence** across VmEquivalenceTest (Layers 1/3/4/5 programs), VmMachineEquivalenceTest (sync state machines), VmSchemaEquivalenceTest (every schema program), and VmAsyncMachineEquivalenceTest (every async program 46-49, 57 via `MachineGroup.dispatcherFactory`). The 1 remaining program is 08/09 (type-decl-only, no value to evaluate).
cli/          `strand verify|run|machine|group|author|grammar <file>`

```

Dependency direction: `verifier → core`; `interpreter → verifier → core`; `hashing → core`; `runtime → interpreter → verifier → core`; `schema → interpreter → verifier → core`; `authoring → core`; `cli → interpreter` + `runtime` + `schema` + `authoring`; `corpus → cli`/`interpreter`/`hashing`/`runtime`/`schema`/`authoring`. The interpreter does not re-run verification — it trusts its input has been verified. The hasher does not re-run verification either — it trusts its input has been verified, and produces hashes for every reachable node. The runtime trusts the same and consumes only verified StateMachine nodes. The SchemaChecker trusts the same: it consumes the verifier's `nodeTypes` map and the canonical store, evaluating invariant bodies via `Interpreter.applyCallable`.

## Code conventions

- **Plain JVM Kotlin.** No Android SDK, no MVVM, no lifecycle, no Activity/Fragment, no DI framework.
- **Sealed classes + `when`** for the node ADT and for typed errors.
- **Structured errors are typed data, not strings.** See `VerifyError`, `InterpretError`. New error cases extend the sealed hierarchy.
- **JUnit 5** for tests. `testLogging` is already wired in the root build.
- **Author ids → opaque `NodeId`s in a single ingest pass.** Forward references inside a document are allowed. Layer 2 will replace `NodeId`s with BLAKE3 hashes; preserve that seam.
- **Scope is by `NodeId`, not by name.** The `name` field on `ParameterDecl` and `Let` is metadata.
- **`NodeRef` is content-addressed in Layer 2 step 2** — `Node.NodeRef.target` is a [Hash] in the canonical form. JSON ingest still uses author ids (string targets); `Hasher.finalize` computes per-NodeId hashes and writes the canonical NodeRef. Verifier and interpreter resolve `target: Hash → NodeId` via the `hashToNodeId` reverse map returned by `finalize`, then continue with NodeId-based forwarding. The verifier rule `NodeRefTargetMustBeClosed` rejects NodeRefs whose target subgraph contains free [VarRef] / [TypeParameter] references; the closure invariant guarantees the target hash is context-independent.
- **`hashing/` module owns Layer 2 content addressing.** `CanonicalEncoder` emits the canonical bytes per `design/node-algebra.md` § Hash construction (4-byte big-endian category tag + canonical-CBOR fields, with de Bruijn `(depth, index)` for VarRef binders and TypeParameter references). The encoder dispatches on `StoredNode` (Canonical vs RawNodeRef) so it operates on both pre- and post-finalization stores; it tolerates unbound VarRef/TypeParameter/RecursiveSelf by emitting an `UNBOUND_SENTINEL` position so finalize does not crash on ill-formed graphs (the verifier reports the actual issue downstream). `Hasher` composes the encoder with BLAKE3 and returns multi-hash digests; `Hasher.finalize(rawStore, root)` is the Layer 2 step 2 entry point that produces a canonical `NodeStore` and the `nodeIdToHash` / `hashToNodeId` maps. `HashStore` is the post-hash deduplicating store. `Hash` and `HashFunction` live in `:core` (not `:hashing`) so `Node.NodeRef.target` can carry `Hash` without a circular dependency.

### When adding a new builtin

A "slice" that adds a builtin to `interpreter/Builtins.kt` is not done until the agent-facing surface knows about it. Every new monomorphic builtin ships with **three coordinated additions** in the same change:

1. **Builtin registration** in [`Builtins.kt`](interpreter/src/main/kotlin/org/strand/interpreter/Builtins.kt) under the `strand-builtin:` namespace, plus unit tests in `interpreter/src/test/`.
2. **Implicit-prelude entries** in [`LayerAGrammar.kt`](authoring/src/main/kotlin/org/strand/authoring/LayerAGrammar.kt) under `reservedNodes`: one `ReservedNodeSpec(jsonType = "FunctionType", ...)` for the signature (`{name}T`) and one `ReservedNodeSpec(jsonType = "ForeignNode", target = "strand-builtin:...", foreignType = "{name}T", effects = [...])` for the callable. For effectful builtins, the effect category (e.g., `cryptoFx`) must also be in the prelude. Verify with a small `Round2PreludeTest`-style assertion that the reserved name elaborates to the expected ForeignNode + FunctionType.
3. **System-prompt documentation** in [`evaluation/dynamic/prompts/strand-system.md`](../evaluation/dynamic/prompts/strand-system.md) under the Implicit prelude tables (FunctionTypes, Foreign-node builtins, Effect categories) so the agent learns the new reserved names. The "Round-2 builtins NOT in the prelude" note at the bottom of that section enumerates the exclusions.

**Exceptions where step 2 is skipped (with note):**

- **Polymorphic builtins** (List.Map, List.Length, String.Split, etc.) — the prelude can only express monomorphic FunctionTypes today. Agents declare an explicit FNT + FRN at each use site, choosing the concrete element type. A polymorphic-FNT prelude facility is a future authoring-layer extension.
- **Option-returning builtins** (String.ParseInt, Bytes.ParseHex, Process.EnvVar) — would require a blessed `Option<T>` in the prelude. Pending; explicit FNT + FRN for now.
- **Builtins typed against agent-chosen payload types** (Fs.*, Net.*, Http.Request, Json.Parse against a specific JsonValue schema) — the agent picks the payload shape; no single prelude FNT fits.

Skipping step 2 *without* one of these reasons is the bug Jeff raised in 2026-05-26: the round-2 builtins shipped without prelude entries even though Math.* / Hash.* / Random.* are all monomorphic. The follow-up commit added the entries; this checklist is the corrective.

## Type system status (Layer 1)

- **Explicit type abstraction and instantiation (System F).** A polymorphic term is a `TypeAbstraction` (N-034) whose body is any expression; its type is a `ForallType` (N-035) over the same `typeParameters`. Every `Application` of a polymorphic value carries `typeArguments`, a positional list whose length equals the function's quantified type-parameter count. The verifier substitutes into the ForallType's body to obtain a `FunctionType` against which value arguments are checked by structural equality. No HM, no unification, no occurs-check, no let-generalization.
- `TypeParameter` is a rigid generic identified by **node identity** — two distinct `TypeParameter` nodes are two distinct variables, even with the same name. A TypeParameter is bound by the enclosing `TypeAbstraction` (in term position) or `ForallType` (in type position) that lists it; an unbound TypeParameter is rejected with `UnboundTypeParameter`. `Lambda` does not implicitly bind TypeParameters.
- **Partial type instantiation is rejected.** If substituting at an Application reduces a `ForallType` to another `ForallType`, the verifier reports `PartialTypeInstantiation`. Every Application of a polymorphic value must reduce to a `FunctionType`.
- `paramType` is mandatory at every `ParameterDecl`.
- **Subtyping is not implemented.** `node-algebra.md` describes structural subtyping; Layer 1 uses strict structural equality. Width subtyping can be added without breaking existing tests.
- `TypeParameter.bound` is parsed but ignored (requires subtyping).

  **Slice 3.6 details (landed 2026-05-24).** `Node.EventStream` gains a third optional content field: `consumerMode: ConsumerMode?` (sibling enum to `OverflowPolicy`, in `core/Node.kt`) with variants `Single` (default) and `Broadcast`. Canonical encoding follows the same additive-versioning rule as slice 3.1 — when `consumerMode` equals its default (`null` / `Single`), the encoder omits the field and the EventStream hash is byte-identical to the pre-slice-3.6 form. JSON ingest accepts the two variant names (case-insensitive). `MachineGroup.validateTopology` is relaxed in two directions: (1) multi-producer fan-in on `internal` and `output` streams is now allowed unconditionally — multiple producer machines share the same underlying `Channel<Value>` with nondeterministic interleaving per Q-009's default (`MachineGroupValidationError.InternalStreamMultipleProducers` is retained as a sealed-class member for backward compatibility but is no longer raised); (2) multi-consumer is allowed when the stream's `consumerMode` is `Broadcast` (`Single` streams still raise `InternalStreamMultipleConsumers`). The runtime introduces [`StreamBus`](runtime/src/main/kotlin/org/strand/runtime/StreamBus.kt), a sealed hierarchy with `Direct` (pre-slice-3.6 single-channel behavior) and `Broadcast` (a producer-facing `Channel<Value>` drained by a pump coroutine that forwards each value to per-consumer `Channel<Value>` instances). The bus owns a `producerHalted` counter so multi-producer streams stay open until *every* producer has halted; `MachineActor.run`'s `finally` block calls `bus.producerHalted()` instead of closing the output channel directly (with a fallback to direct `channel.close()` for `MachineGroupTest` fixtures that build a `MachineInstance` outside `runGroup`). `MachineInstance` gained an `outputBuses: Map<NodeId, StreamBus>` field for this. `StateMachineRuntime.runGroup` reorders to build instances (which allocates per-consumer channels) BEFORE launching broadcast pumps, so each pump sees every consumer's channel at startup — eliminates a subscription-timing race. **Design deviation from the proposal sketch in §4.4:** the implementation uses explicit per-consumer Channel fan-out rather than `MutableSharedFlow`. A `SharedFlow`-based first draft suffered a `replay=0`-drops-emissions-before-subscribers race that required a `subscriptionCount` gate complicating the pump under `runTest`'s test-scope timing; the explicit fan-out keeps closure semantics symmetric with the per-bus producer-counting model. Observable behavior (every consumer sees every event in producer FIFO order) is unchanged. Per-consumer DropOldest / DropNewest overflow integration for broadcast streams (proposal §6.4) is left to a follow-up — slice 3.6 ships with the BlockProducer default propagated through. Tests in `runtime/FanInOutTest`: 6 tests covering topology relaxations (multi-producer accepted, multi-consumer-without-Broadcast rejected, multi-consumer-with-Broadcast accepted) and semantics (fan-in multiset preservation, fan-out per-consumer FIFO, single-consumer-on-Broadcast degenerate case). The verifier-side `BroadcastStreamWithBlockProducerWarning` diagnostic (§5) is deferred to a follow-up — its value rises once per-consumer overflow policies for broadcast land.

Without proposals (still open design space):

- **Provenance-based binding trust.** ADR-005 and `security-model.md` describe the trust model for foreign bindings; Layer 4 step 1 ships an in-process registry that bypasses this entirely. Sandboxed bindings (WebAssembly, seccomp, TEE) are Milestone 2.4.
- **Mutual recursion between types.** Currently encodable via single-product `RecursiveType` + projection (the textbook lowering); higher-arity recursive binders are a possible future extension if a corpus program needs more direct encoding.

### Recursive types (N-041, N-042) — usage notes

Recursive sum types like `μ. Nil | Cons(head: Int, tail: <self>)` require two ProductType nodes in practice (one used inside the type definition with `tail: RecursiveSelf`, one used at value-construction sites with `tail: <recursive type itself>`). This is a consequence of the equirecursive design: the "inner" ProductType describes the case structure when viewed from inside the binder, the "outer" describes the same structure with the recursive reference closed. Both resolve to structurally-equal `TypeExpr.Product`s once equirecursive equality is applied (`TypeExpr.Product` and `TypeExpr.Sum` equality intentionally ignores their `origin` NodeId).

The JSON ingest accepts `effects` edges on `Lambda` and `FunctionType` (each entry a NodeId of an `EffectCategory`). `Application` accepts an optional `effectInstances` field (a list of EffectDecl NodeIds, default empty) — when populated, each EffectDecl positionally instantiates one of the callee's declared effects, and the verifier enforces 1:1 coverage. Capability matching is refinement-lattice in Layer 3 step 2: the runtime context is a `CapabilitySet(grants: Map<EffectCategory NodeId, List<CapabilityPattern>>)` with `Wildcard | Concrete(Value)` slots per category parameter; a capability covers a requirement iff one of its patterns covers the call-site EffectDecl parameter values (wildcards match anything, concretes match by Strand's value equality). The pre-Q-031 `Set<NodeId>` capability API is preserved as a thin `Interpreter.eval(root, Set<NodeId>)` wrapper that builds a wildcard-everywhere `CapabilitySet` so every existing call site keeps working.

`Application` JSON schema: `{ "type": "Application", "function": <id>, "arguments": [<id>, ...], "typeArguments": [<id>, ...]?, "effectInstances": [<id>, ...]? }`. Both optional fields default to `[]`. The canonical encoder gates the `effectInstances` field on `effectInstances.size > 0`: pre-Q-031 Applications (no effect instances) hash byte-identically to their post-Q-031 form, so the existing 32 corpus programs hash unchanged. Effect instances are emitted as a sorted set of multi-hashes — declaration order does not affect the hash.

`ForeignNode` schema: `{ "type": "ForeignNode", "target": "<binding-id>", "foreignType": "<FunctionType id>", "effects": [<EffectCategory ids>] }`. Target identifiers are namespaced; `strand-builtin:` designates the in-process registry (see `interpreter/Builtins.kt`). Layer 4 step 1 ships a small fixed set; future targets like `wasm:` and `process:` will be served by separate dispatchers.

`Pattern` JSON schema uses a `kind` discriminator: `{ "type": "Pattern", "kind": "literal", "patternType": "<typeId>", "literal": "<litId>" }`, `{ "type": "Pattern", "kind": "variable", "patternType": "<typeId>", "name": "n" }`, or `{ "type": "Pattern", "kind": "wildcard", "patternType": "<typeId>" }`. In the canonical encoding all variants share tag 25 with a small discriminator (0=literal, 1=variable, 2=wildcard) — N-025 is one node category per the spec. Variable-pattern names are metadata (not in the canonical encoding); two variable patterns of the same type with different names hash identically, matching ParameterDecl's alpha-equivalence treatment.

`Fixpoint` JSON schema: `{ "type": "Fixpoint", "recursionType": "<FunctionType id>", "body": "<Lambda id>" }`. The body Lambda has one more parameter than the user-facing arity: the first parameter is the recursive call slot whose type equals `recursionType`. Calling the Fixpoint value invokes the body Lambda with the Fixpoint itself bound as the first argument, so VarRefs in the body that point at the first parameter recurse through the same Fixpoint. There is no self-referential hash; the recursion exists only at evaluation time. The verifier enforces the body's structural shape; ill-formed bodies (wrong first-parameter type, wrong arity, etc.) produce `FixpointBodyShapeMismatch`.

`ProductValue` JSON schema: `{ "type": "ProductValue", "ofType": "<ProductType id>", "fields": [<ProductFieldValue ids>] }`. Each `ProductFieldValue` has shape `{ "type": "ProductFieldValue", "fieldName": "<name>", "value": "<Expression id>" }`. The `ProductValue.fields` list must cover every field declared in `ofType` exactly once (the verifier reports `DuplicateProductValueField`, `MissingProductValueFields`, or `UnknownProductValueField` otherwise). Field declaration order in the `fields` array does not affect identity — the canonical encoder sorts by `fieldName`. `ProductFieldGet` reads a field by name: `{ "type": "ProductFieldGet", "target": "<Expression id>", "fieldName": "<name>" }`. The verifier confirms the target's type is a product and that the named field exists.

`SumValue` JSON schema: `{ "type": "SumValue", "ofType": "<SumType id>", "caseName": "<case>", "payload": "<Expression id?>" }`. The `caseName` must match a case declared by `ofType`; the `payload` is present iff that case declared a `caseType` (verifier reports `UnknownSumCase`, `UnexpectedSumPayload`, `MissingSumPayload`, or `SumPayloadTypeMismatch` otherwise). Pattern matching uses a new `kind: "constructor"` form: `{ "type": "Pattern", "kind": "constructor", "patternType": "<SumType id>", "caseName": "<case>", "payloadPattern": "<Pattern id?>" }`. Constructor patterns may nest arbitrarily; VariablePatterns reached from a constructor's payload subtree are valid binders for the enclosing MatchCase's body. The canonical encoder collects all such binders into one stack frame, so VarRefs in the body resolve positionally regardless of how deep the constructor pattern nests.

`Handler` (N-043) JSON schema: `{ "type": "Handler", "intercept": "<EffectCategory id>", "handle": "<Expression id of FunctionType>", "body": "<Expression id>" }`. The handle expression is evaluated once at Handler-entry under the surrounding handler stack, producing a function value (a Closure, ForeignFn, or FixpointFn). The body is evaluated with an `ActiveHandler(intercept, handlerValue)` pushed on a per-call-stack list of active handlers. At every Application in the body, the interpreter scans the handler stack via `findLast` and invokes the innermost handler whose `intercept` is in the called function's declared effects, in place of the original dispatch; the intercepted category's capability check is skipped at that site (the handler subsumes it). Verifier errors: `HandlerNotAFunction` (handle is not a function type), `HandlerOverPolymorphicHandle` (handle is `Forall`-typed), `HandlerSignatureMismatch` (an intercepted Application's value-arg or result types do not match the handler's). The closure rule `closureOf(handler) = (closureOf(body) - {intercept}) ∪ closureOf(handle) ∪ handleFun.effects` is the only place a node category removes an effect from a closure; this is what lets a body that depends on Time.Now run in a surrounding Lambda that does not declare Time.Now.

`ActiveHandler` is an internal interpreter type (not exposed to host code) that carries an `intercept: NodeId` (the EffectCategory) and a `handler: Value` (the pre-evaluated callable). The active-handler list is threaded through every `eval` and `apply*` call alongside the `CapabilitySet` context — the three public `eval` overloads each start with `handlers = emptyList()`.

## State machines (Layer 6 steps 1 and 2)

`StateMachine` (N-027) JSON schema: `{ "type": "StateMachine", "transitionFn": "<Lambda id>", "initialState": "<Expression id>", "inputStreams": [<EventStream id>, ...], "outputStreams": [<EventStream id>, ...]?, "effects": [<EffectCategory id>, ...]? }`. `outputStreams` and `effects` default to `[]`. `inputStreams` must be non-empty (step-1 single-input bound was lifted in step 2). For single-input machines the transition's Event parameter type is `inputStreams[0].eventType`; for multi-input machines the verifier synthesizes a tagged InputEvent sum `stream_0(T_0) | stream_1(T_1) | ... | stream_{n-1}(T_{n-1})` via `Verifier.synthesizeInputEventSum` and requires structural equality (the user declares a matching SumType with cases named `stream_i` in declaration order). The `transitionFn` must be a direct Lambda (Fixpoint-wrapped transitions are step 3) typed `(State, Event) -> (State, Outputs)`. `EventStream` (N-028) JSON schema: `{ "type": "EventStream", "eventType": "<Type id>", "streamKind": "external|internal|output" }`. Both lowercase and capitalized forms are accepted at ingest; the canonical encoder emits the discriminator as a small int (0=External, 1=Internal, 2=Output). `Transition` (N-029) JSON schema: `{ "type": "Transition", "guard": "<Expression id?>", "body": "<Expression id>" }` — parsed for forward schema stability, but no corpus program uses it; standalone Transitions reached via `infer()` are rejected as `TransitionStandalone`.

**Output shapes.** The transition function's result `outputs` field may take either of two shapes; the verifier accepts both and the runtime dispatches based on the produced value. (1) **OutputBatch** (step 1, preserved): a product `{output_0: Option<outputStreams[0].eventType>, output_1: Option<...>, ...}` where each `output_i` is `Some(payload)` or `None`. Empty `outputStreams` means OutputBatch is the empty product `{}`. The verifier synthesizes the `Option<T>` shape via cases `Some` and `None` (user-authored Option types with the same case set compare equal under `TypeExpr.Sum` equality). (2) **Tagged list** (step 2, new): the recursive type `μ. Cons({head: TaggedOutput, tail: <self>}) | Nil` where `TaggedOutput = output_0(T_0) | output_1(T_1) | ... | output_{n-1}(T_{n-1})`. Synthesized via `Verifier.synthesizeTaggedOutputListType` with the canonical case order `Cons, Nil` (matching corpus 31/32). The list form is strictly more expressive — a transition may emit zero, one, or many events per step, to any combination of output streams. For machines with one or zero outputs the OutputBatch form is more convenient; for multi-output or variable-arity emissions the tagged-list form is required. The positional naming (`output_i`, `stream_i`) is deliberate — there is no concrete syntax in Strand, so position is the structural identity.

**Verifier rules.** `StateMachineRequiresInputStream` (zero inputs), `StateMachineTransitionFnNotLambda`, `StateMachineTransitionFnShapeMismatch` (the transition does not match either expected `(State, Event) -> (State, Outputs)` shape — OutputBatch or tagged-list), `StateMachineInitialStateTypeMismatch`, `OutputStreamEventTypeMismatch` (per-slot pinpoint when the OutputBatch shape is closest), `StateMachineEffectCoverageViolation`, `StateMachineMissingImplicitEffect` (slice 3.5 — requires `StateMachine.Receive` always and `StateMachine.Send` when outputs declared, looked up by `EffectCategory.categoryName`), `MalformedEventStream`, `TransitionGuardNotBoolean`, `TransitionStandalone`.

**Runtime APIs.** `runtime/` is a separate Gradle module under `runtime → interpreter → verifier → core`. Two public entry points:
- **Step 1 sync trace.** `StateMachineRuntime.runMachine(machine: NodeId, events: List<Value>, capabilities: CapabilitySet = CapabilitySet.EMPTY): Trace`. Builds a `MachineInstance` (cached transitionFn closure, initial state, per-input-stream `ArrayDeque`, per-output-stream `MutableList`), folds across the event list invoking `Interpreter.applyCallable` per event, decomposes each `{state, outputs}` result, and accumulates a `TraceStep.Step(event, before, after, outputs)` per event plus a final `TraceStep.Halt(finalState, EventsExhausted)`. Restricted to single-input machines using the OutputBatch shape (the step-1 invariant `runMachine` enforces internally). Replay-determinism seam: feed `MachineGroupHandle.recordedEvents(instance)` back into `runMachine` against the same StateMachine NodeId to reproduce the per-step trace.
- **Step 2 async actor group.** `StateMachineRuntime.runGroup(group: MachineGroup, scope: CoroutineScope): MachineGroupHandle`. Validates topology (`MachineGroup.validateTopology` raising `MachineGroupValidationError.InternalStreamNoProducer | NoConsumer | MultipleProducers | MultipleConsumers | ExternalStreamCannotBeProduced | OutputStreamCannotBeConsumed`), allocates one `Channel<Value>` per unique EventStream NodeId (structurally-equal streams share a channel — content-addressing IS the wiring), builds one `MachineInstance` per machine wired to the shared channels, spawns one `launch { runActor(instance) }` coroutine per instance. The `MachineGroupHandle` exposes `externalInputs: Map<NodeId, SendChannel<Value>>`, `externalOutputs: Map<NodeId, ReceiveChannel<Value>>`, `await()`, `cancel()`, and `recordedEvents(instanceId)`. Each actor's loop uses `select` over its input channels (Q-009's nondeterministic-merge default), wraps multi-stream payloads in a `stream_i`-cased SumV, calls the cached transition function via `Interpreter.applyCallable`, then dispatches outputs by detecting the value's shape (ProductV → OutputBatch path; SumV → tagged-list path).

`Interpreter.applyClosure` is promoted from `private` to `internal` so the runtime can construct its own per-event apply path (`applyCallable`) without re-entering `Interpreter.eval` at the top level. The pre-evaluated transition function value is cached at instance start — a Lambda body can be deeply nested under Let/TypeAbstraction whose captured environment is non-trivial to rebuild every event; caching makes per-event dispatch a single closure-apply call.

**CLI subcommands.**
- `strand machine <file.json> --events <events.json>` — drives a single-machine program through the step 1 synchronous `runMachine`. Event JSON: top-level `{"events": [...]}` with tagged value records (`{"tag": "int", "value": N}`, `{"tag": "product", "fields": {...}}`, `{"tag": "sum", "case": "X", "payload": ...}`). Prints the trace in a human-readable line-per-step format.
- `strand group <file.json> --events <events.json>` — drives every StateMachine reachable in the canonical store as a `MachineGroup` through `runGroup`. The events file uses the "routed" format `{"events": [{"stream": "<authorName>", "tag": "<tag>", ...}, ...]}` — each entry names the destination external input stream by its author id. Output streams are drained concurrently and each emission is printed as it arrives, prefixed with the output stream's author name. Multi-machine programs use a top-level `Let` chain (e.g., corpus 48) so `Hasher.finalize` keeps every StateMachine reachable; the CLI walks the store for all StateMachine NodeIds rather than relying on the root.

Both event formats are decode-only in step 2; encode-side support lands alongside snapshot/replay in step 3.

**InstanceId.** Each `runMachine` / `runGroup` instance is tagged with a fresh UUID-backed `InstanceId`. Step 1's `Trace` does not expose it (one instance per `runMachine` call, so the id is implicit); step 2's `MachineGroupHandle.instances: Map<InstanceId, MachineInstanceHandle>` exposes it for inspection and per-instance recorded-event retrieval.
